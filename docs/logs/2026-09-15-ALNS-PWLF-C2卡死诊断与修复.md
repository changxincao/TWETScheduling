# ALNS PWLF C2 卡死诊断与修复

## 1. 问题与结论

平衡 family 算例生成 seed 时，远端 Oracle JDK 21.0.7 上有两个进程连续运行约 20 小时，另一个同类进程在 `HEU.Solution.merge3Segments` 的 C2 编译代码中触发 JVM native crash。此前观察到的约 4 万和 18 万个 PWLF segment 是进程内所有存活函数的总量，不是某一条函数链增长到该长度，不能据此判断算法仍在正常处理超大函数。

Heap dump 中确认一条 `PiecewiseLinearFunction.Segment` 链出现 `next == this` 的单节点自环，线程因此在 `PiecewiseLinearFunction.shiftX` 中无限遍历。JFR 同时显示该热点存在大量反优化；相同 jar、输入和 seed 在远端使用 `-XX:TieredStopAtLevel=1` 禁用 C2 后可正常完成，本机 Java 22 也可正常完成。结合 native crash 所在位置，当前证据将问题定位为远端 JDK 21.0.7 C2 对 `merge3Segments -> shiftX().add()` 高频临时链表路径的优化异常，而不是算例正常需要 20 小时，也不是 ALNS 时间判断本身失效。

`C1` 是 HotSpot 的快速、轻量优化编译器，`C2` 是高频热点使用的激进优化编译器。C1-only 仅用于定位问题，正式运行仍允许 C2；修复通过改写 Java 热路径规避触发条件，不依赖关闭 JIT。

## 2. 修改

`Solution.merge3Segments` 中五处 `shiftX(...).add(...)` 改为已有的 `PiecewiseLinearFunction.addShifted(...)`。后者直接以双指针扫描完成“横移后的函数与另一函数相加”，在定义域、斜率和截距上与原表达式等价，但不再创建临时 shifted 链表，也避免触发已观察到的 C2 异常路径。

`PiecewiseLinearFunction.copy()` 和 `shiftX()` 增加单节点自环检查。一旦遇到 `segment.next == segment`，立即抛出 `IllegalStateException`，避免损坏结构持续占用 CPU。该检查每个 segment 只增加一次引用比较，不改变正常函数结果。

没有修改 `EngineALNS`、`EngineVND`、`Move` 的内部截止时间、循环条件或搜索预算。需要特别说明：当前 `ExperimentBatchScheduler` 使用无超时的 `Process.waitFor()`，尚未提供独立的子进程硬截断。本次通过规避 C2 触发路径并对已观察到的自环快速报错恢复正常退出；如需额外防御，应在批处理器外层单独增加进程级超时，不能改动算法内部时间语义。

## 3. 验证

随机等价测试覆盖 50,000 组 PWLF，比较原 `f.shiftX(delta).add(g)` 与 `addShifted(f, delta, g)` 在定义域端点、所有分段边界和相邻边界中点的函数值，全部通过。自环回归测试确认损坏链表会立即失败；`OutsourcingMoveConsistencyTest` 检查 14,168 项通过；现有 `PiecewiseLinearInsertScalarTest` 的 50,000 组随机测试通过。

在远端保持普通 C2 开启，仅覆盖修改后的两个类后，三个已知失败输入均正常完成：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| `n50-set02 / m3 / family / medium / narrow` | 超过 20 小时仍卡在 `shiftX` | 45.702 秒，成本 377513 |
| `n60-set03 / m2 / family / high / zero` | 超过 20 小时仍卡在 `shiftX` | 172.792 秒，成本 1210070 |
| `n50-set03 / m4 / family / high / narrow` | JVM 在 C2 编译的 `merge3Segments` 中崩溃 | 19.574 秒，成本 741239 |

第一项与远端 C1-only 对照得到相同成本 377513。ALNS 是按时间预算运行的随机启发式，不同编译路径的迭代数和最终指纹可以不同，因此这里只把相同成本和正常结束作为回归证据，不声称逐步轨迹一致。

`n60-set03` 的 172.792 秒不是单次 ALNS 越过 60 秒限制。正式 seed 入口固定运行三个独立随机 seed，再选择其中成本最低者；三次分别耗时 60.170、57.430 和 55.132 秒。第一轮略高于 60 秒，是因为时间只在 ALNS 外层迭代边界检查，已经开始的一次 VND 会完整结束。相应地，`n50-set02` 三次只耗时 16.209、14.373 和 15.070 秒，是由无改进迭代数等停止条件提前结束。因而不同算例的 seed 总时间本来就会不同，理论上可接近三倍单次预算。

## 4. 当前边界

诊断 overlay 已在第三台远端的诊断目录验证，但本次没有替换正在使用的正式批次 jar，也没有终止两个原始卡死进程。正式续跑前应构建包含本修复的新版本，并显式终止或跳过旧卡死任务后重新排队。若同时增加外部硬保护，应作为独立的调度基础设施修改验证。
