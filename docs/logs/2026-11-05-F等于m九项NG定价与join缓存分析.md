# F=m九项NG定价与join缓存分析

主要结论：这9项慢在NG exact pricing，而非分支树；同时存在约21轮DSSR的重复搜索和不便宜的单轮函数labeling。wide还叠加了明显的join组对膨胀。不能只用“节点少”判断计算轻，也不能把全部join时间都归给缓存。此次只读提取、统计和核查代码，没有改求解器、缓存、堆额度或在途任务。

## 1. 范围、计时口径与对照

固定前一份49项配对中的n60/set01/family/F3/m3，共base/medium/high×zero/narrow/wide的9项。NG来自06检修前已完成输出，8项TIME_LIMIT、1项根节点闭合；不混入本轮24GiB新资源重跑。读取9份NG components/nodes/config及live/stdout，另通过只读SFTP获取交接机原18份TI/TI+SRI已完成结果的components/nodes，没有运行该机程序或恢复实验。输入和加载seed的配对沿用20261105-ng49-ti-paired.csv的逐项核验；运行硬件/时段不同，不将每次pricing视作同dual控制实验。

总时间、组件时间取最终CSV，DSSR调用数/轮数取每条Pricing[GCNGBBStyleNgDssrPricing]结束日志，按pricingCall去重。732条日志与components中的732次exact调用逐项一致；这些调用可因时限返回，累计15307轮包含末尾不完整轮，不表示15307份精确闭合证书。所有732次记录均repairPricing=false。

exactPhaseMs在单次pricing开始清零、DSSR各轮累积，所以每次调用只加一次；forward/backward为正式续跑部分，probe包含最终保留状态及丢弃候选，不能把全部probe当浪费，也不能把probe再重复加进init。累计组件exact86285.95秒，phase总计比它少24.13秒，其中末次初始化超时未打印完整phase；该小尾部未伪分配到join或labeling。

## 2. 耗时的具体位置

占比统一以九项累计solveTime为分母，不是对每项百分比简单平均。

| NG分项 | 平均每项秒 | 占总时间 |
| --- | ---: | ---: |
| forward正式续跑 | 4849.38 | 49.57% |
| backward正式续跑 | 1710.34 | 17.48% |
| midpoint probe | 1331.03 | 13.61% |
| join | 1612.16 | 16.48% |
| 其余初始化（不含probe） | 67.81 | 0.69% |
| join前compact | 13.26 | 0.14% |

因此“DSSR轮数多”和“单轮慢”都成立，不能只挑其中一个。base/narrow和base/wide都约21轮，但每轮2.11秒和5.23秒，且exact调用31次对98次；medium/narrow每次只有11.9轮，仍因每轮12.07秒耗满时限。这些是不同CG轨迹/dual下的观察分解，不是单独改变窗口的控制消融。

全部732次NG调用的repeatability过滤均报告repeatable60/nonRepeatable0，说明F=m并没有让时间窗自动排除重复访问；实际仍需反复恢复elementarity。这条证据只能说明本9项，不能推出所有F=m都难。

TI平均总5758.34秒，其中全部pricing3639.63秒（63.21%）；TI+SRI平均总5190.75秒，其中pricing4920.20秒（94.79%）。普通TI主定价累计138952次，单次加权均时0.1598秒；TI+SRI主定价8677次，均时5.098秒。NG一次完整exact含多个DSSR轮，不能直接把117.88秒当作与TI的一轮等价；但NG的单个松弛轮均时5.64秒也显著高于普通TI，且再叠加约21轮。不同dual/列池/树轨迹意味着这些均值不是同状态算力的严格比值。

例如base/wide：普通TI主定价505次，共9.586秒，平均0.019秒；NG exact98次，共10816.0秒、2070轮。普通TI不要求每列elementary，无须在每次定价内部执行这套恢复流程；NG的强列空间不能免费取得。TI虽然树可能更大，但可以用很便宜的定价支撑更多CG/节点，NG则在少数节点内已耗尽时间。TI+SRI也并非都快：base/wide与high/wide仍耗满3小时，不能泛化为它在本组每个场景都占优。

## 3. join缓存的影响与边界

9份实际config均enableNgDssrJoinEnvelopePrefilter=true、enableNgDssrJoinEnvelopeCompression=false。恢复时仍是冻结v8，没有删除先前发现的group-pair Boolean缓存，也没有收缩跨terminal的BitSet生命周期。本地同版JoinEnvelopeIndex仍包含两层结构，分析见2026-11-05-NG-DSSR-join缓存OOM分析.md。

| 窗口为wide | 累计join秒 | 占总时间 |
| --- | ---: | ---: |
| base | 4165.2 | 38.23% |
| medium | 3317.6 | 30.43% |
| high | 2569.9 | 23.77% |

zero约4.56%--6.02%，narrow约10.02%--13.14%。因此wide上的join不是小开销；其大头不能用全组平均16.48%掩盖。

base/wide第98次exact单次1107.82秒、31轮，其中全部join758.33秒。最后一轮的预筛计数为737963691个组对，预筛join346.737秒。medium/wide第52次exact为573.23秒、24轮，join296.71秒，最后一轮402472641个组对、预筛join233.807秒。该组对计数在initialize中resetStatistics清零，表示对应最后一轮，不是所有调用累计；不能把它误写成存活label数。

prunedForwardIndices已用(backwardGroup,lastJob)的BitSet缓存整份结果；同组合以后直接命中BitSet，不再进入canPruneGroup。forwardGroup绑定固定terminal，因此当前唯一调用链下，每个forwardGroup/backwardGroup判定只有一次，pruneByGroup内的Boolean关系没有后续命中收益，却仍被保存到本轮join结束。数亿组对会使这层引用表及扩容代价很大；BitSet还跨已处理的terminal保留，另有生命周期累积。这是可核查的低效点，与“全部join应关闭”不同，必要的预筛判定和真正的路线拼接仍须保留。

现有日志没有heap dump或按分配来源记录的GC时间，无法给缓存占堆比例、GC连带耗时或删除缓存后的精确加速比。join计时包括索引、预筛、必要函数比较、真实拼接和期间GC，不能把4165秒全部说成无用缓存。即便只作算术假设把base/wide全部join时间去掉，仍剩约6729秒，远高于TI的34.7秒，说明多轮函数搜索本身仍是主要差距之一；这不是缓存优化总收益的理论上限，因为潜在GC连带效应未量化。

当前判断：该缓存优化值得单独验证，尤其针对wide与旧OOM样本；但不能据本次统计承诺NG会因此追上TI。先保留在途实验不动，未关闭prefilter、未改memory更新或正式配置。
