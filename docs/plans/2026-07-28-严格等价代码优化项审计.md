# 严格等价代码优化项审计

## 1. 审计边界

本次只检查附件中九类优化建议与当前代码的对应关系，不修改算法代码，也不启动求解。严格等价的含义仍是：pricing engine 调用顺序、DSSR 的 Tmid/轮次/top-C/K/更新顺序、返回列及排序、restricted column ID 集合及顺序、strong branching 评分和分支树、certificate/fixing/writeback 均不改变。

需要补充一个边界：ALNS 使用墙钟时间终止时，即使只增加诊断计时，也可能轻微改变最后执行的迭代数。因此 VND operator 计时必须由诊断开关控制；若要逐项比较列和分支树，应使用非绑定总时限或固定迭代数的诊断入口。

## 2. 当前结论

### 2.1 应优先实施

1. **拆分 LP 建模、求解和解读取时间。** 当前 `LP.solveRelaxation()` 把 `buildModel()`、`cplex.solve()` 和 dual/value 读取记在同一个 master LP 时间中；`Tree` 中名为 `*_rmp_build` 的统计只覆盖 `LP.construct()`，没有覆盖 CPLEX 矩阵构造。因此现有日志无法判断 strong trial 慢在 Java/Concert 建模还是 simplex。应先按 variables/objective、coverage、machine/branch、cut、repair、solve、extract 分段计时。该修改只增加粗粒度计时，不改变调用顺序。

2. **复用普通 time-indexed 的大数组 scratch。** `TimeIndexedGraphSolver` 每次 pricing 都重新分配 `dist`、`predState` 和 `predAddedJob`，在大 horizon 下单次可产生十几 MB 的短命数组。engine-local buffer 按当前 `stateCount` 完整重置即可保持严格等价，同时明显降低分配和 GC；不应复用任何旧 dual 下的数值。

3. **引入最小版不可变列结构共享。** 当前 temporary `TWETColumn` 进入 `Pool` 后，sequence、signature、jobs 和 jobVisitCounts 会再次构造；同 sequence 成本改善时也重新构造全部结构。建议先引入只包含这四项的 `ColumnPattern`，temporary candidate、Pool column 和成本改善 header 共享它，并缓存一次只读 sequence view。不要第一步就把全部 arc posting、adjacency 和 cut 系数塞入该对象。

4. **若继续重点优化 time-indexed SRI，则实现 packed residual。** 当前每个 rank-1 label 扩展都会 clone `byte[activeCuts]`，并逐 cut 扫描。现有 residual 严格为 0/1，适合用 `long`/`long[]` 表示。该修改能降低状态复制和逐 cut 判断，但不能消除 horizon 与 residual 组合造成的 label 膨胀。实现时必须分别保持 forward、backward、join、dominance 的现有更新顺序，并按 active cut index 递增累加 dual，避免改变浮点求和顺序。

### 2.2 先完成 LP 计时，再决定范围

5. **LP 系数缓存有价值，但不能一次做成全局 posting 系统。** coverage 已使用 O(1) 的 jobVisitCounts，主要问题只是 `n × restricted columns` 扫描；arc/adjacency 行仍会反复扫描 sequence；SRI 行还会为每个 `(cut,column)` 重建 scope/memory membership 并扫描 sequence。建议顺序为：
   - 先把 cut 编译成可复用的 scope/memory 表，去掉每次系数计算的 boolean 数组分配；
   - 在 `ColumnPattern` 中按紧凑 primitive 数组缓存 directed arc multiplicity/adjacency；
   - 只有 LP 分阶段统计仍证明行构造占主导时，再增加稀疏 `(cutId,columnId)` 系数缓存。

   暂不建立全局 `arcKey -> columnIds` posting。它会增加列池常驻内存、restricted 交集和顺序恢复逻辑，当前没有证据表明优于按 restricted column 顺序读取列内缓存。cut ID 当前不可变，因此 `(cutId,columnId)` 缓存语义可行，但必须稀疏或有界。

6. **有界堆只替换“大 M、小 K”的位置。** `LP.resetRestrictedColumnsByCurrentReducedCost()`、外包对应入口和 time-indexed root seed 选择可以从全排序改为 bounded heap，并在最后按原 comparator 排序。Arc strong candidate 最多约 O(n^2)，而且 `Tree` 当前需要完整 candidateCount；phase1/phase2 数量更小，不值得为它们增加统一堆框架。root seed 还要先排除已经是 root seed 的同 signature 列，否则只保留 K 个候选会改变“跳过重复后继续补足 K 个”的语义。

### 2.3 可做但优先级低

7. **time-indexed candidate 扫描只做小改。** dual-window evaluator 失败前不必先构造 signature；重复 job 可在回溯时用 epoch 数组同步判断；最终可直接复用 `ColumnPattern`。不建议给每个时空 state 增加 `depth` 数组，只为精确预分配少量返回 sequence 的容量会额外增加 O(nH) 内存，收益不抵成本。

8. **ng-DSSR repeated-segment scratch 暂不改。** 当前每条 witness 分配两个 `n+1` 整数数组；一轮可能扫描到 top-C 上限，但找到 K 个有效更新后即停止，且 `n` 通常为 40--100。其中 `middleMarks` 已用 mark 避免清零，`lastPosition` 的短数组填充很便宜。只有后续 allocation profile 证明该处显著时，才值得改为 solver-local epoch scratch。

### 2.4 当前不建议实施

9. **不缓存 Node 的 time-indexed arc lookup。** 当前 lookup 只在存在时空禁弧时构造一个 O(n^2) 的 `BitSet[]` 只读视图，已经避免了热循环中的 HashMap 查询。跨 pricing 缓存需要覆盖 forbid/replace/merge/copy/writeback 的全部失效路径，复杂度高于当前可见收益。

10. **不把 static time-indexed tables 提升到全局 Context。** 普通 no-cut 与 rank-1 主线本来互斥；rank-1 已与其 no-cut delegate 共享同一 `StaticPricingData`。pre-heuristic 当前默认关闭，root preprocessor 又是短生命周期独立 context。继续全局化主要会延长大 penalty table 的存活时间，实际重复构造很有限。

## 3. 当前代码中已经完成的相关优化

ng-DSSR top-C witness 池已经是 `SequenceSignature` 哈希表加有界 `TreeSet`，不存在附件之外所说的线性 sequence 去重和每次全排序；no-SRI 主线也已经在分配 SRI 容器前返回。初始列构造已经用本次 build 的 `evaluatedSequenceIds` 避免同一历史 sequence 重复 evaluator。这三项不应重复修改。

## 4. 推荐实施顺序

1. LP/VND 诊断计时，其中 VND 统计默认关闭。
2. time-indexed primitive scratch 复用。
3. 最小版 `ColumnPattern`，先只消除 candidate 到 Pool 的重复结构构造。
4. 根据 LP 计时结果，优先做 compiled cut coefficient 和列内 arc/adjacency 缓存；再判断是否需要稀疏 cut-column cache。
5. 仅在保留 time-indexed SRI 为核心实验方法时，实现 packed residual。
6. 最后考虑目标明确的 bounded heap 和 candidate 小优化。

每项应独立提交。除 wall-clock 诊断外，结构等价测试至少比较：每轮 pricing 返回 signature/成本/顺序、restricted IDs 及顺序、active cuts、strong candidate/side score、节点创建和关闭顺序、最终 objective/bound。
