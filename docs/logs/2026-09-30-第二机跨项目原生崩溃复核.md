# 第二机跨项目原生崩溃复核

2026-09-30约16:04--16:15，只读检查第二机 `100.68.243.192` 的 `D:\ccx`。本次用户要求定位频繁报错的原因；没有停止、重启实验，没有修改远端代码、JDK、BIOS或求解配置。

## 1. 当前判断

频繁报错主要发生在当前 `TSPP_SVU` 实验，而非正在运行TWET。错误是MOSEK、CPLEX和HotSpot编译器中的原生访问异常；不能用增大Java堆解释，也不能直接断言Java业务代码无误或CPU已损坏。当前应同时保留两条诊断线：特定模型/连续模型创建触发的native缺陷，以及这台i9-14900K的运行平台稳定性。

按文件SHA-256去重后的中间快照有62份TSPP、25份TWET fatal日志，复制到多个部署目录的同一日志没有重复计数。TSPP快照按顶层problematic frame分为40份MOSEK、11份CPLEX、7份JVM、4份其他。随后又发现16:07:58的 `hs_err_pid5972.log`；按日志内部Time字段统计，今日已有53份独立fatal日志。该数量是进程崩溃次数，不是53个不同算例，重试会反复计数。

第二机为Dell OptiPlex Tower Plus 7020，i9-14900K，128GB内存，Oracle JDK 21.0.7，BIOS 1.24.0，注册表微码0x133。不能因为微码已较新就排除既有硬件退化，也不能因为没有WHEA记录就排除CPU/RAM错误。BIOS当前已经是1.24.0，不应照搬此前第三机的1.23.1状态。

## 3. 为什么不能只归因于某个求解器

TSPP日志中不仅有MOSEK `Task.optimize()` 崩溃，也有CPLEX添加行、添加变量、LP/MIP求解阶段的崩溃。另有C1和C2 CompilerThread原生崩溃，其中一例为向地址0的DEP执行异常。独立的TWET旧批次也包含HotSpot/GC访问异常；其另3份日志明确是系统内存提交不足，必须与访问异常分开，不应一概归硬件。

多个组件随机地址异常使CPU/RAM、旧JDK、native内存破坏都值得检查。另一方面，多份MOSEK日志在相近DLL偏移崩溃、固定模型测试成功而模型序列失败，也保留了求解器内部缺陷或模型生命周期问题的可能性。fatal栈记录的是最终出错位置，不保证此前的破坏也发生在那里。

## 4. 下一步最有辨识力的验证

1. 在失败模型调用solve之前导出 `origin60/lambda0.25` 的完整MOSEK task，保留输入和文件hash；应保存真正失败模型，而非另一个已成功模型。
2. 先在第二机新进程中直接用MOSEK CLI重复求解该task。若稳定复现且另一台机器也复现，优先提交MOSEK模型复现包；模型病态或库bug都比机器猜测更可验证。
3. 若该task单独稳定、只有连续模型序列失败，保持完全相同序列再用新版JDK测试，并检查native对象释放、共享对象、JNI jar/DLL版本及分配器；可用分进程逐模型运行作为诊断，不能直接改正式流程掩盖问题。
4. 在另一台已知稳定机器运行相同task及完整序列。若只有第二机失败，CPU/RAM/BIOS/系统环境方向明显增强。
5. 对持续不同地址、跨CPLEX/MOSEK/HotSpot的异常，安排Dell诊断、内存测试和默认BIOS参数下的CPU稳定性测试。Intel确认13/14代部分桌面CPU存在Vmin Shift风险，但本机是否属于该问题必须继续验证，不能由型号直接认定。

当前4个Java进程属于TSPP的2个controller与2个worker，controller低CPU是正常等待；16:07:58其中一个worker再次崩溃。继续重试可能增加崩溃数量，但没有完成上述分离诊断前，重复整批实验的定位价值有限。
