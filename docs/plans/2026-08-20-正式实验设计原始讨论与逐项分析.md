1. 允许与禁止外包
论文比较了 R109a、R111a 的两组最优路线图：
- 禁止外包时，私人车队必须服务全部客户，路线出现较多交叉和绕行。
- 允许外包后，一些“麻烦客户”被移出私人路线，剩余客户可以形成更紧凑、交叉更少的路线。
- 这些客户未必只是距离最远，也可能是时间窗与周围客户不协调，把它插入路线会显著破坏原有顺序。
所以它真正得到的结论是：
外包不仅是补充运输能力或降低直接成本，还可以选择性移除破坏内部路线结构的客户，从而改善私人车队的整体组织效率。
即使时间窗较紧，这种作用依然存在。它对应到我们的调度问题就是：
- 外包可能优先移除 due window 与其他任务冲突的任务；
- 或者移除会产生较大 setup time/setup cost 的任务；
- 剩余内部任务因而形成更连贯的机器序列；
- 内部 TWET 和 setup 成本可能下降，不能只看外包任务数量。
不过，论文这里只展示了几个代表实例的路线图，没有汇总“平均少多少交叉、平均降低多少成本”，因此属于案例型证据，不是普遍统计结论。
2. 数量折扣
论文比较的是：
- **无折扣：**无论外包多少，都使用最高单位费率；
- **有折扣：**外包总需求越大，单位费率分段下降。
首先有一个直接结论：取消折扣后，所有实例的最优目标值都会上升。但更重要的是，折扣对最优方案结构的影响取决于客户分布。
对于随机、分散实例：
- 有无折扣时，外包集合和私人路线变化很小。
- 例如 RC105 中，启用折扣只多外包了一个需求量为 5 的客户。
- 也就是说，折扣虽然降低支付成本，但没有明显诱导更多外包量。
- 论文据此认为：对于分散客户，公共承运商提供折扣未必能换来足够多的新增业务量。
对于聚类实例：
- 有无折扣时，外包集合和私人路线发生明显变化。
- 折扣会使企业倾向于把一组相邻客户一起外包，从而跨过数量断点、获得更低单位费率。
- 客户聚集程度越高，折扣对外包量和路线结构的影响越明显。
- 因此，公共承运商在聚类业务中提供数量折扣更可能获得新增外包量。
所以数量折扣部分真正的结论是：
数量折扣的效果取决于任务能否形成具有共同结构的“可成组外包集合”。对于彼此分散、缺少协同关系的任务，折扣主要降低既有外包成本；对于聚类任务，折扣可能改变外包决策本身，并触发整组外包。
映射到我们的调度问题，所谓“聚类”不一定是空间聚类，可以表现为：
- due-window 中心接近的一组任务；
- 属于同一 job family 的任务；
- 会共同造成某一时间段产能拥挤的任务；
- 从内部序列中一起删除后能显著减少 setup 或迟到的一组任务。
因此，我们做数量折扣实验时，最有价值的不是证明“折扣越大，外包越多”，而是检查：
1. 外包量是否在折扣断点附近发生跳跃；
2. 新增外包的是零散任务还是具有共同 due-window/setup 结构的一组任务；
3. 折扣只是降低原有外包支付，还是确实改变了内外部任务分配；
4. 内部机器序列是否因此变得更连贯、拥挤程度是否下降。

一、主实验：不同生产环境下，外包价格变化会带来什么影响

先固定一个代表性的任务规模 n，最好选你的算法能够比较稳定求到最优的中等规模。然后按照现有算例生成方式，把实例按三个因素分类：

因素	建议水平	表示什么
setup time	Low / High	任务之间序列关联强不强
due-window width	Tight / Wide	时间要求严格不严格
machine number	Few / Many	内部产能紧不紧

这样就是 2×2×2=8 类基础环境。每类例如生成 10 个实例，同一个基础实例只改变 outsourcing cost，不重新生成任务数据。

然后对 outsourcing cost 统一乘一个系数 λ，例如 {0.5,0.75,1,1.25,1.5,2}。但正式跑之前最好先 pilot 一下，使 λ=1 时不要出现“所有实例全部外包”或“一个都不外包”，否则没有分析空间。

这个实验一次就可以回答你前面的 1、2、3：

外包价格上升以后，外包比例下降多快；
机器少的时候，这条曲线是不是整体更高，即 capacity 紧张时更依赖外包；
due window 窄的时候，是不是同样更依赖外包；
setup 高的时候，外包价格变化是否产生更明显/更弱的反应；
更重要的是看这些因素有没有交互作用。比如机器很多时 due-window 宽窄可能没什么影响，但机器少时 due-window 一变窄，外包迅速增加。

这实际上和 Dabia et al. 那篇 VRP 的分析思路非常接近。他们并不是说“固定成本高一定多外包”就结束了，而是发现这种影响取决于客户是 random 还是 clustered；quantity discount 的作用同样取决于实例结构，随机实例变化很小，而 clustered 实例变化很明显。

所以你这里真正应该找的就是：

同样降低 outsourcing price，在哪一类 scheduling environment 中最容易诱发额外外包？

主要输出也不用很多。我建议固定看 外包任务比例、外包 processing workload 比例、内部 E/T cost、setup cost、总成本。另外再加一个 No-Outsourcing benchmark，就能计算允许外包以后总成本降低多少，即 value of outsourcing。

这样你最后就可以说类似：

当内部 capacity 充足且 due windows 较宽时，即使降低 outsourcing price，最优方案对外包的依赖仍然有限；相反，在机器较少或 due windows 较紧的环境中，outsourcing price 对外包比例具有更明显的影响。

到底是不是这个结果，交给实验决定。

## 逐项分析与收口

### 1. 参考 VRP 论文的性能参数与管理分析参数

对 Dabia、Lai 和 Vigo 的论文重新区分“算法性能实验”和“管理分析”后，原始判断基本正确。
算法性能实验没有系统改变外包价格。论文对每个算例直接使用其所属类别的固定四段 tariff：
断点统一为 200、400 和 600，R 类费率为 `5.00/4.50/4.00/3.50`，RC 类为
`3.50/3.00/2.50/2.00`，C 类为 `2.00/1.50/1.00/0.50`。SP1/SP2、cuts 和
dominance 的对照均在这套既定实例参数上进行。因此它不是“所有算例使用同一个外包价格”，
而是“每个实例类别使用固定 tariff，算法比较时不把 tariff 当作实验因素”。R、RC、C 的
客户结构和承运费率同时变化，所以这些性能表也不能单独识别空间结构或价格的影响。

论文最后的管理分析同样没有做低、中、高外包价格曲线。它主要选择代表实例分析三项内容：
车辆固定成本变化、允许与禁止外包、有数量折扣与无数量折扣。无折扣情景是把各类别最高
单位费率贯穿全域，即 R、RC、C 分别固定为 5.00、3.50 和 2.00，再与原四段折扣比较。
因此，参考论文能够支持“外包是否改变内部路线”和“折扣是否改变外包集合”，但不能支持
“外包价格连续变化时决策如何转折”。当前论文若增加外包价格响应曲线，属于合理的扩展，
不需要为了模仿参考论文而把外包参数固定在一个任意值上。

### 2. 外包价格怎样设置才能形成有效 trade-off

正式参数不能逐实例调到恰好出现某个外包率，否则价格、算例结构和结果会形成循环校准。
更稳妥的做法是先用不进入正式样本的 pilot 实例确定一个全局中心价格，再冻结所有档位。
基础报价继续使用 `b_j=rho*p_j`。可以先用 pilot 中禁止外包方案的单位 workload 成本
`C_i^NO/sum_j p_ij` 确定 `rho` 的数量级，再在一个较宽的对数式网格上测试，使中心价格
下多数环境出现内外部并存。中心价格的目标不是让每个实例都有 50% 外包，而是避免整个
样本退化为几乎全外包或几乎零外包。

原先的 `0.8rho*/rho*/1.2rho*` 适合做局部稳健性，但可能过窄，难以看清从大量外包到
主要内部生产的转折。管理分析更适合先在 pilot 上测试
`{0.5,0.75,1.0,1.5,2.0}rho*`；若两端仍未覆盖低、高外包区间，再统一外扩。正式样本
开始后不再改变这些倍率。禁止外包应通过关闭外包决策实现，并作为单独的配对基准；不能
在数值计算中真的令 `rho=Infinity`，也不应把该点当作价格曲线上的普通有限观测。

### 3. 纯调度算法性能实验

使用 Tanaka 数据派生 `n=20/40/60/80/100` 的方向合理，但不应立即把任务规模、多个
机器数、两类 setup、三类 due window 和三个时间尺度全部交叉。这样会产生数千次长时间
求解，而且很难判断算法排名究竟由规模、负荷还是 horizon 引起。更合理的是分三步进行。

第一步是求解边界 pilot。在原时间尺度、中等 due window 和一类基准 setup 下，使用
`(20,2)、(40,2)、(60,3)、(80,4)、(100,5)` 等代表组合测试四种方法，先确认每种方法
实际能够达到的规模。这里机器数随任务数增加会同时改变规模和单位机器负荷，所以这一组
只能用于寻找可计算边界，不能单独解释机器数效应。

第二步是正式原尺度性能面板。在 pilot 显示可比较的规模上，对同一源实例构造两类 setup
和窄/中/宽三类 due window，完整比较 compact CPLEX、ng-DSSR、time-indexed no-cut
和 time-indexed rank-1/SRI。两类 setup 必须说明究竟改变什么：Low/High setup 表示
序列依赖强度；random/family-clustered setup 才表示任务结构是否聚集。两者不是同一个
因素，不能用“setup 较大”替代“任务聚类”。如果纯性能实验关注计算难度，优先使用
Low/High 强度；若后续管理分析需要对应 VRP 的 random/clustered 机制，再构造均值匹配的
random/family-clustered 结构。

第三步单独做时间尺度扩展。固定代表规模、中等 due window 和固定 setup 结构，将 processing、
setup、release/due-window 端点等时间量同步放大 `alpha=1/5/10`，不加随机扰动。该实验
主要检验 time-indexed 图随 horizon 增长的伪多项式缺陷，应重点比较 ng-DSSR 与
time-indexed no-cut；CPLEX 和 SRI 可以在代表子集上保留，以报告 timeout 时的 bound/gap，
但没有必要把时间尺度与全部规模、窗口和 setup 再做全交叉。四种 BPC/CPLEX 使用同一
实例、同一初始可行方案、单线程和 10800 秒时限，超时结果照样进入表格。

### 4. 两种外包 formulation 的性能比较

外包性能实验的核心对象应是 `columns` 与 `masterVariables` 两种 formulation，而不是
再次全面比较内部机器定价。内部定价固定为已经确定的 ng-DSSR 配置，时间尺度固定为原始
尺度。Compact CPLEX 可以用于小规模正确性和性能参照，但不要求覆盖所有大规模外包实例。
这与参考 VRP 论文先固定其他算法组件、再比较 SP1/SP2 的逻辑一致。

这组实验不需要复制纯调度的完整矩阵，但必须覆盖外包比例可能明显不同的代表环境。建议从
纯调度数据中分层选择两个规模、紧/松两类内部产能、两类 setup 和窄/宽窗口，每格先取
少量共同源实例。经济情景至少包含低/中/高价格且无折扣，因为 formulation 的难度可能随
外包率变化；此外在中等价格下加入一个有折扣情景，确认分段成本不会改变两种 formulation
的相对表现。中等/强折扣都纳入性能面板并非必需，若一个折扣情景已显示相同排序，更多
折扣水平应留给管理分析。

因此，这一部分不应在纯调度所有场景上生成外包成本，也不进入 `alpha=5/10` 的时间尺度
区块。它应是一套平衡的代表子集：每个关键特征均出现，但不做完整高维全因子。主要报告
两种 formulation 的 solved count、时间、gap、root bound、节点、内部/外包 pricing、
RMP 迭代、两类列数、repair 和分支构成；compact CPLEX 只在能够提供有意义参照的规模上
报告。

### 5. 外包价格、内部产能和 due-window 的联合管理分析

原文提出的 `setup x due-window x machine number x outsourcing price` 联合设计，是当前
最有价值的管理实验。它能够在一套配对数据中同时回答：外包价格何时推动 make-or-buy
转折、内部产能紧张时外包价值是否提高、due window 收紧时外包是否改善服务，以及这些
效应是否随序列依赖结构变化。建议固定一个能稳定求得最优的中等规模，使用两类 setup、
窄/宽窗口和紧/松产能形成 8 类生产环境；同一基础实例只改变价格，不重新生成任务数据。

每类环境先使用 5 个共同源实例和 5 个冻结价格倍率，则需要 200 个有限价格外包求解。
对应的禁止外包结果直接复用纯调度实验，不再重复运行。若初步结果的实例间波动较大，再
增加源实例数量，而不是一开始固定每格 10 个并把矩阵扩大到 400 次。统计和图形应采用
同一实例上的配对差值，重点比较价格响应曲线在不同环境中的水平和斜率，而不是只报告
全样本平均值。

这里仍需区分两个 setup 概念。如果目标是研究序列依赖程度，使用 Low/High setup；如果
目标是对应 VRP 中 random/clustered 的结构机制，应使用均值近似一致的 random 与
family-clustered setup。两者同时进入主实验会再次造成爆炸，建议先由论文叙事决定一个
作为主因素，另一个只在代表子集上验证。due-window 宽度表示交付灵活性，机器数表示内部
产能；它们与价格的交互才是这一小节的主要结论来源。

“哪些任务更容易被外包”不宜预先设为独立主假设，但应保留为所有最优解的后处理。先报告
processing time、due-window、TWET 权重、基础外包成本和 setup burden 分组下的外包率；
只有规律在不同价格和生产环境下稳定时，才上升为管理结论。否则如实报告该选择高度依赖
情景，不强行寻找单一任务特征。

### 6. 外包基础成本的两种生成方式

`b_j=rho*p_j` 应继续作为正式主口径。它透明、容易校准，并且不会把 due-window 信息预先
写入外包报价。原文提出的 `processing time + urgency premium` 可以作为小型 robustness，
但不宜与主价格实验完全交叉。直接使用 due-date center 有三个问题：其绝对值会随时间尺度
变化；center 较晚不等于任务一定容易内部加工；更重要的是，当前模型没有外部 lead time
或外包商交付服务，因而“越紧急报价越高”的业务解释尚不完整。

若后续确实保留该稳健性，可用实例内归一化 slack 构造 `u_j in [0,1]`，设置
`b_j=rho*p_j(1+eta*u_j)`，并乘归一化因子，使两种报价机制满足相同的
`sum_j b_j`。`eta` 只固定一个代表值，不再与全部价格、setup、窗口和机器数交叉。该实验
回答的是主结论对报价机制是否稳健，而不是试图证明 due-date-based 报价更真实。若缺少
明确业务依据，这项可以放入附录，甚至完全不做，不影响主实验闭合。

### 7. 数量折扣与分段函数

数量折扣的主问题应是“有无折扣是否改变任务去向”，而不是“最优段数是多少”。参考 VRP
论文也是用各类别最高单位费率贯穿全域，与既定四段折扣直接比较，没有系统改变段数、断点
和每段斜率。当前问题可沿用这一干净逻辑：固定中等基础价格和相同 breakpoint，比较
constant rate 与一套校准后的 incremental discount。若希望观察强度趋势，再增加一套
强折扣即可；没有必要把 2/3/4/5 段作为正文主因素。

折扣参数应在价格 `rho*` 冻结后单独 pilot，避免折扣一开启就退化为全外包。断点按
`B_all` 的比例设置比照搬 200/400/600 更可比；当前 `0.25B_all`、`0.50B_all` 可以作为
初值。正式分析除目标值和外包比例外，还应报告：新增外包 workload、折扣前后外包集合的
重合率、`B(O)` 距 breakpoint 的位置、跨越 breakpoint 的实例数、折扣节省，以及内部
机器序列是否发生重构。这样才能区分“只降低既有支付”和“真正诱导成组外包”。

### 8. 当前推荐的整体实验结构

综合以上分析，正式计算不应形成一个包含所有因素的单一巨型矩阵，而应拆成四个证据层次：

1. **纯调度算法性能。** 先用 `n=20/40/60/80/100` pilot 找到边界，再在可比较规模上做
   两类 setup、三类 due window 的原尺度四算法比较；时间尺度 `alpha=1/5/10` 单独放在
   代表子集上。
2. **外包 formulation 性能。** 固定 ng-DSSR 和原时间尺度，在分层代表子集上比较
   `columns`、`masterVariables`，并以小规模 compact CPLEX 参照；覆盖低/中/高价格和
   一个中价折扣情景。
3. **价格与生产环境管理分析。** 固定一个中等规模，用 `2x2x2` 生产环境和 5 个价格水平
   形成配对价格响应曲线；禁止外包结果从纯调度面板复用，同时分析 value of outsourcing。
4. **数量折扣。** 固定中等价格，在同一环境面板上比较无折扣与有折扣，重点识别外包集合
   和内部序列的结构变化。报价机制或 tariff 段数只作为可选 robustness，不进入主矩阵。

这套结构既保留了原始讨论提出的全部核心问题，也把算法性能、formulation 选择和管理机制
分开。后续真正需要先做的不是继续增加因素，而是完成两组 pilot：一组确定四种纯调度方法
在 `n=20--100` 上的共同可计算边界；另一组校准全局 `rho*` 和一个不会导致退化的折扣函数。
只有这两个结果确定后，才能冻结正式实例数量和最终求解矩阵。

### 9. 参考论文两项管理分析及外包成本生成的进一步核对

允许/禁止外包的结论来自 R109a 和 R111a 等少数代表实例的路线图，而不是完整样本上的
统计检验。禁止外包时，私人车队必须服务所有客户；允许外包后，偏远或时间窗不协调的
客户可以从私人路线中移除，剩余路线交叉更少、结构更紧凑。论文特别指出，这种改善在
R109、R111 这类紧时间窗实例中仍然存在。因此它支持的是“外包可以选择性移除破坏内部
路线结构的客户”，而不是给出允许外包平均降低多少成本或减少多少路线交叉的普遍幅度。

折扣/无折扣分析也是代表实例比较。无折扣时，不论总外包需求是多少，R、RC、C 分别使用
最高边际费率 5.00、3.50、2.00；有折扣时恢复原四段 tariff。取消折扣会使所有测试实例
的最优目标值上升，但方案结构是否变化取决于客户分布。随机分散实例中，折扣前后的外包
集合和私人路线变化很小，论文以 RC105 为例，只多外包一个需求量为 5 的客户；聚类实例
中，折扣会增加外包并明显改变路线，更容易触发整簇客户共同外包。论文由此认为，随机
分散业务中折扣可能主要降低既有支付，未必给承运商带来明显新增业务；聚类越强，折扣越
可能改变外包决策本身。

论文的外包成本不是逐客户随机生成，也不等于每个客户各自的距离成本。每个客户的需求
`d_i` 来自 Liu and Shen 基于 Solomon 构造的原始实例；若外包集合为 `O`，公共承运商只
根据总外包需求 `q=sum_{i in O} d_i` 收费，费用为确定性的分段线性 tariff `Gamma(q)`。
三类实例统一使用 200、400、600 三个断点，边际费率分别为 R 的
`5.00/4.50/4.00/3.50`、RC 的 `3.50/3.00/2.50/2.00` 和 C 的
`2.00/1.50/1.00/0.50`。也就是说，单个客户只通过自己的需求量改变累计 `q`，不存在
独立随机的客户外包报价。

这些费率与私人车辆行驶成本、车辆固定成本、客户 due window 或客户到仓库距离没有公式
上的直接关系。作者只是按空间类别人为设置：客户位置越随机分散，公共承运商费率越高；
聚类客户费率最低。论文没有给出市场数据、估计过程或进一步校准依据。因此 tariff 与
R/RC/C 空间类别存在设计上的关联，但并非从每个实例的实际路线成本计算出来；同时改变
空间结构和费率也意味着原论文不能从性能表中单独识别二者效应。

### 10. 参考论文是否通过成本系数获得“均衡”解

论文没有说明以 50% 外包率、内外成本相等或其他“均衡结果”为目标校准 tariff，也没有
报告跨实例的平均外包任务率/需求率。因此不能根据最终路线图反推作者先设定了一个目标
外包比例。私人服务成本沿用 Liu and Shen 实例中的车辆固定成本与行驶成本；公共承运商
tariff 则由作者按 R/RC/C 类别人为指定。两者在数值尺度上能够竞争，但论文只解释了
“越随机分散，承运商收费越高”，没有给出优化前 pilot、市场估计或平衡条件。

这套设定存在一种定性的抵消关系：R 类客户分散，私人行驶成本通常较高，但外包费率也
最高；C 类客户聚集，私人路线较便宜，但外包费率最低。a/b/c 三档车辆固定成本继续改变
内外部相对吸引力，而 tariff 不随固定成本档位重新校准。因此不同实例自然产生不同程度
的外包，有些解混合使用私人车辆和承运商，但这不是经过统一比例校准的“均衡样本”。

当前调度实验不应直接复制这种依赖类别的人为费率，因为它会把 setup/due-window 结构与
价格效应混在一起。更可控的办法仍是先用禁止外包解的单位 workload 成本确定 `rho` 数量级，
再在独立 pilot 上用统一倍率搜索全局 `rho*`，使正式样本整体覆盖低、中、高外包区域，
而不是要求每个实例都达到相同外包率。

## 11. Dabia、Lai 和 Vigo（2019）Section 7.4 管理启示补充原文

以下内容按本次讨论原样记录，后续实验设计以此为主要参考，不把单一参数的单调变化当作
预设结论。

我重新按这篇 Dabia, Lai, and Vigo (2019), An Exact Algorithm for a Rich Vehicle Routing Problem with Private Fleet and Common Carrier 的 Section 7.4 “Managerial Insights” 看了一遍。它真正得到的管理结论其实不多，主要就是下面 三组，而且很多是通过代表性最优路线图来解释的，不是大规模统计回归。

1. 私有车队固定成本上升，并不一定都会明显促进外包

他们比较了相同实例、不同 vehicle fixed cost 的情况。

对于 随机分布 R 类实例：

固定成本升高以后，外包确实可能增加；
但增加得并不明显；
原因是随机分布下，variable traveling cost 本身很重要，甚至可能比 vehicle fixed cost 更主导；
所以固定成本变化不一定会大幅改变 outsourcing decision。

例如他们比较 R109a 和 R109c：虽然固定成本明显不同，但高固定成本情况下只多外包了一个客户。

对于 聚类 C 类实例：

fixed cost 的影响明显得多；
因为同一个 cluster 内客户之间距离近，服务一个 cluster 的 variable travel cost 相对小；
此时是否多开一辆私人车辆的 fixed cost 就更重要；
一旦固定成本提高，可能会直接把整个 cluster 外包出去。

所以他们真正的结论不是：

fixed cost 越高 → 外包越多。

而是：

外包决策对 fixed cost 的敏感程度取决于实例结构；clustered instances 比随机 instances 更敏感。

这正是你前面说的“参数之间不能孤立解释”的一个很好例子。

2. 允许外包可以改善内部路线结构，而不只是节省直接成本

他们比较了 R109a、R111a：

允许 outsourcing；
完全禁止 outsourcing。

结果发现允许外包后，可以把一些“不方便”的客户拿出去，剩余私人车队的路线明显更规整，交叉更少。

他们特别指出，这些“不方便”的客户并不只是地理位置远，也可能是因为 time windows 不协调。

因此结论是：

outsourcing 不仅用于弥补私人车队 capacity 或比较直接成本，还能够移除破坏内部路线结构的客户，从而得到更紧凑的私人路线。

换句话说，外包存在一个 indirect scheduling/routing benefit：

移除部分客户→剩余客户更容易组织→内部路线成本下降.

而且他们说明，即使是在 tight time-window instances 中，这种作用也存在。

这一点其实跟你的调度问题最有对应关系，只不过你那里不是 route compactness，而可能是：

外包一部分任务以后，剩余任务的内部 sequence 更容易协调。

但论文自己也没有进一步总结“什么特征的客户最容易被外包”，只是通过案例图说明这一现象。

3. 数量折扣的作用高度依赖客户分布结构

这是这篇文章最有意思的一部分。

他们比较：

有 quantity discounts；
没有 discounts：无论外包多少，始终使用 tariff sheet 中最高的单位价格。

首先当然有一个必然结果：

取消折扣以后，所有实例最优目标值都会变差。

但他们重点不是这个，而是看最优 outsourcing decisions 是否发生改变。

对随机分布实例

变化非常小。

例如 RC105 中：

有折扣以后只多外包了一个 demand = 5 的客户；
最优私人路线结构基本没变化。

因此作者认为：

对随机、分散的客户，discount 主要可能是在降低原本就会发生的 outsourcing expenditure，而没有明显诱导新的 outsourcing demand。

于是站在 common carrier 角度：

给这类客户提供 quantity discount 未必划算，因为很难换来明显增加的业务量。

对 clustered instances

完全不同：

discount 会明显改变 outsourced customers；
私有路线结构也明显改变；
clustering 越强，quantity discount 的作用越明显；
企业会因为达到更低单位费率而外包更多客户。

作者因此认为：

对 clustered customers，common carrier 提供 quantity discount 更有吸引力，因为更可能真正增加 outsourced quantity。

所以核心结论是：

Quantity discount 是否改变 outsourcing decisions，并不只由 discount 大小决定，而高度取决于实例本身是否存在可以成组外包的结构。

其实整篇 managerial insights 可以概括成一句话

这篇文章最重要的思想不是：

某参数变大，外包就变多/变少。

而是：

外包政策的效果与问题实例的内部结构存在明显 interaction。

具体有三个表现：

| 改变的东西 | 他们观察到的核心 interaction |
|---|---|
| Vehicle fixed cost | clustered instances 更敏感，random instances 较不敏感 |
| 是否允许 outsourcing | 可以移除“不方便”的客户，改善内部路线结构 |
| Quantity discount | clustered instances 会明显增加 outsourcing；random instances 可能几乎不变 |

因此我觉得这篇文章对你最大的启发其实就是：

你的 setup、due-window、machine number 也不要分别硬解释，而应该看它们形成的不同实例环境，对 outsourcing-price changes 的响应是否不同。

比如最后如果你的实验发现：

某些 setup × due-window × machine-number 组合下，外包价格降很多，外包比例仍然变化很小；
另一些组合下，只要价格略降，外包比例就明显跳升；

这其实就已经是和这篇 VRP 文章同一层次、甚至更系统的 managerial insight 了。

## 12. 当前实验设计的全面收口

### 12.1 先区分三种“算例数量”口径

Tanaka 原始单机 TWET benchmark 包含 11 个任务规模，每个规模均为 125 个实例。原始规模
并不是 `20/40/60/80/100` 的规则序列，而是：

| 原始任务数 | 原始实例数 |
|---:|---:|
| 40 | 125 |
| 50 | 125 |
| 100 | 125 |
| 150 | 125 |
| 200 | 125 |
| 250 | 125 |
| 300 | 125 |
| 350 | 125 |
| 400 | 125 |
| 450 | 125 |
| 500 | 125 |
| 合计 | 1375 |

其中 `n=60`、`n=80` 和 `n=20` 都不是 Tanaka 原始规模。若实验中使用这些规模，必须明确
写成从固定编号的较大源实例中确定性抽取的派生子实例，并公开抽取规则与随机种子，不能
称为 Tanaka 原始 benchmark。

仓库当前库存与原始 benchmark 也不相同。`n=40/50/100` 的单机、双机和四机目录各有
125 个基础文件；三机目录目前分别只有 3 个基础实例，`40-3` 目录另有一个 `timeX10`
派生文件，不能计作第四个基础实例。`n=60` 的 `m=1/2/3/4` 目前都只有 3 个 pilot；
`n=100,m=5` 也只有 3 个 pilot。因此正式实验开始前至少要补齐选中源 case 对应的
`m=3` 和 `n=60` 派生数据。当前 `formal-v1` 的每格 3 例只是运行设施 smoke test，
不是论文正式样本。

正式论文没有必要使用每格全部 125 例，但也不能取编号最前面的若干例。建议先对 125 个
源实例计算不依赖求解器表现的描述量，例如归一化 due-date center、due-date spread、
processing-time variation 和权重分布，再分层抽取每格 5--10 个源实例。实例选择完成后
冻结源编号、派生种子和全部参数，不根据某种算法的时间或 gap 替换实例。

### 12.2 实验一：小规模正确性对齐

这一部分只验证模型和算法是否求解同一个问题，不承担性能结论。建议从冻结的 Tanaka 源
实例中确定性抽取 `n=8/10/12` 子实例，使用 `m=2/3`，每个组合 5 例。比较 compact
CPLEX、外包集合列模型和 master 显式外包模型；两种分解分别使用其正式内部定价配置。

为同时检查内部定价的一致性，具体运行组合固定为 compact CPLEX、`columns+ng-DSSR`、
`columns+time-indexed`、`masterVariables+ng-DSSR` 和
`masterVariables+time-indexed`，共 5 个组合。

每个实例需要核对最优目标值、内部机器序列、外包任务集合、外包总 workload、TWET、
setup cost、未折扣基础外包金额和最终 tariff 支付。若存在多个等价最优解，不要求序列
完全相同，但目标分解和每个方案的独立可行性校验必须通过。该组可能得到的唯一正式结论
是“模型和实现一致”，不应以小规模运行时间宣称某个 formulation 更快。

### 12.3 实验二：纯调度精确算法比较

该部分关闭外包，比较四种方法：compact CPLEX、ng-DSSR BPC、time-indexed no-cut BPC
和 time-indexed rank-1/SRI BPC。所有 BPC 必须共享同一初始列快照、同一上界、单线程、
同一 10800 秒时限和相同 branch-and-price 公共配置。CPLEX 尽量使用同一调度作为 MIP
start。超时实例照样报告上下界和 gap，不能只保留求得最优的实例。

正式原时间尺度面板以 `n=40/50/60`、`m=2/3` 为主，每个 `(n,m)` 单元分层选择 5 个
源实例，共 30 个基础问题。due-window center 保留 Tanaka due date 经机器数换算后的结构，
半宽使用实例尺度化水平 `h=0、2*p_bar、6*p_bar`。这样每个基础问题有窄、中、宽三个
窗口场景，共 90 个原尺度场景。主表应完整比较四种方法，即最多 360 次求解。

setup 不应同时承担“强度”和“聚类结构”两个含义。纯算法性能主表建议固定一套满足有向
三角不等式、闭包后平均约为 `0.5*p_bar` 的基准 setup；若确实需要两类 setup 强度，
则在中等窗口的代表子集上补 Low/High，而不是与三个窗口、三个时间尺度全部交叉。
setup cost 固定为同一比例 `kappa_ij=lambda*s_ij`，`lambda` 一旦冻结便不再做灵敏度。

时间尺度是独立机制实验。固定中等窗口、基准 setup 和代表性的 `n=40/50`、`m=2/3`，
将 processing、setup、due-window 端点和 horizon 同步乘以 `alpha=1/5/10`，不加入扰动。
该组重点比较 ng-DSSR 与 time-indexed no-cut；SRI 和 compact CPLEX 可在代表子集保留，
但不应为了矩阵完整而把明显无法求解的组合全部扩展。该组回答的是 time-indexed 图对
horizon 的伪多项式敏感性，而不是任务组合结构随 `alpha` 改变。

这一实验可能出现的结论应按证据表述。原尺度、较小 horizon 下，time-indexed 尤其带
rank-1 cuts 的版本可能明显更快；随着时间量同比放大，图节点、弧和 SRI 状态定价成本可能
快速增长，而 ng-DSSR 的计算量对数值尺度更稳定。若 ng-DSSR 只在大 horizon 或宽窗口区域
占优，应把它写成适用区域和扩展性优势，不能写成全面优于 time-indexed。还应分别报告
root gap、节点数和各阶段耗时，区分“根节点更强”与“单次 pricing 更快”。

### 12.4 实验三：两种外包 formulation 的计算性能

这一部分固定内部定价为 ng-DSSR，比较外包集合列化 `columns` 与 master 显式外包及 tariff
变量 `masterVariables`。不再同时改变内部 pricing，否则无法判断差异来自外包建模还是
调度子问题。时间尺度固定为原尺度；compact CPLEX 只在小规模和能够形成有效参照的中等
规模报告。

建议使用 `n=40/50`、`m=2/3`、每格 5 个源实例，共 20 个基础问题。为避免 formulation
排序只对某个外包率成立，每个基础问题覆盖四个经济情景：低价无折扣、中价无折扣、高价
无折扣和中价有折扣。这样两种 formulation 共 160 次正式求解。窗口和 setup 采用管理
实验的代表性中间水平，不复制纯调度部分的完整矩阵。

除总时间、最优数、gap、root bound 和节点数外，还要分开报告内部与外包 pricing 时间、
内部列和外包列数量、RMP 迭代数、Phase-I repair、各类分支次数、列池增长和最终外包率。
可能得到的结论不是预设某个模型必然更好，而是识别：外包率较低、较高或 tariff 起作用时，
哪种建模方式更稳定；外包集合列是否带来更强松弛但更难定价；显式 master 变量是否减少
外包 pricing，却增加 master 结构或分支负担。

### 12.5 外包成本与统一校准规则

主实验使用 `b_j=rho*p_j`，即基础外包报价与任务 processing workload 成比例。模型本身
仍允许异质和一般单调聚合成本；这个比例关系只是为了构造可解释、可控的正式算例。

`rho` 不能逐实例校准。先从不进入正式样本的 pilot 中计算禁止外包最优解的单位 workload
成本 `C_i^NO/sum_j p_ij`，以其中位数确定初始数量级，再测试较宽价格网格。冻结一个全局
中心价格 `rho*` 后，正式价格水平建议使用
`{0.5,0.75,1.0,1.5,2.0}*rho*`。中心档的目标只是让整体样本出现内部生产和外包并存，
不是强迫每个实例达到 50% 外包。若 pilot 两端仍全部外包或全部内部生产，只允许在正式
样本开始前统一外扩倍率。

这套全局价格必须跨 setup、窗口和机器数保持不变。只有如此，才能把不同环境的外包响应
解释为问题结构差异，而不是人为给每类实例重新调价。禁止外包通过关闭外包决策实现，
作为单独配对基准，不用数值无穷大的价格冒充价格曲线上的一个观测点。

### 12.6 实验四：外包价格与生产环境的交互

这是最重要的管理实验。固定一个能稳定求得最优的中等规模，优先使用 `n=50`，并用
setup、due-window 和 machine number 形成 8 类环境：两类 setup、窄/宽窗口、`m=2/3`。
每类使用同一批 5 个源实例，并对每个实例运行 5 个冻结价格水平，共 200 个有限价格求解。
对应的禁止外包解从纯调度实验复用。

setup 的两类需要在正式生成前明确选择。若研究序列依赖强弱，可用相同 setup metric 的
Low/High 缩放，保持矩阵相对结构和三角不等式；若希望更直接对应 Dabia 的 random/clustered
interaction，则应构造均值匹配的 random setup 与 family-clustered setup，使差异来自
结构而不是平均 setup 大小。二者不能混称，主实验只选一种，另一种最多用于代表性稳健性。

每个场景至少报告外包任务比例、外包 workload 比例、总成本、内部 TWET、setup cost、
外包支付、窗内完成比例、早到/迟到任务比例和机器负荷。统计应使用同一源实例上的配对
曲线，比较不同环境下价格响应的水平、斜率和跳变位置，而不是只报所有实例的总体均值。

可能得到的结论包括：产能紧、窗口窄或序列冲突强的环境对外包价格更敏感；产能宽松、
窗口较宽时，价格下降主要降低原本就会发生的外包支付，任务去向变化有限；也可能发现
某个因素的主效应很弱，但与机器数或窗口存在明显 interaction。无论结果如何，都应沿用
Dabia 的解释方式：不写成“参数增大必然导致更多外包”，而是说明哪些生产环境改变了
企业对价格的响应。

### 12.7 实验五：允许外包的价值与内部序列重构

这一部分不必另建一套求解矩阵。对实验四中每个外包解，直接与同源、同 setup、同窗口、
同机器数的禁止外包解配对。除总成本下降外，需要分解外包带来的直接与间接作用：外包
支付增加了多少，内部 TWET 和 setup 成本减少了多少，窗内完成比例是否改善，机器负荷和
内部序列是否更平衡。

为了对应 VRP 中“移除不方便客户后路线更规整”的案例证据，应选择少量代表实例展示甘特图
或机器序列。选择依据必须事先定义，例如总成本改善的中位实例、外包集合变化最大的实例
和几乎不变化的实例，不能只挑最漂亮的图。可进一步比较外包前后保留下来的 setup arcs、
平均 setup、发生变化的相邻关系和拥挤时段任务数。

可能得到的关键结论是：外包价值不只等于外部报价与单个任务内部成本之差，还来自移除
破坏内部顺序的任务后产生的系统重排收益。若这种收益主要出现在窄窗口、高 setup 或少机器
环境，便形成与 Dabia 的 clustered/tight-window 观察相对应的调度结论。若内部序列几乎
不变，则应如实说明外包在这些环境中主要是直接成本替代。

### 12.8 实验六：数量折扣是否真正改变任务去向

固定中等基础价格 `rho*`，比较无折扣与一套中等 incremental discount；强折扣只在 pilot
表明中等折扣几乎不改变方案时再增加。令 `B_all=sum_j b_j`，断点初值为
`0.25B_all` 和 `0.50B_all`。无折扣斜率为 `(1,1,1)`，中等折扣可从
`(1,0.85,0.70)` 开始 pilot；强折扣初值为 `(1,0.70,0.45)`。函数必须连续、非递减，
采用 incremental discount，不使用跨过断点后对以前金额追溯降价的 all-units 口径。

该实验可复用实验四的 8 类生产环境和中价无折扣结果，每类 5 个源实例；若只新增中等
折扣，需要额外 40 次求解。分析重点不是“有折扣时目标一定更低”，而是区分两种机制：
折扣只降低既有外包支付，还是改变了外包任务集合并诱导一组任务共同跨过断点。

因此需要报告外包集合 Jaccard 重合率、新增外包 workload、`B(O)` 到两个断点的距离、
跨越断点的实例数、折扣节省 `B(O)-G(B(O))`、内部序列变化和成本分解。若 family-clustered
setup 或 due-window center 接近的任务更容易被共同外包，可以得到与 Dabia clustered
instances 相似的结论；若随机结构下集合基本不变，则说明折扣主要转移支付，并未给外包商
带来显著新增业务量。

### 12.9 “哪些任务被外包”作为探索性后处理

任务级分析不应预设一个单一规则。现有逐算例输出应支持按 processing time、TWET 权重、
due-window center/width、基础报价、外包前内部 completion 状态和任务相关 setup burden
分组，计算各组外包概率。还可以识别被外包任务是否集中在同一 due-window 时段、同一
family 或共同造成高 setup arcs。

只有某一规律在不同价格和生产环境中稳定，才应上升为管理结论。例如可能发现外包优先
移除的不是 processing time 最大的任务，而是内部 workload 较大、窗口冲突强且移除后能
显著改善相邻 setup 的任务。若特征随价格或环境反转，则更合理的结论是外包选择具有明显
情景依赖性，而不是强行给出普适任务画像。

### 12.10 推荐执行顺序和冻结点

正式运行前应按以下顺序收口。第一，补齐选中源 case 的 `m=3` 和 `n=60` 派生数据，并
完成小规模一致性验证。第二，用独立 pilot 确定四种纯调度方法的共同可计算边界，同时
冻结主面板规模。第三，校准全局 `rho*` 和一套中等折扣，不进入正式样本。第四，先运行
纯调度性能和 formulation 比较；由 formulation 结果选择管理实验的唯一求解方式。最后
运行价格交互、外包价值和折扣实验。

必须冻结并发布的内容包括：源实例编号、任务抽取规则、setup 生成种子、due-window 参数、
时间尺度、`rho*`、价格倍率、折扣断点和斜率、共享初始列 fingerprint、算法配置和时限。
正式求解后不能因为某一方法较慢、外包率不理想或结论不显著而更换实例或重新校准参数。

当前最合理的论文证据结构不是一个巨型全因子，而是六个目的明确的区块：小规模正确性、
纯调度算法性能、两种外包 formulation 性能、价格与生产环境 interaction、允许外包的
结构价值、数量折扣的决策效应。前两组回答算法是否正确和何时高效，后四组回答外包如何
建模以及什么生产环境下外包政策真正改变决策。

按当前每格 5 个源实例估算，核心求解预算如下。这里的数量是 solver run，不是不同源数据
文件数，也不包括前期价格和折扣 pilot：

| 实验区块 | 计算口径 | 预计 runs |
|---|---|---:|
| 小规模正确性 | 30 个子实例 × 5 个模型/定价组合 | 150 |
| 原尺度纯调度 | 30 个基础问题 × 3 个窗口 × 4 种方法 | 360 |
| 时间尺度扩展 | 20 个基础问题 × 2 个新增尺度 × 2 种主方法 | 80 |
| 外包 formulation | 20 个基础问题 × 4 个经济情景 × 2 种 formulation | 160 |
| 价格与环境 | 8 类环境 × 5 个源实例 × 5 个价格 | 200 |
| 中等数量折扣 | 8 类环境 × 5 个源实例；无折扣结果复用 | 40 |
| 合计 | 不含 pilot 和可选 robustness | 990 |

最坏情况下 990 次都跑满 10800 秒并不现实，因此执行时必须分阶段。正确性和边界 pilot
先完成；原尺度纯调度和 formulation 形成结果后，再确认管理实验所用的唯一 formulation
以及哪些规模能稳定闭合。这里的“分阶段”是按预先定义的规则缩减后续矩阵，不能在看到
某个算法输赢后挑选实例。若计算预算不足，优先减少每格源实例数或将可选 SRI/CPLEX 放到
代表子集，不应删除超时困难例或只报告成功结果。

## 13. 按全因子口径重新收紧的四个实验章节

本节记录 2026-08-20 的最新决定，并覆盖本节此前“10 个 pilot + 10 个正式实例”和拆分
多个计算面板的方案。当前口径是：每个任务规模使用 20 个正式实例，不再另设 10 个 pilot；
实验一和实验二均采用统一的完整因子组合，不为了减少运行数而把窗口、setup 或时间尺度拆到
不同样本。论文呈现时可以按研究问题拆表，但底层数据矩阵和求解任务不拆。

### 13.1 正式样本与任务抽取

正式数据仍以 Tanaka 单机 TWET 数据为源，覆盖 `n=20/40/50/60/80/100`。其中
`n=40/50/100` 直接来自对应的 125 个原始源实例，`n=20` 从 40-task 实例派生，
`n=60/80` 从 100-task 实例派生。`n=50` 保留：它是原始规模，不需要任务抽取，而且当前
项目在该规模上有最多的历史求解证据，能够连接 40-task 的相对容易区和 60-task 以后更常见
的长尾区。

每个任务规模选取 20 个正式实例，不再把其中一半划为 pilot。实例不能按文件顺序、求解
时间或最终 gap 选择。对 40、50 和 100 的 125 个源实例计算归一化 due-date 位置与离散度、
processing-time variation、两类 TWET 权重分布和总 workload，再使用固定种子的 k-medoids
选择 20 个代表实例。20-task 与选中的 40-task 源实例一一对应；60/80/100-task 共享选中的
100-task 源实例和嵌套任务集合 `S60 subset S80 subset J100`。所有任务抽取索引、特征、
medoid 距离和固定种子写入 metadata。

派生规模不能简单截取前若干任务。按 processing time、归一化 due date 和两类权重做分层
抽取；保留任务的 `p_j、w'_j、w_j` 不变，原始 due date 按保留 workload 比例修正：

\[
d_j^S=\operatorname{round}\left(d_j\frac{\sum_{i\in S}p_i}{\sum_{i\in J}p_i}\right).
\]

这里不再另建统计意义上的 pilot 样本。正式生成前允许使用少量未入选的历史实例做参数
有效性检查，例如确认两个窗口等级没有退化成相同完成结构；这种检查只用于排除明显无效的
参数，不用于追求某种算法排序或目标外包率，也不能替换 20 个正式实例。

### 13.2 跨机器数的严格配对

`n<=60` 使用 `m=2/3/4`，`n>=80` 使用 `m=3/4/5`。同一源实例在不同 `m` 下必须共用
任务集合、processing time、TWET 权重、due-window center 和任务级 setup 基础矩阵，因而
机器数才可以解释为内部产能变化。

当前 `ETConverter` 不满足这个正式配对口径。第一，它的 setup 随机种子包含 `m`，所以同一
任务集合的 2-machine 和 4-machine 文件会得到不同的随机 setup realization。第二，它使用
`ceil(d_j/m)` 重新计算不同机器数下的 due date；机器增加的同时交付时间也提前，近似维持
单位机器负荷。因此现有不同机器目录适合构造“难度相近的并行机实例”，却不能支持“增加
机器带来更多产能，从而减少外包”的管理解释。

正式生成器应从 `data/40-1、50-1、100-1` 的单机源数据重新生成。对每个任务集合只计算
一次 due-window center：`n<=60` 使用参考机器数 `m_ref=2`，`n>=80` 使用 `m_ref=3`，即
`c_j=ceil(d_j^S/m_ref)`；随后把同一组 `c_j` 复制给该规模的三个机器水平。setup seed 只由
源实例编号、任务集合 fingerprint 和全局 seed 决定，不再包含 `m`。这样跨机器数比较只改变
可用机器数，不同时改变交付目标或 setup 样本。若最终仍选择沿用 `ceil(d_j/m)`，论文中就
必须删除“机器数代表产能松紧”的表述；当前推荐采用固定 center。

### 13.3 Due-window 等级

due window 是无 TWET 惩罚窗口 `[max(0,c_j-h),c_j+h]`，其中 `h` 为半宽。历史参数
`W50/W100/W300` 分别表示 `h=50/100/300`，不是总宽度。现有 Tanaka 数据的平均加工时间
中位数约为 50；实测代表实例中，`W100` 约等于 `1.8--2.7*p_bar`，`W300` 约等于
`5.4--8.1*p_bar`。因此此前的 `h=2*p_bar` 基本对应历史 W100，而 `h=6*p_bar` 基本对应
历史 W300。后者确实可能过宽，使大量任务都能落在无惩罚区间，削弱 due-window 因子的
解释力。

当前先冻结 Wide 为 `h=3*p_bar`。Medium 是否继续用 `2*p_bar`，需要一次很小的参数
有效性检查，因为 `2*p_bar` 与 `3*p_bar` 的距离可能不足以形成两个明显不同的完成结构。
建议在 3--5 个未入选历史实例上同时比较 `h=0、1.5*p_bar、2*p_bar、3*p_bar`，只检查
早到/窗内/迟到比例、TWET 成本占比和窗口内完成率，不比较算法快慢。若 `2` 与 `3` 明显
可区分，则正式水平使用 `0/2/3`；若二者大部分指标接近，则使用间距更均匀的 `0/1.5/3`。
无论结果如何，`6*p_bar` 不再进入正式矩阵，也不根据正式求解结果事后调整窗口。

### 13.4 Setup 与时间尺度

setup time 使用 Low/High 两级。每个任务集合先生成一套有向基础随机矩阵，再执行 Floyd
闭包保证三角不等式；Low/High 共用同一随机数和弧的相对次序，仅通过二分缩放使闭包后的
真实平均比例达到：

| setup 等级 | 闭包后 `avg(s_ij)/p_bar` |
|---|---:|
| Low | 0.25 |
| High | 0.75 |

该定义与现有 `SetupRatioVariantGenerator` 的实际口径一致，避免直接使用闭包前的 eta。
setup cost 不再形成第三个实验因素，固定为 `kappa_ij=20*s_ij`。因此 Low/High 同时表示
setup 占用时间和直接 setup 支出的强弱，符合“同一物理 setup 越长，耗用资源和成本都越高”
的设定。系数 20 沿用当前已经大量测试的成本口径，正式生成时需要额外输出 no-outsourcing
最优解中的 setup cost 占比，用于证明它既不是可忽略项，也没有完全淹没 TWET；但不根据
该占比继续调参。Low/High 只能称为 setup 强度，不能称为 random/clustered。

时间量级完整使用 `alpha=1/10/20`。为了满足“平均放大而非每个任务机械乘同一个固定倍数”
同时又不改变单个实例的任务相对结构，放大倍数按实例而不是按任务抽取。20 个正式实例中：

| 时间量级 | 实例级倍数 `g` |
|---|---|
| 1 | 全部 `g=1` |
| 10 | `[8,9,10,11,12]` 各使用 4 次 |
| 20 | `[16,18,20,22,24]` 各使用 4 次 |

倍数按实例编号做固定置换，并令同一实例的 `g20=2*g10`。processing time、due-window
center、half-width 和 setup time 同乘 `g`；`w'_j、w_j` 与 setup cost 的单位时间系数
保持不变。这样两组平均倍数严格为 10 和 20，单个实例内部的组合结构和算法配对关系不变。

### 13.5 实验一：无外包调度的完整算法比较

实验一关闭外包，比较 compact CPLEX、ng-DSSR BPC、time-indexed no-cut BPC 和
time-indexed rank-1/SRI BPC。四种方法在每个派生实例上使用同一初始调度；三种 BPC 共享
完全相同的初始内部列、incumbent 和 fingerprint，CPLEX 使用对应调度作为 MIP start。
所有求解单线程、时限 10800 秒，超时也保留最终上下界、gap 和完整阶段统计。

按照本次“不拆面板”的决定，六个任务规模、20 个实例、三个机器数、三个窗口、两个 setup、
三个时间尺度和四种方法全部交叉：

\[
6\times20\times3\times3\times2\times3\times4
=25{,}920\text{ solver runs}.
\]

底层是一个完整全因子实验，论文中可分别用规模/机器数表、window/setup 表和时间尺度图展示，
但这些只是结果呈现方式，不再使用不同实例子集。主要指标包括 solved count、时间、最终 gap、
root bound/gap、节点数、列池、LP/pricing/cut 时间、内存、图节点与弧数、ng-DSSR label、
DSSR 轮数和 join 统计。核心分析是：时间数值尺度如何放大 time-indexed 图；window/setup
如何改变 relaxed pseudo-column 与 elementary pricing 的差异；这些影响是否随任务规模和
机器产能发生交互。setup 的效果不能预设为单调，历史结果已经显示更强 setup 既可能强化
序列依赖，也可能直接压制重复绕行。

### 13.6 外包基础报价与默认折扣

实验二的任务级未折扣报价定义为

\[
b_j=\rho p_j,
\]

不再给每个任务额外抽取随机报价。这样报价与外包 workload 有明确关系，避免随机价格掩盖
setup、window 和机器数造成的生产环境差异。`rho` 是最高边际费率下的单位 processing-time
报价，也是整体外包价格水平。

不另设价格 pilot。实验一完成后，使用所有 `alpha=1` 正式场景中最佳已验证无外包可行解
的成本 `z_i^NO`，计算全局单位 workload 成本中位数

\[
u^*=\operatorname{median}_i\left\{\frac{z_i^{NO}}{\sum_jp_{ij}}\right\}.
\]

默认 incremental discount 在全部任务都外包时的平均支付比例为
`0.25+0.85*0.25+0.70*0.50=0.8125`，因此定义
`rho^*=u^*/0.8125`。这个定义使中等价格下“全部外包的折后总支付”与正式样本的典型内部
生产成本处于同一数量级，但不逐实例校准，也不强迫得到 50% 外包率。正式价格只取
`rho in {0.5,1,2}*rho^*`，分别表示外部报价为中心尺度的一半、相同和两倍。`rho^*` 一旦由
上述公式生成即冻结，不能根据外包结果是否均衡再次调整。

令 `P=\sum_jp_j`、`B_all=\sum_jb_j=rho*P`。默认折扣断点定义为
`B_1=0.25B_all`、`B_2=0.50B_all`，等价于累计外包 workload 达到总 workload 的 25% 和
50%。在不同任务规模和价格水平下，该定义保持相同经济含义；若直接用固定货币断点，规模
较大或 `rho` 较高的实例会更容易跨段，形成不必要的混杂。默认连续 incremental tariff 为

\[
G(B)=\min(B,B_1)+0.85\min((B-B_1)^+,B_2-B_1)
      +0.70(B-B_2)^+.
\]

它不是 all-units discount：跨过断点后，只对新增部分使用较低费率，不追溯降低前面部分。
全部任务外包时最大折扣为 18.75%。

### 13.7 实验二：加入外包后的完整性能比较

实验二使用实验一的 `alpha=1` 数据，不再重复时间放大维度；除此之外，任务规模、机器数、
due window 和 setup 全部保留，不能只在一种 Medium/Low 环境下比较外包模型。比较三种方法：
compact CPLEX、使用 ng-DSSR 内部定价的 `columns` 外包集合列模型，以及使用同一 ng-DSSR
内部定价的 `masterVariables` 显式外包模型。两种 BPC 的内部定价固定为 ng-DSSR，不再根据
某个场景临时选择不同 pricing。

每个生产场景使用低/中/高三个基础价格和固定中等折扣，完整求解量为：

\[
6\times20\times3\times3\times2\times3\times3
=19{,}440\text{ solver runs}.
\]

该实验同时回答 formulation 性能和考虑外包后问题是否变难。除了普通 BPC 指标，还需要
报告内部与外包 pricing 时间、内部/外包列数、RMP 迭代、Phase-I repair、分支类型、最终
外包任务率和 workload 比例。与实验一同源 `alpha=1` 结果配对后，可以检验高外包率是否
因为缩小内部排程而更容易，零外包附近是否接近纯调度，以及内外部成本竞争最激烈的中间区
是否反而最难。不能预设“允许外包一定更容易”。

### 13.8 实验三：复用外包结果的管理分析

实验三不新增求解，直接复用实验二中能够得到可信最优解或最小 gap 的结果，并与实验一的
同源无外包解配对。成本层报告总成本、earliness、tardiness、setup 和外包支付；服务层
报告早到、窗内和迟到任务比例；决策层报告外包任务数、外包 workload、机器负荷和 tariff
位置；结构层报告外包前后内部相邻 arcs、平均 setup、机器序列变化和拥挤时段任务数。

分析重点不是分别证明“机器多、窗口宽或外包便宜会怎样”，而是识别交互：同样降低外包
价格时，哪类 `setup × due-window × machine-number` 环境最敏感；允许外包是否只替代直接
成本，还是通过移除 due window 不协调或高 setup burden 的任务，进一步降低内部 TWET/setup
并重构机器序列。任务特征分析保留为探索性后处理，只有跨价格和环境稳定的规律才写成一般
结论。

### 13.9 实验四：有无数量折扣

折扣实验不再覆盖全部任务规模，推荐固定原始且已有充分历史验证的 `n=50`，保留 20 个实例、
`m=2/3/4`、三个窗口和两个 setup，固定中等价格 `rho=rho^*`，使用实验二中表现更稳定的
一个外包 formulation。比较：

1. 无折扣：边际费率 `(1,1,1)`；
2. 有折扣：断点 25%/50%，边际费率 `(1,0.85,0.70)`。

完整对照为

\[
20\times3\times3\times2\times2=720\text{ runs}.
\]

其中 360 个有折扣、中等价格结果已经包含在实验二，因此只新增 360 个无折扣求解。当前
不增加强折扣、改变段数或移动断点。分析先报告取消折扣后的目标增加，但重点是外包集合
Jaccard、外包 workload、跨断点实例数、折扣节省和内部序列变化，以区分“折扣只降低既有
外包支付”和“折扣诱导一组任务共同外包”两种机制。

| 实验三：结果复用 | 0 |
| 实验四：新增无折扣对照 | 360 |
| 合计 | 45,720 |

这是“不拆实验矩阵”和“每规模 20 个正式实例”的直接计算后果。四线程下，若平均每次求解
5 分钟，仅 solver wall time 约需 39.7 天；平均 15 分钟约需 119 天；若大量大实例跑满
10800 秒，完整矩阵在现实上不可完成。该事实不改变当前设计，但正式生成器和调度器必须支持
按同一预注册矩阵分批运行、断点续跑和完整保留 timeout，不能在看到结果后删除困难组合。
论文结果可以分表，实验定义仍保持一个全因子总体。

当前只剩 due-window 的 Medium 水平尚未最终冻结：Wide 已从 `6*p_bar` 改为 `3*p_bar`，
Medium 在 `1.5*p_bar` 与 `2*p_bar` 中通过小规模参数有效性检查选择。20 个正式实例、跨 `m`
固定 center/setup、setup R25/R75、setup cost 系数 20、时间尺度 1/10/20、外包价格归一化
公式、三档价格以及 25%/50% incremental discount 断点均按本节记录。

## 14. 机器数、窗口、setup、外包报价与计算预算的再次修订

本节记录 2026-08-20 的后续讨论，并覆盖第 13 节中与本节冲突的参数。主要变化是：跨机器
数使用中间机器数确定共同 due-window center；窗口恢复为已有大量历史结果的 `W0/W100/W300`；
setup 因子从强度 Low/High 改为均值匹配的 random/family 两种结构；删除复杂的无外包成本
中位数归一化；折扣断点从 25%/50% 下调；不再执行 45,720 次完整全因子求解。

### 14.1 同一任务集合跨机器数如何配对

同一任务集合在不同 `m` 下共用 `p_j`、TWET 权重、due-window center、release time、setup
time 和 setup cost，只改变机器数量。参考机器数不再取最小档，而取三个机器水平的中间档：

| 任务规模 | 机器数 | 共同 center 的参考机器数 |
|---|---|---:|
| `n<=60` | `2/3/4` | `m_ref=3` |
| `n>=80` | `3/4/5` | `m_ref=4` |

对派生后的任务集合先计算一次 `c_j=ceil(d_j^S/m_ref)`，再复制给三个 `m`。这样低于参考
档表示产能偏紧，参考档表示基准，高于参考档表示产能偏松。若沿用第 13 节的最小参考机器数，
其余两档都只会向宽松方向变化，难以形成对称、可解释的产能比较。

正式生成顺序应为：读取单机源数据并确定嵌套任务集合；计算一次 workload 修正后的 due date；
按中间 `m_ref` 计算一次 center；生成一次 setup realization；最后只替换 `m` 写出三个实例。
setup seed 不包含 `m`。同一派生实例上的四种算法共享初始调度和列快照；不同 `m` 的初始
调度不要求相同，因为可用机器数已经变化，但任务属性和 setup 必须相同。

### 14.2 Due-window 与时间放大

正式窗口半宽采用 `W=0/100/300`。这里 `W` 是无惩罚窗口
`[max(0,c_j-W),c_j+W]` 的半宽，不是总宽度。`W100` 在现有 Tanaka 派生数据上大约为
`2*p_bar`，`W300` 大约为 `6*p_bar`。虽然 W300 会使更多任务可以无惩罚完成，但已有大量
历史实验表明它并未普遍退化为零 TWET，而是会显著扩大 relaxed pricing 空间并产生有代表性
的算法差异。相比 W250，W300 有更多可复用历史结果，且与 W100 的间距更清楚，因此保留
W300，不另设 W250。

时间量级实验要保持相对窗口紧度不变。若实例级时间倍数为 `g`，则 `p_j`、center、setup
time 和 `W` 同乘 `g`。因此基础 W0/W100/W300 在平均 10 倍和 20 倍时间量级中分别对应
W0/W1000/W3000 和 W0/W2000/W6000。不能只放大 processing/due date 而保留绝对 W100，
否则实验同时改变了时间数值尺度和窗口紧度。

### 14.3 Random 与 family setup

setup 的正式因素是结构，不再是 R25/R75 两个平均强度。两类 setup 应具有相同的闭包后
平均强度，建议统一冻结为

\[
\operatorname{avg}_{i\ne j}(s_{ij})/\bar p=0.25.
\]

Random setup 从同一有界范围独立生成有向弧，再做 Floyd 闭包并整体缩放到上述目标均值。
Family setup 将任务随机、均衡地分成约 10 个任务一组，即
`F=max(2,round(n/10))` 个 family；family 分配使用固定 seed，且不按 processing、due date
或权重排序，避免把 setup 结构与交付属性预先绑定。类内原始 setup 较小，类间较大，推荐
初始比例约为 1:3，并加入少量固定随机扰动；随后同样执行 Floyd 闭包和整体缩放。生成后
必须输出闭包后的全局均值、类内均值、类间均值及二者比例，确认 family 特征没有被最短路
闭包抹平。

两类 setup 的全局均值必须一致。否则 random/family 的比较会同时混入 setup 大小和结构，
无法对应 VRP 文献中的 random/clustered interaction。setup time 不宜过大，`0.25*p_bar`
与现有实例的实际量级相近，也比原计划的 R75 更稳妥。

setup cost 仍与 setup time 成比例，但系数 20 暂不继续作为无解释常数冻结。一个更自然的
固定口径是

\[
\kappa_{ij}=\gamma s_{ij},\qquad
\gamma=\operatorname{median}_j\max\{w_j^E,w_j^T\}.
\]

对当前 40/50/100-task Tanaka 源数据的 23,750 个任务，右侧中位数为 8、均值约为 7.137，
因此可直接冻结 `gamma=8`。这使一个单位 setup time 的直接成本与典型任务较重一侧的 TWET
斜率处于同一量级，不再额外引入 setup-cost 灵敏度因素。正式冻结前只需检查其成本占比，
不按算法快慢调整。

### 14.4 外包基础报价

用户提出的核心思路是让外包报价随任务的早到/迟到惩罚斜率变化，而不是通过无外包解再次
反推全局 `rho*`。直接使用 `max(w_j^E,w_j^T)` 在数学上可行，但它的单位是成本/时间，且
时间整体放大时外包报价不会同步变化。为保留这一排序逻辑并保持量纲和时间尺度一致，建议
采用

\[
b_j(\lambda)=\lambda\,\bar p\,\max\{w_j^E,w_j^T\},
\]

其中 `p_bar` 是该派生任务集合的共同平均 processing time，`lambda` 为无量纲价格系数。
因为 `p_bar` 对同一实例中的所有任务相同，任务之间的外包报价排序仍完全由最大 TWET 斜率
决定，没有重新引入任务级 processing 长度。若希望长任务本身更贵，可把 `p_bar` 换成
`p_j`，但那是另一种报价机制，不应与主实验混用。

正式价格水平可先冻结为 `lambda=0.5/1/2`。它们是明确的低、中、高三档，不再要求中档
产生某个指定外包率，也不逐实例校准。无外包相当于报价无穷大，直接复用实验一结果。

### 14.5 VRP 论文的折扣设置与本问题的断点

Dabia、Lai 和 Vigo 的正式 tariff 使用总外包需求量的固定绝对断点
`0--200/200--400/400--600/>=600`，不是总需求的 25%/50%。R 实例四段单位费率为
`5/4.5/4/3.5`，RC 为 `3.5/3/2.5/2`，C 为 `2/1.5/1/0.5`。无折扣对照则在全部外包量
上使用各类最高费率 `5/3.5/2`。该论文同时求解 25、50、100-customer 实例，所以固定绝对
断点在不同规模下对应的总需求比例并不相同；它适合其既定 tariff sheet，但不适合直接复制
到本项目跨 `n=20--100` 的统一实验中。

本问题继续使用相对断点，但把第一、第二断点改为

\[
B_1=0.10B_{all},\qquad B_2=0.25B_{all},\qquad
B_{all}=\sum_j b_j(\lambda).
\]

边际费率保持 `(1,0.85,0.70)`。第一段在外包约 10% 的基准报价总量后结束，能让中等外包
方案实际接触折扣；第三段从 25% 后开始，保留“大批量外包才获得较低费率”的含义。全部
任务外包时平均支付比例为 `0.10+0.85*0.15+0.70*0.75=0.7525`，最大折扣 24.75%。
断点按 `B_all` 缩放后，改变 `lambda` 不会改变某个外包集合位于哪一段；若以固定货币值或
固定任务数设断点，规模、任务权重和价格水平都会混入折扣机制。

该 10%/25% 口径当前是推荐值，不宣称来自 Dabia 等人的比例换算。正式结果应直接报告
`B(O)/B_all`、跨过 B1/B2 的实例比例和各段使用量；若绝大多数中价实例连 B1 都不到，数量
折扣实验本身就没有识别力，此时应在正式运行前按预注册规则整体下调，而不能看完算法结果
后逐实例调整。

### 14.6 避免完整全因子爆炸的平衡设计

第 13 节的 45,720 次求解在 10,800 秒时限下不可执行。这里把“每个规模 20 个算例”解释为
20 个正式环境实例，而不是每个因子单元再放 20 个实例。对每个 `n`，把 20 个代表源实例
按固定方案分配到六个 `W x setup` 单元，单元频数为 `4/4/3/3/3/3`，并在不同 `n` 间轮换
哪两个单元获得第 4 个实例。每个环境实例仍完整运行三个机器数和待比较算法，因此算法和
机器数比较保持严格配对；W/setup 主效应依靠跨 20 个代表源实例的平衡分配识别。

当前推荐的可执行矩阵为：

| 章节 | 设计 | runs |
|---|---|---:|
| 无外包原尺度 | 6 个 n x 20 环境实例 x 3 个 m x 4 种算法 | 1,440 |
| 时间尺度 | n=40/50，各 20 个环境实例；10 个取 x10、10 个取 x20；3 个 m；ng-DSSR 与 no-cut | 240 |
| 外包 formulation/价格 | n=40/50/60 x 20 环境实例 x 3 个 m x 3 个价格 x 3 种方法 | 1,620 |
| 数量折扣 | n=50 x 20 环境实例 x 3 个 m x 有/无折扣；中价、最佳 formulation | 120 |

数量折扣表中的 60 个有折扣结果已包含在外包性能实验中，因此新增求解为 60 次。按去重后
计算，当前总量约为 3,360 次，而不是 45,720 次。它仍然较大，但每个任务规模保留 20 个
正式实例，所有算法在同一环境上配对，并且 W、setup、机器数、价格和时间尺度均实际进入
实验。与完整全因子相比，代价是 W/setup 不再对同一源实例做全部六种重复测量；论文统计
应使用分层汇总或回归控制 `n`、`m` 和源实例特征，不能把每个单元的 3--4 个实例当成单独
的小样本做过强结论。

当前主要推荐由此为：机器数严格配对，W0/W100/W300，均值匹配的 random/family setup，
`gamma=8` 的 setup cost，按最大 TWET 斜率生成基础外包报价，10%/25% incremental discount，
以及约 3,360 次的平衡不完全因子求解矩阵。最终生成代码应等这些参数确认后再改，避免现有
`formal-v1` 在参数反复变化期间继续膨胀。

## 15. Due date、family setup 与固定绝对折扣断点的最终方向

本节继续覆盖第 14 节中冲突的建议。当前已经确认：中间机器档作为参考；W100/W300 使用
固定绝对半宽；family 数量限制在 3--6；setup-cost 系数恢复为 20；折扣政策采用跨规模固定
的绝对断点，而不是每个实例分别按 `B_all` 缩放。

### 15.1 “使用原 due date”指什么

Tanaka 单机文件中的原始 due date 不能不经转换直接作为 2/3/4 台并行机的 center。以
50-task 数据为例，原始 due date 与单机总 workload 同量级，直接复制到三台机器后会使交期
相对于并行机负荷整体过晚。正确口径是保留原 due date 的相对结构，但只按参考机器数转换
一次：

\[
c_j=\operatorname{round}(d_j^S/m_{ref}),
\]

其中 `d_j^S` 是任务抽取后按保留 workload 修正的原始 due date。没有任务抽取的 40/50/100
规模直接使用源文件 `d_j`。`n<=60` 取 `m_ref=3`，`n>=80` 取 `m_ref=4`；所得 `c_j` 再原样
复制到三个机器水平。因此“原来的 due date”是 center 的数据来源，不是未经并行机转换的
最终数值。

### 15.2 W100/W300 不再随机扰动

正式窗口采用任务间相同的固定半宽 `W=0/100/300`。即同一 W 场景下每个任务使用
`[max(0,c_j-W),c_j+W]`，不再从 `U(80,120)` 或 `U(250,350)` 单独抽取任务级窗口。
固定 W 的优点是窗口因素只有一个清楚的控制量，并能直接复用现有 W100/W300 历史结果；
任务级随机扰动会额外引入窗口异质性，使算法差异难以归因。时间尺度为 `g` 时仍同步使用
`gW`，保持相对窗口紧度。

### 15.3 Family 数量和 setup 强度

family 数量不再按每 10 个任务一个 family，而在 3--6 间随规模缓慢增加：

| n | 20 | 40 | 50 | 60 | 80 | 100 |
|---|---:|---:|---:|---:|---:|---:|
| family 数 | 3 | 3 | 4 | 4 | 5 | 6 |

每个任务集合采用固定 seed 做均衡随机分组。类内原始 setup 小、类间原始 setup 大，random
setup 则不使用 family 信息。两类 setup 仍要求闭包后的全局平均 setup 相同；这个要求不是
为了声称调度问题会复现 VRP 的 clustered 结论，而是为了让比较只反映结构。若 family 的
全局平均 setup 更大，最终观察到的差异无法区分来自 family 结构还是 setup 总量。

`avg(s_ij)/p_bar=0.25` 也不是理论常数，而是规模无关的强度控制。它表示一次典型 setup 约
为平均 processing time 的四分之一，接近当前派生实例和历史 R25 数据的量级，并明确保持
processing 为主要时间消耗。与 VRP 不同，调度中的 processing 通常明显大于 setup，因此
不应预设 family setup 会像地理 clustering 一样产生强烈的成组外包效应。这里更合理的研究
问题是：在 setup 只占次要比例时，family 结构是否仍会改变内部序列和折扣诱导的外包集合；
若效应较弱，本身也是可报告结论。

setup cost 按本轮决定恢复为

\[
\kappa_{ij}=20s_{ij}.
\]

原因是 setup time 本身较小，若系数只取典型 TWET 斜率 8，直接 setup cost 很可能过弱。
两类 setup 共用该系数，不再把 20 作为灵敏度因素。正式数据需报告 setup time 占总加工时间
比例和 setup cost 占目标值比例，确认它没有完全淹没或消失。

### 15.4 外包价格水平

基础报价继续使用共同时间尺度乘最大 TWET 斜率：

\[
q_j=\bar p\max\{w_j^E,w_j^T\},\qquad b_j(\lambda)=\lambda q_j.
\]

`q_j` 称为任务的标准报价量，`lambda` 是外包价格水平。考虑计算预算，正式主矩阵先采用
三个价格 `lambda=0.5/1/2`；若前三档结果显示 1 与 2 之间发生主要转折，再只对最佳外包
formulation 补 `lambda=1.5`，而不是让所有模型增加第四档。这样既能得到 3--4 个价格点，
又不把 formulation 性能实验无条件扩大 1/3。

### 15.5 Dabia 等人的绝对断点相当于多少比例

Dabia、Lai 和 Vigo 使用 Solomon 前 25、50、100 个客户，统一采用绝对需求断点
200/400/600。按公开 Solomon 数据重新汇总，各类别总需求及断点占比如下：

| 类别 | 客户数 | 总需求 | 200 占比 | 400 占比 | 600 占比 |
|---|---:|---:|---:|---:|---:|
| R | 25 | 332 | 60.2% | 120.5% | 180.7% |
| RC | 25 | 540 | 37.0% | 74.1% | 111.1% |
| C | 25 | 460 | 43.5% | 87.0% | 130.4% |
| R | 50 | 721 | 27.7% | 55.5% | 83.2% |
| RC | 50 | 970 | 20.6% | 41.2% | 61.9% |
| C | 50 | 860 | 23.3% | 46.5% | 69.8% |
| R | 100 | 1458 | 13.7% | 27.4% | 41.2% |
| RC | 100 | 1724 | 11.6% | 23.2% | 34.8% |
| C | 100 | 1810 | 11.0% | 22.1% | 33.1% |

因此该论文没有让每个规模“同样容易获得折扣”。25-customer 实例的第一断点已经相当于
37%--60% 总需求，部分后续段根本不可达到；100-customer 实例的第一断点只相当于约
11%--14%，第三断点也仅约 33%--41%。这种规模效应来自统一的真实 tariff，而不是实验
校准误差。

本问题应采用相同思想，但不直接复制货币数值 200/400。当前模型的 tariff 自变量是标准
报价量之和 `Q(O)=sum_{j in O}q_j`，因此先在全部正式 50-task 源实例上计算

\[
Q_{50}^{ref}=\operatorname{median}_{i:n_i=50}\sum_jq_{ij},
\]

再固定绝对断点

\[
Q_1=0.25Q_{50}^{ref},\qquad Q_2=0.50Q_{50}^{ref}.
\]

这两个数一旦由正式数据生成即对所有 `n`、`m`、W、setup 和价格水平固定，不再随单个
实例的 `B_all` 改变。25%/50% 只用于把绝对断点锚定到 50-task 参考规模，恰好接近 Dabia
等人在 50-customer 实例中的前两段比例；在小规模上折扣更难达到，在大规模上更容易达到，
这正是统一 tariff 应有的规模效应。三个边际费率仍为 `(1,0.85,0.70)`。

为使改变 `lambda` 只改变价格而不改变同一外包集合的数量档位，模型中的货币域断点应写为
`B_1(lambda)=lambda Q_1`、`B_2(lambda)=lambda Q_2`。这样 tariff 档位由固定标准报价量
`Q(O)` 决定，价格档只同比放大支付金额。若直接固定货币 B1/B2 而同时改变 `lambda`，同一
任务集合会仅因单位价格上涨而更容易获得数量折扣，混淆价格效应和数量效应。

该固定绝对断点方案比第 14 节的逐实例 10%/25% 更接近参考论文，也更符合统一承运商政策。
正式生成器只需在所有 50-task 正式任务集合确定后计算一次 `Q50_ref` 并写入 suite metadata，
不需要求解 pilot，也不根据实际外包率调整。

## 16. Setup 生成细节、惩罚权重分析与 Q50 断点解释

### 16.1 为什么匹配平均 setup，以及具体怎样生成

random/family 两类 setup 保持相同的闭包后平均值，是实验控制要求，不是对实际工厂的强制
假设。本文要比较的是任务之间是否存在 family 结构；若 family 数据同时具有更大的 setup
总量，算法难度、内部成本和外包集合的变化无法归因。`avg(s_ij)/p_bar=0.25` 的作用只是把
setup 固定在相对 processing 较小但不可忽略的量级，并使不同任务规模和时间尺度可比较。

正式生成建议按以下顺序进行。random setup 对每条有向任务弧从约
`[0.10*p_bar,0.40*p_bar]` 的范围生成原始值。family setup 使用第 15.3 节的 3--6 个均衡
family，类内原始值约为 `[0.05*p_bar,0.15*p_bar]`，类间原始值约为
`[0.25*p_bar,0.45*p_bar]`。两类数据分别执行 Floyd 闭包保证三角不等式，再用现有比例校准
逻辑把闭包后的全局均值缩放到 `0.25*p_bar`；整数化后重新闭包并复核均值。random/family
使用独立但固定的 seed，同一任务集合跨 m 复用完全相同的矩阵。

这些原始区间只控制结构，最终正式口径以闭包后统计为准。每个实例输出全局平均 setup、
类内平均、类间平均、类间/类内比例以及 setup/workload 比例。若 Floyd 闭包把 family 对比
明显压平，应调整原始类内/类间区间，而不是提高最终全局平均 setup。setup cost 固定为
`20*s_ij`。

调度和 VRP 的结构作用不应强行类比。VRP 的相邻客户行驶成本通常是路线成本主体之一，而
本文 setup 明确小于 processing。family setup 在这里是“次要序列依赖是否仍影响外包和内部
排程”的结构实验；若最终效应弱于 VRP clustered instances，这是合理结果，不应通过放大
setup 强行制造相同结论。

### 16.2 当前报价不能直接推出高权重任务一定被外包

基准外包报价量定义为

\[
q_j=\bar p\max\{w_j^E,w_j^T\}.
\]

较高 TWET 权重一方面提高任务在内部发生早到或迟到时的成本，增加外包动机；另一方面也
提高 `q_j`，使该任务的外包报价更高，抑制外包。因此不能在求解前直接写成“平均早到/延误
权重越高就越容易外包”。真正决定外包的是可避免的内部 TWET/setup burden 与外包支付之间
的相对关系，并受机器数、窗口和其他任务序列影响。

现有正式结果仍可做任务级后处理，比较被外包与内部任务的最大 TWET 权重、processing、
due-window 冲突和 setup burden，但这只是结构分析。若要单独识别惩罚权重的因果影响，建议
增加一个真正的灵敏度实验：固定 `n=50、m=3、W100`、最佳外包 formulation、默认价格和
折扣，对内部 `w_j^E,w_j^T` 同比乘 `theta=0.5/1/2`，同时冻结由原始权重生成的 `q_j`、
Q1/Q2 和 setup。这样 theta 只改变内部违约代价，不同步抬高外包报价。random/family setup
均保留时，20 个源实例共 120 次求解；若计算预算紧，可只使用一种 setup，降为 60 次。

### 16.3 Q50 参考断点的直观含义

对每个正式 50-task 任务集合，先计算“如果所有任务都按基准报价量计入外包”的总量：

\[
Q_i^{all}=\sum_{j=1}^{50}q_{ij}.
\]

20 个正式 50-task 实例会得到 20 个 `Q_i_all`。将其排序并取中位数，得到唯一的
`Q50_ref`。例如若这些总量的中位数为 18,000，则固定

\[
Q_1=4,500,\qquad Q_2=9,000.
\]

此后 20-task、40-task、50-task、60-task、80-task 和 100-task 实例全部使用同一个
4,500/9,000，绝不再按各自总量重算。于是小规模可能连 Q1 都难以达到，大规模更容易进入
第三段，和 Dabia 等人的固定 200/400/600 具有相同逻辑。25%/50% 只用于一次性确定参考
绝对数值，不是每个实例的相对断点。

为了避免价格水平改变折扣档位，概念上应把标准报价量和货币支付分开。令

\[
B(O)=\sum_{j\in O}q_j,
\]

则价格水平 lambda 下的支付函数为

\[
G_{\lambda}(B)=\lambda\left[
\min(B,Q_1)+0.85\min((B-Q_1)^+,Q_2-Q_1)+0.70(B-Q_2)^+
\right].
\]

因此 Q1/Q2 是承运商固定的标准报价量断点，lambda 只同比改变支付金额。当前代码若仍以
`b_j=lambda*q_j` 作为 tariff 自变量，可以等价地把模型域断点写成 `lambda*Q1` 和
`lambda*Q2`；论文表述优先使用上式，逻辑更清楚。

## 17. Setup 强度、外包模型比较范围与剩余参数

本节记录 2026-08-20 的最新决定，并覆盖第 14--16 节中关于平均 setup 强度的旧建议。

### 17.1 `On the exact` 的 setup 数据口径与本文的 0.5 选择

Bulhoes 等人的 *On the exact solution of a large class of parallel machine scheduling*
没有在正文中重新给出 setup 的随机分布，只把 Kramer 数据分成 small setup（S）和 large
setup（L）。继续追溯 Kramer（2015）第 4.7 节可知，其在 Sen and Bulbul 数据上增加 setup
时采用了 Cicirello and Smith 的生成方法。令 `p_bar` 为平均 processing time，
`s_bar=eta*p_bar`，setup 从限制在 `[0,2*s_bar]` 内的正态分布随机生成；两档参数为
`eta=0.25` 和 `eta=0.75`。因此参考数据的 S/L 是 0.25/0.75 两档，不是 0.5。

本文不再把 setup 强度作为第三个实验因素。按本轮决定，random/family 两种结构统一使用中间
强度：

\[
\operatorname{avg}_{i\ne j}(s_{ij})/\bar p=0.5.
\]

这里的 0.5 是在文献两档之间选取的固定中等强度，用于避免把“结构差异”和“强度差异”混在
一起，不能写成直接复现文献的一个参数水平。正式生成以 Floyd 闭包和整数化后的实际均值为
准；两类 setup 必须达到相同均值。setup cost 继续固定为
`kappa_ij=20*s_ij`，不再另做系数灵敏度。

random setup 可直接沿用 Kramer 的截断正态思路，并把目标均值设为 `0.5*p_bar`。family
setup 仍需先规定类内/类间的原始分布，再闭包并统一校准到同一全局均值。原始分布的具体比例
尚未冻结；正式口径应同时约束闭包后的类间/类内均值比，避免 Floyd 闭包把 family 结构抹平。

### 17.2 Dabia 等人在哪些算例上比较 SP1 和 SP2

Dabia、Lai 和 Vigo 的完整测试集包含 25、50、100 customers，每个规模 168 个实例，共
504 个实例。但 Section 7.1 的 formulation comparison 只使用了**全部 168 个
25-customer 实例**，并没有在 50/100-customer 实例上继续同时比较 SP1 和 SP2。两种
formulation 均启用 cuts 和 strong dominance。Table 6 报告：SP1/SP2 的平均时间分别为
158/50 秒，求得最优的实例数为 124/131，平均 root lower bound 为 676/673，平均树节点数
为 4.2/6.5。SP2 的根界略弱、树略大，但总体明显更快，因此后续 25/50/100-customer 的
cuts、dominance 和总体性能实验均以 SP2 为主。

这个口径说明，两种外包 formulation 没有必要在本文全部任务规模上重复比较。更合理的做法
是使用一组具有代表性的中等规模实例确定更有效的 formulation，随后在更大规模和管理分析中
只保留胜出的 formulation。本文是否采用 `n=40/50` 两档，还是只采用一档，仍需结合总运行
预算最终冻结；不建议继续把 `n=40/50/60` 全部纳入 formulation comparison。

### 17.4 当时仍未确定的参数（已由第 17.14 节覆盖）

1. **20 个源算例如何选择，以及 20/60/80-task 如何抽取。** 不能简单取编号前 20 个。
   需要在“使用 100-task 实例的固定随机排列并取嵌套前缀”和“原生 40/50/100 加上只对缺失
   规模做抽取”之间二选一。前者规模比较更严格配对，但需要按保留 workload 修正 due date；
   后者更接近原始 benchmark，但不同规模不再来自同一任务母集。当前推荐前者，但尚未确认。

2. **20 个源算例与六个 `W x setup` 环境的关系。** 仍需决定每个源算例是否跑满六种环境，
   还是采用 `4/4/3/3/3/3` 的平衡不完全分配。前者证据最强但运行量扩大六倍；后者满足
   “每规模 20 个正式环境”的预算，但 W/setup 与源实例不能做完全配对。这是当前最重要的
   实验规模决定。

3. **平均 10 倍和 20 倍的具体实例级倍数。** 现有建议是 10 倍组使用
   `[8,9,10,11,12]`、20 倍组使用 `[16,18,20,22,24]`，各值重复四次，并令同一实例的
   两档倍数对应。这个方案满足平均值准确且不是机械统一缩放，但尚未得到最终确认。

4. **setup 的最终生成规则。** 实例级强度建议使用 `[0.25,0.75]`，但类内均值倍率、闭包后
   family 对比阈值，以及是否采用第 17.7 节的“配对平均校准”仍需最终确认。已经不再推荐把
   random/family 分别缩放到完全相同的闭包后均值。

5. **外包价格是三档还是四档。** 当前最简主矩阵为 `lambda=0.5/1/2`。若加入 1.5，会增加
   约三分之一的外包性能求解量，但只提高价格响应曲线的分辨率。当前推荐正式 formulation
   comparison 保留三档；需要更平滑的管理曲线时，只对胜出 formulation 补 `lambda=1.5`。

6. **时间尺度实验包含哪些算法。** 核心问题是 ng-DSSR 与 time-indexed no-cut 对时间数值
   尺度的敏感性，因此这两种必须保留。compact CPLEX 和 rank-1/SRI 是否进入 10/20 倍区块
   尚未冻结；当前建议把它们限制在原尺度主表，时间尺度区块只比较前两种，避免把 SRI cut
   生命周期和 MIP horizon 的额外机制混进核心结论。

除上述六项外，窗口、机器数、setup cost、基础报价公式、固定绝对折扣
断点、折扣斜率、时限和单线程口径均已经确定，不应继续反复调整。

### 17.5 为什么两类 setup 使用相同的 0.5，以及 Dabia 大规模实例的用途

random/family 使用相同平均 setup 有一个明确的实验控制目的：本文希望识别的是 setup 是否
具有 family 结构，而不是 setup 总量大小。如果 family setup 的平均值也更大，那么求解时间、
内部 setup cost、TWET 和外包集合的变化都可能只是由“setup 更长”造成，无法归因于 family
结构。因此两类数据必须在 Floyd 闭包和整数化后具有相同全局均值，只允许类内/类间分布不同。

均值选择 `0.5*p_bar` 则是强度选择。Kramer 数据的 small/large 两档为 0.25/0.75，0.5 是
二者的中点。它避免再增加 Low/High setup 因子，同时使 setup 明显影响序列但不必采用最强的
0.75 档。需要注意，0.5 并不是很弱的 setup：一条较长机器序列的 setup 总时间可能约为
processing 总时间的一半。因此正式数据必须报告 `sum setup/sum processing` 和 setup cost
占比，确认该强度没有淹没 TWET。若该比例不符合论文希望描述的生产环境，应在正式生成前
整体修改，不能在看过正式算法结果后再调参。

Dabia 等人的 50/100-customer 实例没有用于 SP1/SP2 选择，而用于三件事。第一，使用已经
选定的 SP2 比较有 cuts 和无 cuts 的最终算法，Table 7 在 25/50/100 customers 上分别求得
131/92/49 个最优解，有 cuts 的合计为 272/504。第二，检验最终算法随规模增长的求解能力，
并报告时间、root bound 和搜索树。第三，在管理分析中提供更大实例的代表性结构案例，例如
RC105 的 100-customer 折扣对照，以及 RC107、C105 的 50-customer 折扣对照。允许/禁止
外包的主要路线图则仍使用 R109、R111 的 25-customer 实例。

因此参考论文的实验层次是：小规模全样本负责 formulation selection；全部规模负责最终算法
评价；少量具有代表性的 25/50/100-customer 最优解负责解释管理机制。这是理解其结果的依据，
但本文是否沿用该范围仍由自身实验目的决定；下一节记录了“两种 formulation 覆盖全部正式
规模”的最新决定。

### 17.6 Setup 强度改为实例级范围，以及外包 formulation 覆盖全部规模

上一节把所有实例的平均 setup 固定为 `0.5*p_bar`，容易被误解为实例之间没有 setup 强度
变化。当前更合适的口径是让不同源实例具有不同的 setup severity：

\[
\eta_i\in[0.25,0.75],\qquad
\operatorname{avg}_{u\ne v}(s_{uv}^{i})=\eta_i\bar p_i.
\]

20 个源实例的 `eta_i` 使用 `[0.25,0.75]` 上的等距分层值，整体均值严格为 0.5，再按固定
seed 打乱后分配给源实例。不能对 20 个实例各自独立随机抽样，否则一次随机 realization 可能
使整体均值偏向一侧。相同源实例在所有 `n/m/W/time-scale` 配对中沿用同一 `eta_i`；该实例
的 random 和 family setup 也使用相同的闭包后目标均值。这样既允许某些实例显著低于 0.5、
某些实例显著高于 0.5，又能把同一实例两类 setup 的差异归因于结构。

具体生成时，random setup 可以按 Kramer 的思路，以 `eta_i*p_bar` 为中心，在
`[0,2*eta_i*p_bar]` 内生成截断正态随机数。family setup 使用同一 `eta_i`，但类内分布较小、
类间分布较大。两套矩阵分别执行 Floyd 闭包，再通过整体比例和整数化复核达到相同的
`eta_i*p_bar`。因此“平均匹配”不是说每条 setup 都相等，而是说同一源实例的两种结构具有
相同总强度；单条弧仍然可以远大于或远小于 0.5。

Dabia 等人的 R/C/RC 实例没有做这种均值匹配。它们沿用 Solomon 的 random/clustered/mixed
空间分布，类别之间的距离结构、固定成本和承运费率本来就不同。其 Section 7.4 主要通过代表
性最优路线解释 interaction，不是控制其他因素后的因果比较。因此该做法可以支持探索性管理
观察，但不能直接证明“聚类结构本身”导致差异。本文若希望比较 random/family setup 的结构
作用，配对均值仍然更严谨。

外包 formulation 的规模范围按本轮决定不再参考 Dabia 的小规模筛选做法。compact CPLEX、
columns formulation 和 masterVariables formulation 在全部正式任务规模上均运行，以直接
观察两种外包处理随 `n` 增长的相对表现。后续额外的价格曲线、折扣和管理分析不再重复两种
formulation，只使用完整性能实验中总体更稳定的一种，避免同一结论重复扩增求解量。

### 17.7 不强制最终均值相等的 setup 生成方案

Dabia 等人的 random/clustered/mixed 实例没有匹配平均旅行距离、固定成本或承运费率。该文
Section 7.4 明确是根据少量最优路线图提出解释性观察，因此这种设计本身并非错误；它回答的
是“不同实例类别表现如何”，而不是“只改变空间聚类、其他因素不变时会怎样”。如果本文也只
使用“可能来自 family 结构”的谨慎表述，确实没有必要强制 random/family 的最终平均 setup
完全相等。

但完全独立生成两类 setup 会留下一个很直接的替代解释：family 实例外包更多，可能只是它
平均 setup 更大。当前推荐采用介于完全独立和完全均值匹配之间的配对方案。

对第 `i` 个源实例先给定共同 severity：

\[
\eta_i\in[0.25,0.75],\qquad \mu_i=\eta_i\bar p_i.
\]

20 个 `eta_i` 使用等距分层值并按固定 seed 打乱，整体均值为 0.5。random 和 family 使用
相同的 `eta_i`、相同的标准正态随机数和相同的初始 setup 随机数，但按不同结构生成 job-to-job
setup。random 弧采用现有 Kramer 口径：

\[
s_{uv}^{R}\sim TN(\mu_i,(\mu_i/2)^2;0,2\mu_i).
\]

family setup 设 `q_i` 为有序类内任务对占全部有序任务对的比例。给定类内均值倍率 `a<1`，
定义

\[
\mu_i^{in}=a\mu_i,
\qquad
\mu_i^{out}=\frac{\mu_i-q_i\mu_i^{in}}{1-q_i}.
\]

这样 family setup 在生成前的期望总体均值仍为 `mu_i`，但类内较小、类间较大。每条弧仍从
对应均值的截断正态分布生成，因此不是固定值。`a` 建议先在 0.4/0.5 中选择一个；选择标准
只看 Floyd 闭包后类间/类内均值比是否仍足够清楚，不看任何算法求解时间或目标值。

两套矩阵随后分别执行当前完整有向 Floyd 闭包。由于闭包会以不同方式改变 random/family，
不再分别缩放到完全相同的最终均值。为避免任务规模越大、可用中转越多时整体 setup 被系统性
压低，可以只使用一个共同的前置尺度系数，使两者闭包后均值的算术平均接近目标：

\[
\frac{\bar s_i^R+\bar s_i^F}{2}=\eta_i\bar p_i.
\]

同一个系数同时作用于两套原始矩阵，不能分别调整。因此最终允许
`avg(s^R) != avg(s^F)`；这种差异是结构和闭包共同产生的结果，而不是人为给 family 指定更大
的总体 setup。正式数据必须输出两类实际均值、均值差、类内/类间比、setup/processing 比和
setup cost 占比。论文结果应表述为“family 类实例中观察到更强/更弱的外包反应，该现象可能
与类内转换较便宜、成组保留或成组移除任务有关”，不写成已经识别的单因素因果关系。

这个方案保留了用户希望的范围变化，也比直接复制 VRP 的类别生成方式更容易解释。当前仍需
最终确认的只剩 `eta_i` 是否采用 `[0.25,0.75]`，以及类内倍率 `a` 取 0.4 还是 0.5；其他
生成逻辑可以据此固定。

### 17.8 Setup 生成的直观解释、数值例子和文献依据

第 17.7 节的公式实际只是在同时控制两个东西：`eta_i` 控制 setup 总体有多大，`a` 控制
family 结构有多明显。random 与 family 不是两套完全无关的数据，而是同一个源实例下的配对
场景。这样后续即使不做严格因果表述，也能避免 family 场景仅仅因为随机抽到了更大的 setup
而显得更难或更容易。

具体可按以下四步理解。首先，对每个源实例计算平均加工时间 `p_bar_i`，再给它一个 setup
强度 `eta_i`，并令目标原始均值为

\[
\mu_i=\eta_i\bar p_i.
\]

Kramer（2015，第 4.7 节）在 Sen and Bulbul 实例上增加 setup 时，沿用 Cicirello and
Smith（2005）的规则：以 `s_bar=eta*p_bar` 为中心，在 `[0,2*s_bar]` 内按正态分布生成，
并采用 `eta=0.25/0.75` 两档。Bulhoes et al.（2020）的精确算法实验继续使用了这套 small/large
setup 数据。因此，本文采用 `[0.25,0.75]` 作为 setup/processing 相对强度的覆盖区间有直接的
调度文献来源；区间内的 20 个分层值是本文为了避免只比较两个极端档位而做的实验设计扩展，
不是原文参数。

其次，random 场景中每个有向 job-to-job setup 都按 Kramer 口径生成：

\[
s_{uv}^{R}\sim TN(\mu_i,(\mu_i/2)^2;0,2\mu_i).
\]

再次，把任务近似均分为 `F` 个 family。设有序类内任务对所占比例为 `q_i`，类内 setup 的
均值取 `mu_in=a*mu_i`，其中 `a<1`；类间 setup 均值则由

\[
q_i\mu_i^{in}+(1-q_i)\mu_i^{out}=\mu_i
\]

反推出

\[
\mu_i^{out}=\frac{\mu_i-q_i\mu_i^{in}}{1-q_i}.
\]

这不是为了制造复杂参数，而是让 family 原始矩阵在“类内小、类间大”的同时，整体期望仍与
random 相同。family scheduling 文献通常把同一材料或同一 family 内的转换视为零或可忽略，
把跨 family 转换视为主要 setup。Schaller, Gupta, and Vakharia（2000）明确采用这种解释；
Moser et al.（2022）的公开实例生成器也把同材料任务间 setup 设为 0，而材料间 setup 独立
生成。本文保留非零类内 setup，是把标准 family 模型放宽为“同类较便宜”，从而仍属于当前
一般 job-to-job sequence-dependent setup 模型。

例如，若 `p_bar=50`、`eta=0.5`，则 `mu=25`。假设有 4 个均衡 family，类内有序任务对约占
`q=0.25`，并暂取 `a=0.4`，则

\[
\mu^{in}=10,\qquad
\mu^{out}=\frac{25-0.25\times10}{0.75}=30.
\]

于是 random 场景的所有弧都围绕 25 波动；family 场景约 25% 的类内弧围绕 10 波动，约 75%
的类间弧围绕 30 波动，而加权平均仍为

\[
0.25\times10+0.75\times30=25.
\]

这就是前述公式的全部含义。实现时，两种场景对同一有向弧使用同一个基础随机数或同一个
分位数：random 把它映射到均值 25 的截断正态，family 根据该弧是否类内，映射到均值 10 或
30 的截断正态。这样能减少纯随机抽样噪声，但不会让两套 setup 数值相同。

最后，两套原始矩阵分别执行三角闭包。Fanjul-Peyro, Ruiz, and Perea（2019）指出，setup
三角性质既服务于模型，也具有实际解释；本文的 ng-DSSR 与相关剪枝还依赖删除中间任务不会
使转换时间变差的口径，因此正式数据仍必须满足这一性质。由于闭包可能对 random 与 family
产生不同幅度的缩短，不能再分别把两者强行拉回完全相同的最终均值。若闭包后两者均值分别为
`s_bar_R` 和 `s_bar_F`，只使用同一个公共比例

\[
c=\frac{\eta_i\bar p_i}{(\bar s_i^R+\bar s_i^F)/2}
\]

同时缩放两套矩阵，整数化后再做一次闭包复核。这个公共比例只校准总体时间尺度，不消除
family 结构自然造成的最终均值差异。比如闭包后均值为 20 和 18、目标为 25，则公共比例为
`25/19`；缩放后约为 26.32 和 23.68，而不是分别都变成 25。

论文中应把来源写清楚：截断正态和 `eta` 区间来自 Kramer/Cicirello；同 family 转换较小、
跨 family 转换较大来自 family/material scheduling 文献；相同随机数、期望均值配平和公共
闭包尺度是本文为构造配对实验加入的控制规则。后三者不能写成既有文献的原始生成器。当前
推荐先保留 `a=0.4` 作为待验证值，只用闭包后的类间/类内均值比判断 family 结构是否被保留，
不根据任何算法运行时间或目标值反向调参。

可直接引用的文献为：Cicirello and Smith（2005），*Journal of Heuristics*,
DOI `10.1007/s10732-005-6997-8`；Kramer and Subramanian（2019），*Journal of Scheduling*,
DOI `10.1007/s10951-017-0549-6`；Bulhoes et al.（2020），*Journal of Scheduling*,
DOI `10.1007/s10951-020-00640-z`；Schaller, Gupta, and Vakharia（2000），*European Journal
of Operational Research*, DOI `10.1016/S0377-2217(99)00387-2`；Moser et al.（2022），
*Journal of Scheduling*, DOI `10.1007/s10951-021-00714-6`；Fanjul-Peyro, Ruiz, and
Perea（2019），*Computers & Operations Research*, DOI `10.1016/j.cor.2018.07.007`。

### 17.9 截断正态与均匀分布的含义和选择

记号

\[
s_{ij}^{R}\sim TN(25,12.5^2;0,50)
\]

表示先从均值 25、方差 `12.5^2`（标准差 12.5）的正态分布抽取一个值，只接受落在
`[0,50]` 内的样本，越界时重新抽取，最后再按实例格式整数化。它不是把小于 0 的值改成 0、
把大于 50 的值改成 50；后者会在两个端点堆积概率。由于截断区间关于均值 25 对称，截断后
的实际均值仍为 25，但实际标准差约为 11.0，略小于原始正态的 12.5。

若改用同范围均匀分布 `U[0,50]`，均值也为 25，但标准差约为 14.43。两者的主要差异不是
平均 setup，而是离散程度。截断正态会让多数 setup 集中在平均值附近：约 71.5% 的样本位于
`[12.5,37.5]`；均匀分布在同一区间的比例只有 50%。因此均匀分布会产生更多接近 0 或 50 的
极端弧，而截断正态更接近“多数换型时间处于典型水平、少数较短或较长”的数据。

两种分布在调度文献中都能找到依据。Kramer（2015，第 4.7 节）明确采用限制在
`[0,2*eta*p_bar]` 内的正态分布，并使用 `eta=0.25/0.75`，Bulhoes et al.（2020）继续使用这套
small/large setup 实例。另一方面，sequence-dependent setup 文献也经常使用均匀分布，例如
Moser et al.（2022）在材料间 setup 上使用 `[1,125)` 的均匀分布，Schaller 等 family-setup
基准也使用多个均匀 setup 区间。因此均匀分布并非不合理，只是与本文当前沿用的 Kramer--
Bulhoes 数据链不一致，并且会额外改变 setup 的离散程度。

当前正式实验推荐保留截断正态，不把“正态/均匀”再增加为一个实验因素。理由是：第一，它
直接对应本文算法比较所参考的 Kramer/Bulhoes 实例；第二，`eta` 已经在 `[0.25,0.75]` 内覆盖
setup 强度变化，无需再用分布类型增加一层变化；第三，均匀分布带来的更多极端弧可能同时改变
Floyd 闭包幅度和算法难度，使 random/family 结构分析更难解释。family 场景的类内与类间弧
也使用同一种截断正态，只改变目标均值；统一最大值按第 17.10 节放宽为 `1.5*p_bar`。

### 17.10 Setup 最大值放宽到 `1.5*p_bar`

按本轮决定，`p_bar=50、mu=25` 的示例不再把最大 setup 限制为 50，而允许到 75。正式规则
不直接写死绝对值 75，而写成

\[
s_{\max}=1.5\bar p_i.
\]

因此示例分布改为

\[
s_{ij}^{R}\sim TN(25,12.5^2;0,75).
\]

仅提高上限不会让大量 setup 自动落入 `[50,75]`。在底层正态仍为 `N(25,12.5^2)` 时，原始
概率中约 2.27% 位于 `[50,75]`，超过 75 的概率仅约 0.003%。这个调整的含义是允许少量较长
换型，而不是把 setup 整体抬高。

需要注意，新区间 `[0,75]` 不再关于 25 对称。直接越界重抽后，条件均值约为 25.69，而非
严格的 25。正式生成器若仍要求 `eta_i*p_bar_i` 表示目标均值，应通过一次数值反解调整底层
正态的位置参数，使截断后的条件均值等于目标均值；不能继续把正态位置参数 25 直接称为最终
均值。random、family 类内和 family 类间均使用同一个绝对上限 `1.5*p_bar_i`，但分别校准到
各自的目标条件均值。Floyd 闭包只会缩短 setup；后续若保留公共尺度校准，也必须同时复核最终
最大值不超过 `1.5*p_bar_i`，不能在闭包后无约束放大。

这项修改是本文对 Kramer `[0,2*eta*p_bar]` 生成区间的扩展，不能写成 Kramer 原始参数。
论文中可表述为：正态分布及 setup/processing 强度区间沿用 Kramer 的设计思想，但统一把
允许的最长 setup 放宽至平均加工时间的 1.5 倍，以保留少量长换型场景。

### 17.11 Floyd 闭包后的正式参数口径

前述原始截断正态参数只能描述 Floyd 之前的候选弧，不能直接当作最终实例的 setup 分布。
Floyd 会把每条直接弧替换为最短中转路径，因此只会缩短 setup，但会同时改变最终均值、
标准差、分位数以及 family 场景的类内/类间均值比。换言之，即使 random 和 family 在闭包前
具有相同的期望总强度，闭包后也可能产生不同均值；闭包前配好的 family 结构也可能被部分
冲淡。正式论文必须区分“原始生成分布”和“闭包后实际统计”，不能声称最终矩阵仍服从原始
截断正态分布。

复核时发现，旧版 `ETConverter` 和 `SetupRatioVariantGenerator` 曾对虚拟点 0 与全部真实任务
执行完整有向 Floyd，而 `s[i][0]=0`。因此任意 job-to-job setup 被错误地强制满足

\[
s_{ij}\le s_{i0}+s_{0j}=s_{0j}.
\]

这会使 `i -> 0 -> j` 成为不属于调度序列的公共捷径，显著压低 job-to-job setup，并削弱类内
与类间的差异。根因是编号 0 在数据结构中同时承担初始状态和零成本终止端点，旧闭包把两种
语义错误地合并成一个可中转节点。论文的问题定义本来已经限定
`i in J union {0}, j,k in J`：0 可以作为 setup 弧的起点，但不能作为中间任务或目标任务。
因此正式闭包应只让真实任务 `k in J` 作为 Floyd 中间点，目标也只取真实任务，同时允许
`i=0`，从而同时保证真实任务间和 initial-setup 的三角不等式。`s[i][0]=0` 继续保留为终止
语义，但完全不参与闭包传播。

因此最终生成顺序应为：固定随机数和 family 划分；按候选分布生成原始矩阵；执行与算法假设
一致的真实任务节点 Floyd；计算闭包后统计；若未达到目标，则只调整 Floyd 前的整体尺度或 family
对比参数，并用同一随机数重新生成和闭包。目标 setup 强度 `eta_i*p_bar_i`、最大值
`1.5*p_bar_i` 和 family 结构强度均以闭包后结果验收。不能在 Floyd 后逐弧裁剪或局部补值，
因为这会重新破坏三角不等式。若使用整张矩阵的公共正比例缩放，缩放本身保持三角不等式，
但整数化和最大值约束仍需复核，必要时再执行一次只用于验证的 Floyd；更稳妥的正式实现是
通过固定随机数下的二分校准 Floyd 前尺度，使闭包后均值直接落入容差，而不是在闭包后强行
拉回目标。

当前结论是：即使修正 0 节点，Floyd 后仍会改变原始分布，因此正式设计仍应把闭包后矩阵
作为最终数据，把原始分布仅作为可复现的生成机制，并采用闭包后验收和前置参数校准。
`ETConverter` 与 `SetupRatioVariantGenerator` 已于 2026-08-20 修正为只通过真实任务执行闭包；
历史上已经按旧规则闭包的数据无法逆推出原矩阵，正式算例必须从未闭包的源数据重新生成，
不能直接沿用现有 `data/` 中被 0 捷径压缩过的 setup。

对提交 `3aa16686` 闭包前后的三个代表实例进行复核后，旧数据在数学上仍然满足当前论文要求
的三角不等式，甚至满足把 0 也包括在内的更强条件，因此基于这些文件得到的历史最优性证书
仍对应各自输入，不属于求解正确性错误。但旧闭包显著改变了实例：40-2、50-2 和 100-2 的
第一个实例中，job-to-job 平均 setup 分别由 `26.04/28.16/26.56` 降为
`9.00/14.57/7.30`，降幅约为 `65.43%/48.27%/72.53%`；被修改的任务间弧比例约为
`90.13%/82.12%/93.49%`，并且三组中所有任务间弧均满足 `s[i][j]<=s[0][j]`。这正是虚拟点
捷径造成的非预期结构约束。

从同一批闭包前矩阵改用修正后的真实任务节点 Floyd，三组平均 setup 为
`13.31/15.40/8.41`，仍会因为完整随机图上的真实任务最短路而低于原始均值，但不再使用
终止弧。修正闭包后的论文口径三角违例均为 0。由此可见，排除 0 修复了语义错误，却不会
消除 Floyd 对随机分布的压缩；正式 family/random 生成仍需按闭包后统计进行尺度与结构验收。

### 17.12 Dabia 时限与错误 Floyd 的额外影响

Dabia、Lai 和 Vigo（2019）在第 7 节明确说明：算法使用 Java 实现，运行机器为 Intel Core
i7 2.8 GHz，主问题 LP 使用 Gurobi 6.5.1，全部实验统一采用一小时求解时限。其表格中的平均
CPU time 只对相应口径下在时限内求得最优的实例计算，不能把平均时间误解为实际时限。本文
当前采用 10800 秒不是对该论文设置的复现，而是考虑当前机器、问题难度和四算法比较后设置的
更长统一时限；写实验设置时应明确说明，不应称为沿用 Dabia 的时限。

为区分“真实任务 Floyd 本身的压缩”和“错误允许 0 中转的额外压缩”，进一步对
40-2、50-2、100-2 每个规模前 5 个实例进行同源对照。每个实例均从提交 `3aa16686` 之前的
原始 setup 出发，分别执行旧全节点闭包和修正后的真实任务节点闭包。结果如下：

| 规模 | 样本数 | 错误闭包额外平均降幅 | 单例降幅范围 | 两种结果不同的弧比例 | 单例弧比例范围 |
|---|---:|---:|---:|---:|---:|
| 40-2 | 5 | 17.75% | 9.30%--32.37% | 44.97% | 31.86%--64.10% |
| 50-2 | 5 | 15.37% | 5.40%--35.27% | 40.15% | 19.47%--75.71% |
| 100-2 | 5 | 21.72% | 8.89%--34.24% | 53.24% | 27.20%--73.09% |

这里的“额外降幅”以修正闭包结果为分母，即
`1 - wrongFullFloydAvg / correctedJobOnlyFloydAvg`；“不同的弧比例”统计所有有向
job-to-job 非对角弧。结果说明错误并非只影响少量边界弧：平均约 40%--53% 的任务间弧发生
改变，setup 均值被额外压低约 15%--22%。旧数据依然满足论文要求的三角不等式，因此旧求解
证书有效；但其 setup 强度和结构不再代表预期生成机制，不能进入正式数据面板。

### 17.13 使用 Floyd 时的最终 setup 生成方案

发现虚拟点错误以及真实任务 Floyd 的规模性压缩后，正式生成不能继续使用“先把原始截断正态
均值设为 `eta_i*p_bar_i`，闭包后直接接受”的做法。Floyd 前的分布只负责生成相对弧结构；
实例级 setup 强度必须定义为 Floyd 后 job-to-job 弧的实际均值。

对源实例 `i`，仍令

\[
\mu_i=0.5\bar p_i,
\qquad
C_i=\left\lfloor1.5\bar p_i\right\rfloor,
\]

所有源实例统一采用中等 setup 强度，不再让 `eta` 随实例变化。random 场景继续按截断正态生成
原始弧；family 场景继续使用同一批随机分位数，但按类内均值 `a*mu_i` 和配平后的类间均值生成。虚拟初始
状态到任务的原始 setup 使用两种场景共同的随机数；所有 `s[j][0]` 仅表示终止并保持 0。原始
setup 和首次 Floyd 全程使用连续 `double`，不能在闭包前先取整；否则取整产生的异常小弧会
被最短路传播，后续统一缩放无法恢复原始结构。当前 `SetupRatioVariantGenerator` 仍是先生成
整数弧再执行 Floyd，只适合既有诊断实验，不能直接作为正式生成器。

每套原始矩阵首先执行修正后的任务节点 Floyd：中间点和目标点只取真实任务，初始状态 0
只允许作为起点。记所得有向度量为 `d_uv`。随后不逐弧补值，而是对整套闭包结果应用同一
标量变换

\[
s_{uv}(c)=\left\lceil\min\{c d_{uv},C_i\}\right\rceil .
\]

通过一维二分选择 `c`，使最终 job-to-job 非对角弧均值尽量接近 `mu_i`。由于向上取整后均值
关于 `c` 是单调阶梯函数，实现应保留目标两侧的候选，选择绝对误差较小者；误差相同时固定
选择较小的 `c`，不能声称每个实例都能连续地精确命中目标。缩放保持三角
不等式，统一上限截断 `min(x,C_i)` 仍保持三角不等式，向上取整也保持该性质；因此该变换不
需要依靠第二次 Floyd 再次改变数据。实现中仍应在整数化后运行一次 Floyd 审计，但必须要求
`changedArcs=0`，否则说明生成或整数化实现存在错误。这里先将 `C_i` 向下取为整数，因此向上
取整后的 setup 也不会超过该上限。

random 与 family 应分别求自己的尺度 `c_R` 和 `c_F`，使二者在同一源实例上具有相同的最终
平均 setup `mu_i`。这比先前“共用一个闭包后尺度、允许最终均值不同”的方案更适合正式配对：
已确认 Floyd 对不同结构和不同任务规模的压缩幅度差异很大，若不分别归一化，family/random
差异会同时混入总 setup 强度和结构，无法判断结果来自哪一项。分别归一化只控制总强度，不会
消除类内/类间的相对结构。

family 场景暂保留 `a=0.4` 作为原始类内倍率，但不根据求解时间或目标值调参。生成后只做数据
结构验收：报告闭包前后和最终的类内均值、类间均值及其比值；若任务节点 Floyd 后类间/类内
比已经接近 1，说明当前 family 生成方式被闭包洗掉，应改用 family-level metric 构造，而不是
继续减小 `a` 直到获得希望的算法结果。

每个正式实例至少输出以下 setup 元数据：固定 `eta=0.5`、`p_bar_i`、目标均值 `mu_i`、上限 `C_i`、
原始均值、首次 Floyd 后均值、闭包压缩率、首次 Floyd 修改弧比例、最终缩放系数、最终均值、
目标均值误差、最终最大值、达到上限的弧比例、最终三角违例数、审计 Floyd 修改弧数，以及
family 场景的类内/类间均值比。
setup cost 最后按 `kappa_uv=20*s_uv` 生成，不能在校准前参与 setup time 的 Floyd。

同一任务集合只生成一次 random/family setup 矩阵，并在该任务集合的不同机器数 `m` 下复用；
setup 随机种子不能包含 `m`。否则机器数效应会与另一套随机 setup 混在一起，破坏配对比较。

这里不再把 `avg(s_ij)/p_bar=0.25/0.50/0.75` 作为额外的三档 setup 实验因素，也不再让该
比值在 20 个实例之间分层变化。正式生成统一要求
`avg(s_ij)/p_bar_i` 尽量接近 0.5，random/family 在同一实例上使用相同目标。这样 setup 大小
保持为固定的中等背景条件，实验只比较 random/family 的结构差异，不需要在结果中解释 setup
强度变化。正式输出仍保留实际 `avg(s_ij)/p_bar_i`，但仅用于验证生成精度。

该方案的含义是：截断正态仍与 Kramer/Bulhoes 数据链保持联系，Floyd负责把原始弧转化为算法
要求的有向度量，闭包后归一化负责消除任务规模和结构导致的强度漂移。正式论文应报告原始
生成分布和闭包后归一化规则，不能把最终矩阵表述为仍服从截断正态。

### 17.14 冻结前的剩余参数（已由第 18 节解决）

本节记录进入最终冻结前的状态；其中五项待定内容均已在第 18 节解决。此前已经确定且不再
讨论的口径包括：`n=20/40/50/60/80/100`、每个规模 20 个源实例、对应机器数 `2/3/4` 或
`3/4/5`、共同参考机器数 `3/4`、固定窗口半宽 `W=0/100/300`、random/family 两类 setup、
Floyd 后 `avg(s_ij)/p_bar≈0.5`、`s_ij<=floor(1.5*p_bar)`、`kappa_ij=20*s_ij`、三段
incremental discount `(1,0.85,0.70)`、由 `Q50_ref` 一次生成并跨规模固定的绝对断点、单线程
和 10800 秒时限。每个源实例完整生成三个窗口和两类 setup，不再采用把 20 个实例拆给六种
环境的平衡不完全设计。

目前真正需要在正式生成器实现前冻结的参数只有以下几项。

1. **源实例选择与缺失规模抽取。** 已确定每个规模取 20 个，但尚未最终选择固定随机抽样还是
   基于可观察数据特征的代表性抽样；`n=20` 从 40-task、`n=60/80` 从 100-task 抽取时，是否
   使用同一固定排列的嵌套前缀也未最终确认。选择规则必须只使用原始数据特征，不能使用任何
   求解时间、gap 或算法结果。

2. **family 原始类内倍率。** family 数、均衡随机分组和类间均值配平公式已确定，目前只剩
   `a=0.4` 是否直接冻结。该值只能通过 Floyd 后的类间/类内 setup 比检查结构是否仍存在，
   不能根据算法快慢或外包比例调整。若不再增加数据生成试验，可直接固定 `a=0.4` 并完整报告
   最终结构比。

3. **10 倍和 20 倍时间组的实例级倍数。** 时间尺度为 `1/10/20` 已确定，但仍需在“全部实例
   精确乘 10/20”和“20 个实例分别使用 `[8,9,10,11,12]`、`[16,18,20,22,24]`，组均值分别
   为 10/20”之间选择。前者最容易解释，后者符合此前希望的实例间尺度变化。

4. **外包价格点数。** 基础报价量、价格乘数的作用位置和折扣函数已确定；主价格集合仍需在
   `lambda={0.5,1,2}` 与 `{0.5,1,1.5,2}` 之间选择。三档足以比较低/中/高价格，四档只提高
   中高区间响应曲线的分辨率，同时增加约三分之一的外包求解量。

5. **数量折扣专门对照的覆盖范围。** 有/无折扣的政策定义已确定，当前建议只在 `n=50`、全部
   20 个源实例、三个机器数、三个窗口和两类 setup 上比较；是否正式采用这一范围尚未得到
   最终确认。它不影响外包性能主矩阵的数据生成，只影响新增无折扣求解数量。

除此之外，三套 BPC profile、compact CPLEX 对照、共同初始列、实时日志和结果字段都已经固定。
现有 `formal-v1` 仍是旧占位数据，不能因为算法参数已确定就直接用于正式服务器长跑；上述五项
冻结后还需要重新实现正式数据生成并重建 manifest。

## 18. 最终冻结的正式实验设计

本节记录上述五项的最终决定，并作为后续正式数据生成、manifest 构造和论文实验章节的唯一
当前口径。第 13--17 节保留讨论演化和选择依据；其中与本节冲突的参数均以本节为准。

### 18.1 源实例、任务子集与共同基础数据

正式规模为 `n=20/40/50/60/80/100`，每个规模 20 个任务集合。源算例不再做特征聚类或按
求解难度筛选，而是从 Tanaka 相应规模的 125 个文件中用固定随机种子无放回选择。随机种子、
被选文件编号和任务下标全部写入 suite metadata，选择过程不得读取求解时间、gap 或算法结果。

`n=20` 与 `n=40` 共用 20 个被选中的 40-task 父实例：每个父实例对 40 个任务做一次固定随机
排列，前 20 个形成 20-task 子集，全部 40 个形成 40-task 实例。`n=60/80/100` 共用 20 个
被选中的 100-task 父实例：同一随机排列的前 60、前 80 和全部 100 个任务形成嵌套子集。
`n=50` 从原生 50-task 数据中独立随机选择 20 个文件。保留任务的 processing time 和两类
TWET 权重不变；对子集先按保留 workload 占父实例 workload 的比例缩放 Tanaka due date，
再按参考机器数生成共同 due-window center：

\[
d_j^S=\operatorname{round}\left(d_j\frac{\sum_{k\in S}p_k}{\sum_{k\in J}p_k}\right),
\qquad
c_j=\left\lceil\frac{d_j^S}{m_{ref}}\right\rceil.
\]

`n<=60` 使用 `m=2/3/4` 和 `m_ref=3`，`n>=80` 使用 `m=3/4/5` 和 `m_ref=4`。同一任务集合
在不同机器数下共用 processing、权重、center、setup time 和 setup cost，只改变机器数量。
窗口半宽固定为 `W=0/100/300`；这里 W 是 `[center-W,center+W]` 的半宽，不做任务级扰动。

### 18.2 Setup time 与 setup cost

每个任务集合生成 random 和 family 两套 setup。两者最终均满足

\[
\operatorname{avg}_{i\ne j}(s_{ij})/\bar p\approx0.5,
\qquad
s_{ij}\le\lfloor1.5\bar p\rfloor.
\]

random 使用截断正态原始弧；family 数随任务规模固定为 `3/3/4/4/5/6`，使用固定随机种子做
近似均衡分组，不按 processing、due date 或权重排序。family 原始类内均值倍率正式固定为
`a=0.4`，类间分布中心按有序类内任务对比例配平，使 Floyd 前的名义加权中心与 random 相同。两种结构
使用共同随机分位数和共同初始 setup 随机数。

具体令 `mu=0.5*p_bar`、`C=floor(1.5*p_bar)`。random 弧按

\[
\widetilde s_{ij}^{R}\sim TN(\mu,(\mu/2)^2;0,C)
\]

生成。这里 `mu` 是截断前正态分布的中心；最终强度仍由 Floyd 后校准决定。family 中若有序
类内任务对比例为 `q`，则类内中心为 `mu_in=0.4*mu`，类间中心为

\[
\mu_{out}=\frac{\mu-q\mu_{in}}{1-q}.
\]

类内和类间分布的标准差分别取各自中心的一半，并使用共同上限 C。初始状态到任务的原始 setup
在 random/family 中使用相同的 random 分布和随机分位数；所有 `s[j][0]` 保持为 0。

原始弧和首次 Floyd 使用连续值；Floyd 的中间点和目标点只能是真实任务，虚拟点 0 只允许作为
起点。对闭包结果分别寻找统一放大系数，并按

\[
s_{ij}(c)=\left\lceil\min\{c d_{ij},\lfloor1.5\bar p\rfloor\}\right\rceil
\]

使 random/family 的最终平均值都最接近 `0.5*p_bar`。整数化后的第二次 Floyd 只作审计，必须
满足三角违例为 0 且 `changedArcs=0`。setup cost 最后固定为 `kappa_ij=20*s_ij`。正式数据
同时输出闭包压缩率、放大系数、目标误差、上限命中率和 family 的类间/类内均值比；`a=0.4`
不再根据算法速度、目标值或外包比例调整。

### 18.3 时间尺度

纯调度实验使用原尺度和两个放大档。对每个规模先用固定随机种子独立抽取 10 个
`u in {5,...,15}`，每个 u 同时加入 `u` 和 `20-u`，再固定随机打乱，得到 20 个 `g_L`；因此
所有值都位于 `{5,...,15}` 且样本均值严格为 10。再令 `g_H=g_L+10`，因此高档位于
`{15,...,25}` 且样本均值为 20。同一源实例的全部机器数、窗口和 random/family 场景共用
相同的 `g_L/g_H`，避免时间尺度与其他因素混杂。

放大按实例进行，不能给同一实例中的不同任务分别抽倍数。processing time、due-window center、
窗口半宽和 setup time 同乘 `g`，TWET 单位时间权重保持不变，setup cost 仍按放大后的
`20*s_ij` 计算。这样一个实例内部的任务顺序关系、窗口相对位置和 setup 三角结构保持不变；
实验比较的是数值时间域和 time-indexed horizon 的扩大，而不是另一套随机调度问题。

### 18.4 实验一：无外包调度的精确算法比较

实验一关闭外包，比较四种方法：compact CPLEX、ng-DSSR BPC、time-indexed no-cut BPC 和
time-indexed rank-1/SRI BPC。每个规模的 20 个源实例完整交叉三个机器数、三个窗口、两类
setup 和三个时间尺度，四种方法使用同一派生实例；三种 BPC 共享相同初始列、incumbent 和
fingerprint，compact CPLEX 使用对应调度作为 MIP start。完整求解量为

\[
6\times20\times3\times3\times2\times3\times4=25{,}920.
\]

本节主要比较规定时限内求得最优的数量、总时间、最终 gap、root bound/gap、节点数、列数、
cut 数、master/pricing/branch 时间和内存。time-indexed 额外报告图节点、图弧和 arc fixing；
ng-DSSR 报告 label、DSSR 轮数、completion bound、midpoint probe、join 和正反向扩展时间。
分析重点是任务规模、机器数和 due-window 对四种方法的影响，以及 `[5,15]`、`[15,25]` 时间
放大后 time-indexed horizon 成本与 ng-DSSR 数值稳定性的差异。所有 timeout 都保留最终证书
和 gap，不能只汇总成功实例。

### 18.5 外包数据和外包成本

外包实验只使用原时间尺度，但保留全部任务规模、机器数、窗口和两类 setup。任务 `j` 的标准
报价量固定为

\[
q_j=\bar p\max\{w_j^E,w_j^T\}.
\]

在选定的 20 个正式 50-task 任务集合上计算 `Q_i_all=sum_j q_ij`，取其中位数为 `Q50_ref`，
再一次性固定绝对断点

\[
Q_1=0.25Q_{50}^{ref},\qquad Q_2=0.50Q_{50}^{ref}.
\]

这些断点跨任务规模、机器数、窗口和价格保持不变。正式外包价格只取三档
`lambda=0.5/1/2`。默认支付函数为连续 incremental discount：

\[
G_\lambda(B)=\lambda\left[
\min(B,Q_1)+0.85\min((B-Q_1)^+,Q_2-Q_1)+0.70(B-Q_2)^+
\right],
\quad B=\sum_{j\in O}q_j.
\]

因此价格只改变支付水平，不改变任务的标准报价量和折扣断点。

### 18.6 实验二：外包模型的性能比较

实验二比较 compact CPLEX、外包集合列化的 `columns` formulation 和 master 中显式外包/
tariff 变量的 `masterVariables` formulation。两种 BPC 都固定使用 ng-DSSR 作为内部调度定价，
不在不同场景临时切换 pricing。对所有 `n/m/W/setup` 原尺度场景和三个价格完整求解，默认都
使用上述中等数量折扣，完整求解量为

\[
6\times20\times3\times3\times2\times3\times3=19{,}440.
\]

除实验一的算法指标外，本节报告内部/外包 pricing 时间、内部列与外包列数量、RMP 迭代、
Phase-I repair、分支类型、最终外包任务比例、外包 workload 比例和成本分解。核心问题是两种
外包表示的求解效率如何随规模和外包率变化，以及允许外包后问题相对同源纯调度实例是更容易、
更困难还是呈现中间外包率最难。后续管理分析只使用本节总体更稳定的一个 BPC formulation。

### 18.7 实验三：外包价格、产能和窗口的管理分析

本节不新增求解，直接复用实验一和实验二的同源最优解或规定时限结果。成本层报告 earliness、
tardiness、setup、外包支付和总成本；服务层报告早到、窗内、迟到比例；决策层报告外包任务数、
外包 workload、机器负荷和 tariff 所在分段；结构层报告外包前后内部相邻弧、平均 setup、机器
序列和拥挤时段变化。

分析重点是低/中/高价格在不同机器数、窗口和 random/family 环境下是否产生不同外包响应；
允许外包是否只是替代直接成本，还是会移除 due-window 不协调或高 setup burden 的任务，从而
同时降低内部 TWET/setup 并重构机器序列。任务特征只作探索性后处理，只有跨实例和价格稳定
出现的规律才写成一般结论。

### 18.8 实验四：有无数量折扣

数量折扣对照固定为 `n=50`、20 个源实例、`m=2/3/4`、W0/W100/W300、random/family、原始
时间尺度和中等价格 `lambda=1`，使用实验二选出的 BPC formulation。比较无折扣
`(1,1,1)` 与默认折扣 `(1,0.85,0.70)`，断点均使用固定 `Q1/Q2`。有折扣结果已包含在实验二，
因此只新增

\[
20\times3\times3\times2=360
\]

个无折扣求解。重点分析外包集合 Jaccard、外包 workload、跨断点实例数、折扣节省和内部序列
变化，区分“折扣只降低原有外包支付”和“折扣诱导一组任务共同外包”两种机制。

### 18.9 运行、输出和当前状态

所有正式求解单线程、时限 10800 秒，并通过四个独立子 JVM 的 scheduler 持续运行。每个 run
保留实时 `live.log/stdout.log/stderr.log/status.txt`，结束后输出核心摘要、组件耗时、节点、列、
cut、外包决策、最终机器调度和完整列池。实时统计只在阶段边界更新，高频 label/arc/PWLF 诊断
默认关闭，不影响热路径。

上述研究参数已全部冻结；后续只需在实现时给源文件抽样、任务排列、family 分组和尺度分配设置
独立固定随机种子，并把实际值写入 metadata。这些种子是复现标识，不再是需要根据实验结果选择
的研究参数。现有 `formal-v1` 使用旧窗口、时间尺度、setup 和外包占位参数，不能直接长跑；必须
按本节重新实现正式生成器并生成新的实验包。三个主求解区块合计 45,720 次求解，需按预注册
manifest 分批执行并完整保留 timeout。

## 19. 图规模、折扣断点与求解矩阵压缩分析

本节回应第 18 节冻结后暴露出的计算量问题。数据生成参数本身不需要撤回，但“每种方法在全部
因子组合上都运行”造成 45,720 次求解，明显超出必要证据范围。以下压缩方案目前是建议，尚未
覆盖第 18 节；待确认后再修改正式生成器和 manifest。

### 19.1 Time-indexed 图规模可以分析什么

time-indexed 的规模不是抽象描述，可以用低频、可复现指标直接量化。当前每次定价消息已经输出
实际 horizon；root preprocessing 消息已经包含平均 compact-window 长度和缩减比例，以及
paper graph fixing 的候选弧数、固定弧数、process/idle/end/cleanup 分类。由实例和最终窗口还
可以一次性计算 dense state capacity `(n+1)*(H+1)` 与 active window states
`sum_j(end_j-start_j+1)`。这些指标与 exact pricing 调用次数和平均时间结合，足以解释时间尺度
放大为什么增加 time-indexed 成本。

热循环中的 `states/arcScans/timeArcSkips` 受默认关闭的 diagnostics 开关控制，正式运行不应为了
论文表格重新开启数亿次计数。实现正式结果输出时，应把 horizon、dense/active states、root
fixing candidate/fixed 和 window shrink 作为一次性结构化字段写入结果；不要开启逐弧诊断。
因此“图规模”可以分析，但应区分静态图容量和实际扫描工作量，不能把两者混成同一个数字。

### 19.2 固定断点与 Dabia 等人的一致性边界

Dabia、Lai 和 Vigo 使用跨 25/50/100-customer 实例固定不变的绝对需求断点 200/400/600，
形成四段 tariff；断点不是按每个实例总需求比例重新计算。本文先从 50-task 正式样本生成唯一的
`Q50_ref`，再固定 `Q1=0.25*Q50_ref`、`Q2=0.50*Q50_ref` 并跨全部规模使用，和参考论文的
核心逻辑一致：断点只校准一次，之后是统一的绝对 tariff，不同规模达到折扣的难易程度自然不同。

两者并非参数完全相同。参考论文使用三个断点和四段价格，本文使用两个断点和三段 incremental
价格；参考论文的 200/400/600 来自给定 tariff sheet，本文的绝对数值由 50-task 标准报价量
确定。若标准报价总量近似随 n 线性增长，本文 Q1/Q2 对 n20、n40、n50、n60、n80、n100 的
大致比例分别为 `(62.5%,125%)`、`(31.25%,62.5%)`、`(25%,50%)`、`(20.8%,41.7%)`、
`(15.6%,31.25%)`、`(12.5%,25%)`。这与参考论文首两个断点在 25-customer 上较难达到、
在 100-customer 上明显更容易达到的结构十分接近。正式数据只需额外输出每个实例的
`Q1/Q_all`、`Q2/Q_all` 和断点可达性，确认实际比例没有因权重分布严重偏离该近似。

因此该断点设计是合理的，也比逐实例使用 25%/50% 更接近参考论文。小规模可能无法进入第三段
不是错误，而是统一绝对 tariff 的预期规模效应。数量折扣管理分析固定 n50，也正好位于两个
断点都具有可解释性的参考规模。

### 19.3 45,720 次从哪里产生

第 18 节中，一个源实例在纯调度区块被扩展为 `3m*3W*2setup*3scale*4methods=216` 次求解；
在外包区块又被扩展为 `3m*3W*2setup*3price*3methods=162` 次。真正造成爆炸的是方法和所有
环境全交叉，不是随机生成 20 个源任务集合。源数据生成成本很低，仍可为每个规模保留 20 个
任务集合；求解 manifest 没有必要让每个集合承担全部研究问题。

### 19.4 推荐的平衡求解矩阵

简单把每个规模从 20 个源实例减为 10 个，仍会产生约 7,000--8,000 次求解，而且会放弃已经
确定的 20 个正式任务集合。更合理的做法是保留全部源数据，但不让每个源实例重复承担全部
`W*setup` 环境。算法比较和管理分析采用不同但预先固定的覆盖口径。

1. **纯调度原尺度主比较。** 对每个规模的 20 个源实例，按固定随机方案分配到六个
   `W*setup` 单元，单元频数为 `4/4/3/3/3/3`，并在六个规模间轮换获得第 4 个实例的单元。
   每个环境仍完整运行三个机器数和四种方法，因此方法与机器数比较严格配对。总量为
   `6*20*3*4=1,440` 次。W 和 setup 的效应在跨规模的平衡样本上分析，不对每个 n 的单个
   3--4 实例单元作过强结论。

2. **时间尺度机制面板。** 固定 `n=40/50/60`，每个规模预先选择 10 个源任务集合，均衡分配
   W100/W300，固定 random setup 和 `m=2/3`，只运行两个放大档下的 ng-DSSR 与
   time-indexed no-cut。原尺度从主面板复用，新增 `3*10*2*2*2=240` 次。这里的目标是验证
   horizon 机制，不需要让 compact CPLEX 和 rank-1/SRI 重复承担极端时间域。

3. **外包 formulation 选择。** 固定 `n=40/50`，每个规模 10 个预先平衡分配的环境实例，
   完整运行三个机器数、三个价格和 compact/columns/masterVariables，共
   `2*10*3*3*3=540` 次。该面板负责选择外包表示，不要求在所有规模上重复比较三种表示。

4. **胜出外包 formulation 的规模扩展。** 对 `n=20/60/80/100` 各取 10 个平衡环境实例，
   三个机器数和中等价格下比较 compact 与胜出 formulation，共 `4*10*3*2=240` 次。这样仍
   能检验模型随规模的扩展性，而低/中/高价格对计算的影响已由第 3 项识别。

5. **n50 管理分析。** 对 n50 全部 20 个源任务集合完整交叉三个 W、两类 setup、三个机器数
   和三个价格，但只运行胜出 formulation，共 `20*3*2*3*3=1,080` 次。它承担价格、产能、
   窗口和 setup 结构的交互分析。为计算 value of outsourcing，只为缺失的 n50 环境补一个
   已选定纯调度方法，扣除主面板已有环境后新增 `20*3*2*3-20*3=300` 次。

6. **有无折扣。** 在同一 n50 管理面板、中等价格和胜出 formulation 下新增无折扣结果，
   共 `20*3*2*3=360` 次。有折扣结果直接复用第 5 项。

上述名义总量为 4,200 次；第 3 项中 n50 胜出 formulation 的 90 次结果已经包含在第 5 项，
由 manifest 去重后约为 4,110 次。若第 4 项与其他面板还有完全相同的 run，也应继续按完整
fingerprint 去重。该数量相比 45,720 次减少约 91%，同时保留每个规模 20 个公开源任务集合、
所有算法的同环境配对以及 n50 管理分析的完整因子交叉。

数据文件也不应按每个 run 重复生成。正式数据层只保存 120 个基础任务集合及其 random/family
setup realization；W、机器数和时间倍数生成派生场景，价格、折扣和算法仅作为 manifest 中的
运行参数。这样“20 个源实例”不会膨胀成数万份重复数据，求解矩阵也能按章节独立续跑。
