# 正式实验当前统一方案

本文档把 2026-08-20 至 2026-08-23 的实验讨论整理成一套可执行口径。早期记录中的 25,920 次四方法全因子、原尺度主表加时间放大补充面板、每规模 20 个源实例完整交叉，以及只保留 900 次外包定向面板等方案均为讨论过程，不再作为当前执行方案。当前纯调度和外包性能实验使用同一组基础环境；纯调度改变时间尺度，外包实验固定原尺度并以三档外包价格替换三档时间尺度。数量折扣面板按最新每格 5 个实例的计算预算记录。正式求解总量为 `4050+4050+90=8190` 次，不含共享初始列生成和小规模正确性验证。

## 1. 共同数据生成口径

### 1.1 源任务集合

正式规模使用 `n=20/40/50/80/100`，不再把 `n=60` 放入主矩阵。每个规模固定选择 5 个任务集合，不根据求解时间、gap 或任何算法结果筛选。

`n=20` 和 `n=40` 从同一批 5 个 Tanaka 40-task 文件构造。对每个父实例使用固定随机种子排列任务，前 20 个任务形成 n20，全部任务形成 n40。`n=50` 从原生 Tanaka 50-task 文件中固定随机选择 5 个。`n=80` 和 `n=100` 从同一批 5 个 Tanaka 100-task 文件构造，前 80 个任务形成 n80，全部任务形成 n100。由此既保留 Tanaka 的 processing time 与 TWET 权重，也能在 20/40 和 80/100 之间做嵌套规模比较。

所有抽样种子、父文件编号、任务排列和保留下标必须写入 metadata。正式数据生成不得读取历史求解结果。

### 1.2 机器数和 due-window

`n<=50` 使用 `m=2/3/4`，共同参考机器数为 `m_ref=3`；`n>=80` 使用 `m=3/4/5`，共同参考机器数为 `m_ref=4`。同一任务集合在不同机器数下共用 processing time、TWET 权重、due-window center、setup time 和 setup cost，只改变机器数量，避免把机器数效应与另一套随机数据混在一起。

对子集实例，先按保留 workload 比例缩放父实例的 Tanaka due date，再按参考机器数生成共同中心：

\[
d_j^S=\operatorname{round}\left(d_j\frac{\sum_{k\in S}p_k}{\sum_{k\in J}p_k}\right),
\qquad
c_j=\left\lceil\frac{d_j^S}{m_{ref}}\right\rceil.
\]

窗口半宽为 `W=0/100/300`，任务 j 的 due window 为 `[max(0,c_j-W),c_j+W]`。W 是统一半宽，不对单个任务再加随机扰动。W0 保留为零宽边界情形；W100 和 W300 分别代表中等和较宽窗口。

### 1.3 Setup time 和 setup cost

每个任务集合生成 random 和 family 两套 sequence-dependent setup。两者最终都校准到

\[
\operatorname{avg}_{i\ne j}(s_{ij})/\bar p\approx 0.5,
\qquad
s_{ij}\le \lfloor\bar p\rfloor,
\]

因此 setup 总强度保持为相同的中等背景条件，主要比较随机结构与 family 聚集结构，而不是把 setup 大小再增加为一个实验因子。

具体令

\[
\mu=0.5\bar p,
\qquad
C=\lfloor\bar p\rfloor.
\]

新上限使单条 setup 不超过平均 processing time；取整前的区间 `[0,\bar p]` 关于 `\mu` 对称，`floor` 带来的小偏差由后续位置参数校准吸收。random 原始弧采用截断正态，目标均值为 `\mu`，标准差为 `\mu/2`。这里的目标均值是截断后的条件均值；实现时通过一维数值求解确定截断前正态位置参数，再用逆累积分布函数采样，不能把位置参数直接当成截断后的实际均值。

family 数随 `n=20/40/50/80/100` 分别取 `3/3/4/5/6`。对每个任务集合先用固定随机种子打乱任务，再按 round-robin 分配到 family，使任意两个 family 的任务数最多相差 1，且分组不使用 processing、due date、权重或求解结果。设 family `f` 的任务数为 `n_f`，有序类内任务对比例为

\[
q=\frac{\sum_f n_f(n_f-1)}{n(n-1)}.
\]

这里的 `q` 不是额外实验参数，而是全部有序任务对中“起点和终点属于同一 family”的比例。family `f` 内共有 `n_f(n_f-1)` 条真实任务弧，全部任务共有 `n(n-1)` 条真实任务弧，因此上述比值正好给出类内弧占比。整体原始均值满足 `q*mu_in+(1-q)*mu_out=mu`；先规定类内均值为 `0.4mu`，再解这个加权均值方程，就得到 `mu_out=(mu-q*mu_in)/(1-q)`。它让 family 场景具有明显的“类内低、类间高”结构，同时不因总体 setup 均值改变而与 random 场景失去可比性。

family 原始弧的类内目标均值为

\[
\mu_{\mathrm{in}}=0.4\mu,
\]

类间目标均值按

\[
\mu_{\mathrm{out}}=
\frac{\mu-q\mu_{\mathrm{in}}}{1-q}
\]

确定。这样在执行 Floyd 前，按全部有序任务对加权后的 setup 期望仍为 `\mu`。类内和类间标准差分别取 `\mu_in/2` 和 `\mu_out/2`，共同截断到 `[0,C]`；同样通过校准截断前位置参数，使截断后的条件均值命中对应目标。random 与 family 对每条有序弧共用同一个均匀分位数 `u_ij`，再分别映射到各自的截断分布；因此两种结构的随机性相互配对，差异主要来自是否具有 family 结构。虚拟起点到任务的原始 setup 在两类场景中使用相同的 random 分布和相同分位数。

按上述近似均衡分组，各规模的名义参数如下。`mu_out` 始终低于新上限 `C≈p_bar`，不会因为配平公式本身被上限截断。

| n | family 大小 | q | `mu_out/mu` | `mu_out/p_bar` |
|---:|---|---:|---:|---:|
| 20 | 7/7/6 | 0.300 | 1.257 | 0.629 |
| 40 | 14/13/13 | 0.317 | 1.278 | 0.639 |
| 50 | 13/13/12/12 | 0.235 | 1.184 | 0.592 |
| 80 | 16/16/16/16/16 | 0.190 | 1.141 | 0.570 |
| 100 | 17/17/17/17/16/16 | 0.158 | 1.113 | 0.556 |

原始 setup 和第一次 Floyd 全程使用连续值，不能在闭包前取整。Floyd 的中间点和目标点只允许真实任务；虚拟点 0 只能作为起点，`s[j][0]=0` 只表示结束且不得参与闭包传播。记闭包结果为 `d_ij`，random 和 family 分别寻找自己的统一尺度 `c_R/c_F`，并按

\[
s_{ij}(c)=\left\lceil\min\{cd_{ij},C\}\right\rceil
\]

转换为整数，使 job-to-job 弧的最终均值最接近 `\mu=0.5\bar p`。分别校准尺度是为了让两类 setup 的最终总强度可比，而不是消除 family 的类内/类间差异。整数化后再次执行 Floyd 审计，要求三角违例数和二次 Floyd 改写弧数均为 0。setup cost 最后固定为

\[
\kappa_{ij}=20s_{ij}.
\]

每个数据文件同时记录 `p_bar`、`mu`、`C`、family 数及各 family 大小、`q`、`mu_in/mu_out`、截断分布位置参数、原始均值、第一次 Floyd 后均值、闭包压缩率、首次 Floyd 改写弧比例、最终校准系数、最终均值及目标误差、最大 setup、上限命中率、三角违例数、审计 Floyd 改写弧数，以及 family 在闭包前后和最终矩阵中的类间/类内均值比。

### 1.4 时间尺度

纯调度实验使用原始、中等放大和高放大三个尺度。对每个规模用固定种子生成 5 个中等倍率 `g_L in [5,15]`，并令 `g_H=g_L+10 in [15,25]`。同一源任务集合的所有算法、机器数、窗口和 setup 结构共用相同倍率。

放大时 processing time、due-window center、窗口半宽、setup time 及其他时间量统一乘以 g，TWET 单位时间权重不变，setup cost 重新按放大后的 `20s_ij` 计算。W0 放大后仍为 0；W100/W300 表示原尺度半宽，写入放大文件时同步变成 `100g/300g`。

时间尺度不再是 solver 参数。所有放大实例必须在生成实验包时写成独立 `.dat`，manifest 直接引用最终文件；runner 读取数据后不会再执行 `timeScale` 变换。

## 2. 实验一：无外包的三种 BPC 比较

本实验关闭外包，比较三种固定算法：`NG_DSSR`、`TIME_INDEXED` 和 `TIME_INDEXED_SRI`。compact CPLEX 不进入正式性能主矩阵，避免在明显超出其能力的时间域重复超时。

三种算法完整交叉 5 个规模、每规模 5 个任务集合、3 个窗口、2 类 setup、3 个机器数和 3 个时间尺度：

\[
5\times5\times3\times2\times3\times3\times3=4{,}050
\]

次正式求解。每一个 `instance/setup/W/m/scale` 场景先用 3 个预先固定、仅由场景 ID 和重复编号生成的随机数种子独立运行初始 ALNS。每次最多 60 秒，按真实 incumbent 成本选择最好的一次；目标相同时固定选择重复编号较小者。只保存获胜 run 的完整 `FixedInitialColumnSeed`，不把三个 run 的列集合并，否则会改变初始 RMP 大小。该快照包含进入初始 RMP 的全部列序列，以及获胜 incumbent 使用的机器序列；这里的 `FixedInitialColumnSeed` 是固定初始列快照，随机数 seed 则是三次 ALNS 的随机流起点，两者不能混称。

三种 BPC 随后读取同一个快照，并用当前实例重新评价列成本。SHA-256 fingerprint 用于确认三个 run 读到的序列快照完全相同。seed 生成文件记录三次随机数 seed、各自 incumbent 成本、实际用时、初始列数、incumbent 列数和 fingerprint，以及最终获胜编号和总生成时间。最多前处理时间为 `3*60=180` 秒；这部分只生成一次并被三种算法共用，单独报告，不计入任何一种 BPC 的求解时间。这样算法间差异不会来自 ALNS 墙钟停止或随机轨迹造成的不同起点。

NG_DSSR 固定保留完整 time-indexed root preprocessing，因此论文中应把它明确写成该方法的组成部分，而不是把结果解释为纯 ng-DSSR。

本节首先报告 solved count、总时间、最终 gap、root bound/gap、节点数、列数、cut 数、master LP、pricing、cut separation、strong branching 和 repair 时间。timeout 必须保留最终 incumbent、bound 和 gap，不能只统计成功实例。

root 下界保留现有两个正式口径即可。`rootBoundBeforeCuts` 是 root 的 exact pricing 已闭合、但尚未分离 cut 时的下界；`rootBound` 是 root 的全部 pricing/cut 循环结束后的最终下界。无 cut 方法通常两者相同，rank-1/SRI 方法的后者可能更强。NG_DSSR 启用 time-indexed root preprocessing 时，预处理先写回安全的时间窗和禁弧，再由 ng-DSSR 完成正式 root pricing，因此这里记录的 ng-DSSR root bound 是预处理后的正式 root 下界；临时预处理 LP 只用于缩域，只单独报告预处理耗时和状态。

time-indexed 额外报告 horizon、dense/active states、图节点与图弧、root compact-window、arc fixing 动作数以及真正新增的 `nodeTimeArcNewlyFixed`。NG_DSSR 额外报告 exact/heuristic pricing 时间、label 数、DSSR 轮数、completion-bound 构造与剪枝、midpoint probe、join、正反向扩展及正反不平衡。

本节总体比较 ng-DSSR 与 time-indexed 两类定价方式的适用范围，并分析任务规模、机器数、窗口宽度、setup 结构和时间尺度对求解效率的影响。rank-1/SRI 作为 time-indexed 的加强版本，用于判断更强 root/tree bound 能否抵消 cut 和带 cut pricing 的额外成本。

## 3. 实验二：两种外包表示的性能比较

外包实验只使用原时间尺度。BPC 内部机器调度统一使用 `NG_DSSR`，不根据实例临时切换。比较三种方法：compact CPLEX、外包集合也列化的 `columns` formulation，以及在 master 中显式保留外包和 tariff 变量的 `masterVariables` formulation。

此前暂定的任务标准报价量为

\[
q_j=\bar p\max\{w_j^E,w_j^T\}.
\]

该式量纲正确，但它使同一实例中加工时间为 1 和 100、权重相同的任务具有完全相同的外包报价。当前 Tanaka 40/50/100 样本的 processing time 实际范围正是 1--100，因此该式会把释放内部产能最多的长任务相对定价得过低，可能人为诱导长任务外包。正式生成建议改为

\[
q_j=p_j\max\{w_j^E,w_j^T\}.
\]

其中 `p_j` 反映外部加工 workload，`max` 表示外部承运商按任务较严格的一侧服务代价报价。使用 `max` 本身可以解释为保守的服务等级价格，但它会使高 TWET 权重同时提高内部违约成本和外包报价，因此不能把“高权重任务更容易外包”预设为结论。如果不希望外包商报价依赖企业内部惩罚权重，更中性的备选才是 `q_j=p_j*w_ref`，其中 `w_ref` 是跨任务固定的代表性权重。当前主方案采用 `p_j*max`，同时在论文中说明上述业务含义。

令任务的未折扣外包支付为 `b_j(lambda)=lambda*q_j`。如果任务在 due window 的某一侧偏离 `delta`，该侧单位惩罚为 `w_j^x`，忽略 setup 节省以及对其他任务的连锁影响时，外包比内部违约更便宜的近似条件为

\[
\delta>
\lambda p_j\frac{\max\{w_j^E,w_j^T\}}{w_j^x}.
\]

当违约发生在权重较大的一侧时，阈值简化为 `delta>lambda*p_j`。因此 `lambda=0.5/1/2` 可分别解释为：只有偏离约半个、一个或两个 processing time 后，单任务直接违约成本才超过外包报价；`lambda=0.5` 并不表示任务只要越窗就必然外包。若违约发生在权重较小的一侧，阈值更高。真实最优决策还会同时考虑移除任务后节省的 setup、对其他任务完成时间的影响和数量折扣，因此该关系只是价格档的标度解释，不是逐任务判定规则。

Dabia、Lai 和 Vigo（2019）的设置与此不同。其 tariff 直接作用于所有外包客户的总物理 demand，不为单个客户随机生成报价，也不把外包费率与客户时间窗、私人路线成本或惩罚权重用公式关联。作者按空间类别人为指定三套确定性费率：R 为 `5/4.5/4/3.5`，RC 为 `3.5/3/2.5/2`，C 为 `2/1.5/1/0.5`，统一使用绝对 demand 区间 `0--200/200--400/400--600/>=600`，理由仅是客户越随机分散，承运商报价越高，并未通过 pilot 把外包比例调到均衡。我们的 `p_j*max` 因而不是对该文 demand tariff 的直接复制，而是一种调度特定的“加工量乘服务重要性”报价。它可以保留，但论文必须明确假设 `w_j^E,w_j^T` 同时反映任务对外部服务等级的要求；如果这些权重只表示企业内部会计惩罚，则该报价机制的业务解释会变弱。

调度文献能够直接支持的是报价随外部加工量增加，而不是 `max` 这一具体权重组合。Qi（2009）的 *Two-stage production scheduling with an option of outsourcing from a remote supplier* 和 Lee 与 Choi（2011）的 *Two-stage production scheduling with an outsourcing option* 均采用按外包 processing time 计费的基本结构；Kim、Lee 和 Wang（2022）的 *Scheduling of two-machine flowshop with outsourcing lead-time* 也把这一类与外包加工时间成比例的模型作为直接相关基础。Mokhtari 和 Nakhai Kamal Abadi（2013）则说明调度模型也可以允许 job/subcontractor-dependent 的一般外包成本。本文据此以 `p_j` 作为外包报价的加工量基数，再乘 `max{w_j^E,w_j^T}` 表示任务要求较严格一侧的服务重要性。前半部分有既有文献依据，后半部分是本文为当前 TWET 场景规定的实例生成规则，论文不能把完整公式误写成直接照搬某篇文献。

当前正式口径就冻结为 `q_j=p_j*max{w_j^E,w_j^T}`、`b_j(lambda)=lambda*q_j` 和 `lambda=0.5/1/2`，不再把纯加工量报价或其他报价公式加入正式实验维度。论文中的准确表述应为“参考既有调度外包研究按加工时间计费的做法，以 processing time 为报价基数，并结合本问题的服务重要性构造任务报价”，而不是声称既有文献采用了同一个 `max` 公式。

现有研究中的“倍率”也没有统一标准。Lee 和 Choi（2011）使用 stage-specific 常数 `alpha_i`，目标中的外包项为 `alpha_i*sum p_ij`，主要按 `alpha_i` 相对单位调度时间成本的区间讨论复杂性，并非通过样本校准一个公认市场倍率。采用 job-dependent 成本的计算论文往往根本不保持与加工时间成比例：Lee 和 Sung（2008）的基准中 `p_j~U[1,10]`、`o_j~U[1,30]`，并进一步比较 `o_j~U[1,10]/U[10,20]/U[20,30]`；Kim、Lee 和 Wang（2022）的基准中 `p_j~U[1,30]`、`o_j~U[1,10]`，并比较 `o_j~U[10,30]/U[20,40]/U[30,50]`。Safarzadeh 和 Kianfar（2019）先独立生成 operation outsourcing cost，再为不同 problem class 通过预实验选择目标函数中的外包成本权重，使结果形成低、中、高外包率；其权重按规模变化，约在 `0.005--0.35`，不是统一倍率。因此文献真正提供的是“按加工量计费”或“通过价格/权重档覆盖不同外包率”两种实验范式，而不是一个可以直接照搬的数值。本文的 `lambda=0.5/1/2` 应依靠前述 break-even 含义解释，并在正式结果中检查是否确实产生低、中、高且非退化的外包水平，而不能声称这些数值来自某篇文献。

在正式 n50 样本上计算 `Q_all=sum_j q_j` 的中位数 `Q50_ref`，只校准一次绝对断点

\[
Q_1=0.25Q_{50}^{ref},\qquad Q_2=0.50Q_{50}^{ref}.
\]

断点随后跨规模、机器数、窗口和价格保持不变。价格档为 `lambda=0.5/1/2`，默认采用连续 incremental discount，三段边际费率为 `(1,0.85,0.70)`：

\[
G_\lambda(B)=\lambda\left[\min(B,Q_1)+0.85\min((B-Q_1)^+,Q_2-Q_1)+0.70(B-Q_2)^+\right].
\]

外包性能实验沿用实验一的全部基础环境，只删除时间尺度维度并固定为原始尺度，再用三个外包价格替换三个时间尺度。也就是说，5 个规模、每规模 5 个任务集合、3 个窗口、2 类 setup、3 个机器数、3 个价格和3种方法全部配对：

\[
5\times5\times3\times2\times3\times3\times3=4{,}050
\]

次正式求解。这个口径使外包与无外包在原始时间尺度下拥有完全相同的 `instance/m/W/setup` 场景，也能直接比较加入外包后问题变容易还是变困难。计算量较大，但不再通过删掉 W0、机器档或大规模价格档破坏配对。

外包场景同样先运行三随机种子的初始 ALNS，并让 compact、`columns` 和 `masterVariables` 共享获胜方案。V2 快照同时保存内部机器序列和获胜 incumbent 的外包任务集合；恢复时按目标场景的 `q_j` 和 tariff 函数重新计算外包支付。`columns` formulation 据此加入对应外包集合 seed 列，`masterVariables` formulation 据此恢复同一个 incumbent 外包向量。恢复入口还会检查内部序列与外包集合是否恰好覆盖全部任务，避免列集合与 UB 不一致。

本节除通用 BPC 指标外，还报告内部 pricing 与外包 pricing 时间、内部列和外包列数量、RMP 迭代、Phase-I repair、分支类型、外包任务比例、物理外包 workload 比例、标准报价量比例、实际支付、折扣节省和成本分解。物理 workload 为 `sum_{j in O} p_j`，表示外包释放了多少内部加工时间；标准报价量为 `sum_{j in O} q_j`，是 tariff 函数的输入。两者不能混用：相同 processing time 的两个任务释放相同产能，但若服务权重不同，其标准报价贡献可以不同。主要判断 `columns` 与 `masterVariables` 的效率是否随规模和外包率变化，并观察允许外包后问题是因为内部任务减少而变容易，还是因额外变量、tariff 与分支结构变困难，或者在中等外包率附近最难。后续管理分析固定使用整体更稳定的一个 BPC formulation。

## 4. 实验三：允许外包的价值及价格、产能和窗口效应

本节原则上不新增算法方法，只复用实验一和实验二中同源、原时间尺度的解。对于同一个任务集合、m、W 和 setup，比较禁止外包与允许外包。低/中/高价格用于观察外包响应曲线，机器数表示内部产能背景，W 表示 due-window 压力，random/family 表示 setup 的结构形态。

分析分为四层。成本层报告 earliness、tardiness、setup、外包支付和总成本；服务层报告早到、窗内和迟到任务比例；决策层报告外包任务数、外包 workload/标准报价量、机器负荷和 tariff 分段；结构层比较外包前后的内部相邻弧、平均 setup、机器序列和拥挤时段。

本节重点不是重复“外包越便宜，外包越多”这一显然趋势，而是检验不同生产环境对价格变化的响应是否不同，并判断外包是否会移除 due-window 不协调、高 setup burden 或高 TWET burden 的任务，使剩余内部序列更连贯。任务特征只做探索性后处理，只有跨实例、价格和环境稳定出现的规律才写成一般性管理结论。

由于实验二与实验一的原尺度场景完整配对，本节可以在全部五个规模、三个机器档、三个窗口和两类 setup 上分析允许外包的价值及价格响应。不过管理结论仍应按规模分层，不能把同一任务集合在不同 m/W 下的重复观察当作独立样本。

## 5. 实验四：有无数量折扣

本节固定 n50、原时间尺度、中等价格 `lambda=1` 和实验二选出的 BPC formulation，比较无折扣 `(1,1,1)` 与默认折扣 `(1,0.85,0.70)`。断点均使用统一的 `Q1/Q2`，不按实例重新计算。

与最新“每格 5 个实例”的计算预算保持一致时，使用实验一和实验二中的同一批 5 个 n50 任务集合，完整交叉 m2/m3/m4、W0/W100/W300 和 random/family，共 90 个环境、180 个有/无折扣结果。实验二已经包含全部 90 个中等价格默认折扣结果，因此只需新增 90 个无折扣求解。

早期文档曾规定使用 20 个 n50 源实例，对应 360 个环境和 720 个有/无折扣结果。该版本与后来为控制总计算量采用的每格 5 个实例不一致。当前按 5 个执行，总体口径与两个性能实验一致；若以后增加到20个，应作为管理分析样本扩充，而不能反向改变已经预注册的算法性能矩阵。

本节报告外包集合 Jaccard、外包任务数和报价量、跨越 Q1/Q2 的实例数、折扣节省、内部成本和机器序列变化。需要区分两种机制：折扣是否只降低原本就会外包的任务支付，还是使一组具有相近 due-window 或共同 setup 结构的任务跨过断点并共同外包。

## 6. 正确性验证、运行方式和输出

小规模 compact/columns/masterVariables 对拍属于正式长跑前的正确性验证，不作为论文性能主表。建议在 n8/n10/n12 上验证三种模型的最优目标、调度、外包集合、成本分解和 validator 一致；其数量不进入两组 4,050 次性能实验和90次折扣增量。

每次正式求解固定 CPLEX 单线程、时限 10,800 秒、最大节点数 100,000。批处理由 scheduler 同时维持 4 个独立子 JVM；任一任务结束后立即启动下一个依赖已满足的任务。每个场景先生成并落盘共享 seed，然后算法任务读取同一个 seed。NG_DSSR 保留 time-indexed root preprocessing；三种 BPC 的其余参数由 `BestBpcProfiles` 固定，结果记录 profile version。

当前实际执行不是“每个 BPC 自己检查本地 seed，不存在就自动跑 ALNS”，而是 manifest 把每个场景拆成一个独立 seed 任务和若干依赖它的 solve 任务。通过 `ExperimentBatchScheduler` 运行时，seed 任务输出目录若已有 `SUCCESS` 标记，该任务被视为完成并跳过；否则启动 `FormalExperimentRunner --action=seed`，重新加载同一场景三次，使用三个确定随机流各运行一次最多 60 秒的 ALNS，按真实 incumbent 成本选择最好者并写入唯一 V2 快照。seed 子进程正常退出后，scheduler 写入 `SUCCESS`，随后才允许依赖该任务的 BPC 子进程启动。各 BPC 使用 `--action=solve` 直接读取同一快照，不再运行 ALNS；快照缺失或损坏时 solve 直接失败，不会自行补生成。

以一个具体场景为例，实际时序只有两段。第一段先把同一个落盘 `.dat` 读取三次，分别运行 repetition 0、1、2 的 ALNS；三次之间不传递列，也不合并列池，只比较最终可行 incumbent 的真实目标值，并把最好一次的初始 RMP 列、incumbent 内部机器序列和外包集合写成一个 `.seed` 文件。第二段才分别启动待比较的方法：纯调度时为 NG_DSSR、TIME_INDEXED 和 TIME_INDEXED_SRI，外包性能实验时为 compact、columns 和 masterVariables。它们彼此独立，不是先运行 NG_DSSR 再把结果交给 time-indexed；每一种方法都从同一个 `.seed` 文件重新建立自己的求解过程，并写入各自结果目录。三次 ALNS 的时间单列为共享起点生成时间，不计入任何一种方法的 BPC 求解时间。

续跑时也按这个边界处理：若 seed 任务已有 `SUCCESS`，三次 ALNS 不再运行；某个算法任务已有自己的 `SUCCESS`，该算法也不再运行；只有尚未成功的算法任务会继续使用原来的共享 `.seed` 启动。因此断点续跑不会为不同算法重新生成不同初始解。

manifest 是批处理任务清单，不是算例数据，也不是求解器本身。TSV 固定包含六列：`runId` 是任务唯一编号；`mainClass` 是子 JVM 入口，当前统一为 `HEU.FormalExperimentRunner`；`args` 保存该入口所需的完整参数，例如 `action`、实例路径、算法、共享 seed 路径、输出目录、时限和外包设置；`outputDir` 是该任务自己的日志与结果目录；`dependsOn` 是逗号分隔的前置任务 ID；`block` 只用于生成不同实验小节的子 manifest，scheduler 本身不依赖该列做求解决策。manifest 不保存 ALNS 随机数、初始列内容、求解过程或最终结果，这些分别由 seed metadata、`.seed` 快照和各任务输出目录保存。

生成器为每个具体场景写一条 `action=seed` 行和若干条 `action=solve` 行。seed 行的 `dependsOn` 为空；同一场景的所有 solve 行都把该 seed 行的 `runId` 写入 `dependsOn`。文件中通常把 seed 行放在其 solve 行之前以便人工阅读，但真正保证顺序的是依赖关系，不是文本行号。scheduler 启动后一次性读取全部行，检查必需列、重复 `runId`、未知依赖和循环依赖，然后维护 pending、running、successful 和 failed 四类状态。最多同时启动 4 个独立子 JVM：没有依赖的 seed 任务可以直接运行；solve 任务只有在其 seed 成功或因已有 `SUCCESS` 被跳过后才会启动；seed 失败时相应 solve 被标记为 `BLOCKED`。scheduler 只负责组织任务，不读取算法目标值，也不会在算法之间传递结果。

每个实际启动的任务先在自己的输出目录写 `args.txt` 和 `status.txt`，再组装 `java -cp ... HEU.FormalExperimentRunner ...` 命令；子进程的标准输出和错误分别重定向到 `stdout.log` 和 `stderr.log`。子进程返回 0 时写入 `SUCCESS` 并标记 `SUCCEEDED`，非零时标记 `FAILED`。再次运行同一 manifest 时，已有 `SUCCESS` 的任务记为 `SKIPPED` 并被视为依赖成功，因此可以继续调度尚未完成的后继任务。某个任务结束后，scheduler 立即用空出的并发槽扫描并启动新的就绪任务，直至 manifest 中全部任务成功、跳过、失败或因依赖失败而阻塞。

这里还有两个不同含义的 seed。随机 seed 是 ALNS 的随机流起点，当前不是手工列出三组固定整数，而是用场景 `runId` 确定性生成。设固定初值 `offset=0xcbf29ce484222325`、乘数 `prime=0x100000001b3`，先计算 `value=offset XOR salt`，再按 `runId` 字符顺序反复执行 `value=(value XOR char)*prime`，最后返回

```
value XOR (0x9e3779b97f4a7c15 * (repetition + 1))
```

其中 repetition 固定为 `0/1/2`。每次 repetition 同时建立两条独立随机流：`EngineALNS` 使用 salt `0x41c64e6d`，`Utility` 使用 salt `0x9e3779b9`。因此同一个场景重跑时三组数值完全一致，不同场景因 `runId` 不同而得到不同数值，ALNS 主搜索和其他随机操作也不会共用同一个 `Random` 状态。实际数值及三次目标、时间和获胜编号均写入 seed metadata。最终共享的 `FixedInitialColumnSeed` 则不是随机数，而是三次 ALNS 中成本最好者的初始列、incumbent 机器序列和外包集合快照。三次列池不合并，三种 BPC 只共享这个获胜快照。

这里的 salt 只是生成随机种子时加入的固定“流标签”。如果只对 `runId+repetition` 做一次哈希，再把同一个结果同时交给 `EngineALNS` 和 `Utility`，两条随机流会从完全相同的内部状态开始，产生人为相关的随机序列。两个不同 salt 使相同场景和 repetition 映射为两个不同的 long seed，从而把 ALNS 主搜索与其他随机操作分开。salt 的十六进制常数本身没有业务含义，也不是经过算例调优得到的参数；换成其他固定且不同的非零常数同样可行。当前值一旦用于正式实验就必须保持不变，因为修改 salt 会改变全部 ALNS 轨迹和共享初始列。该哈希只服务于可复现和随机流分离，不用于密码学安全，也不表示某组种子比另一组更优。

恢复已有实验时，scheduler 当前检查的是 seed 任务目录中的 `SUCCESS`，而不是同时验证 `.seed` 文件。正常成套保存时两者一致；如果人工删除或损坏 seed 文件但保留 `SUCCESS`，scheduler 会跳过 seed 生成，后续 solve 才在读取快照时失败。反过来，若 `.seed` 文件存在但 `SUCCESS` 缺失，seed 任务会重新执行三次 ALNS并覆盖快照。因此正式迁移和续跑必须把 seed 文件、对应 seed 任务输出目录及其 `SUCCESS/run.properties` 一起保留；后续可以再把“跳过前同时校验快照存在及 fingerprint”作为调度器稳健性修复，但这不影响当前全新正式批次的正常流程。

求解过程写入 `live.log`、`stdout.log`、`stderr.log` 和 `status.txt`。结束后输出 `core-summary.csv`、`components.csv`、`nodes.csv`、`columns.csv`、`pool-summary.csv`、`pool-columns.csv`、`cuts.csv`、`outsourcing.csv`、`incumbent-schedule.csv`、配置快照和 Markdown 摘要。实时日志只在阶段边界更新，高频 label/arc/PWLF 诊断默认关闭；完整列池和调度表在求解结束后生成，不进入算法热路径。

## 7. 当前实现状态

当前 `experiment-suite/formal-v1` 仍是基础设施 pilot，不是上述正式矩阵。它包含 243 个 seed 任务和 945 个 solve 任务：pricing comparison 729、outsourcing formulation 54、outsourcing price 81、outsourcing discount 81。其规模为 n40/n50/n60、每格 3 个文件，窗口仍按 `0/2/6*平均处理时间`，时间尺度仍为固定 1/5/10，setup cost 和外包经济参数也是旧占位口径。

当前 pilot 已完成时间尺度落盘：5/10 倍 processing、due date 和 setup 已写入独立 `.dat`，runner 不再接受 `timeScale`。`FormalExperimentRunner` 的 seed action 已固定运行 3 次最多 60 秒的独立 ALNS，每次重新加载 Data 并分别重置 ALNS 与 Utility 随机流，按真实 incumbent 成本择优且只保存获胜 run。`FixedInitialColumnSeed` 已升级为 V2，除内部列外保存 incumbent 的外包任务集合；恢复时按目标场景重新计算 baseline 与 tariff，V1 无外包快照仍可读取。求解结束后的 `outsourcing.csv` 已同时输出外包任务比例、物理 processing workload、标准报价量比例、实际外包支付及逐任务的 processing、窗口和权重信息。

尚未完成的是正式的 5 个规模、5 个源集合、W0/W100/W300、random/family、实例级 `[5,15]/[15,25]` 倍率、`q_j=p_j max{w_j^E,w_j^T}` 以及跨规模固定绝对断点的最终生成器。因此当前代码可以验证共享 seed、V2 外包恢复、日志和调度器，正式长跑仍需先完成并冻结最终数据生成。
