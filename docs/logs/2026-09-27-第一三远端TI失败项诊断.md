# 第一、第三远端 TI/TI+SRI 失败项诊断

2026-09-27 对第一台 Arc TI/TI+SRI 和第三台 Cluster TI/TI+SRI 正式批次做了只读复核。两台调度器均已结束，第一台 2160 项中 2158 项成功、2 项失败，第三台 2160 项中 2156 项成功、4 项失败。这里的成功是存在正式 `SUCCESS` 标记，既包括证明最优，也包括具有可报告状态和界的正常限时结果；下述 6 项是子 JVM 异常退出，不应与普通超时混合统计。

## 1. 第一台的两个确定性代码边界

### 1.1 MachineCountBrancher 生成矛盾机器区间

失败项为 `n060-set01/m2/family/base/zero/F=3/TI`。日志显示节点 102 的继承机器区间为 `[0,2]`，当前解仍触发机器数分支；随后生成的节点 103 却为 `machine=[3,2]`。CPLEX 在构造 `machineCount` range 时因此报告 `IloRange has incompatible bounds`，正式求解以 `FAILED` 结束。失败前已有 incumbent `119150.0` 和 bound `110954.06286776514`，但该项不能视为正常限时结果。

根因在 `MachineCountBrancher`：旧代码直接把左支上界写成 `floor(machineUsage)`，把右支下界写成 `ceil(machineUsage)`，没有与父节点现有 `[min,max]` 区间取交，也没有拒绝 `newMin > newMax` 的空子节点。该例很可能是机器数在上界 2 附近的数值偏差超过分支容差，导致 `ceil(machineUsage)=3`；无论偏差来源如何，分支器都不应把 `[3,2]` 传给 LP。

2026-09-27 已做最小修复：先把 LP 机器使用量贴回父节点区间，再判断其是否为整数；真正需要分支时，左右 child 的新边界与父区间取交，并保留空区间防御检查。`BranchResult.none()` 在 `Tree` 中只会拒绝当前机器数候选并继续后续分支器，不会关闭父节点。定向测试覆盖上界 `2.0000001`、下界 `-0.0000001` 和正常分数值 `1.4`，均通过；正常值仍生成 `[0,1]` 与 `[2,2]` 两个 child。

### 1.2 strong trial 筛列后没有重新验证 seed 可行性

失败项为 `n060-set01/m2/random/medium/narrow/TI`。节点 6 的 strong trial 对候选两侧都得到可行 RMP，消息为 `lightweight_rmp_trial_seed_filtered_no_resolve`。trial 随后按 reduced cost 把 child seed 筛到 53 列，但没有在筛列后重解；节点 7 用这 53 列构造正式 RMP 后立即不可行。由于节点带有 `strongBranchingSeedPrepared=true`，`PC.solve()`没有进入现有 Phase-I repair，而是直接抛出 `Prepared strong branching child is infeasible on formal solve`。

定向诊断已经在相同节点两次稳定复现，并排除了普通筛列删坏正值支持的解释。prepared child 进入诊断 Phase-I 后，唯一正人工量为 `machineSlack_ub=2.03207767314e-07`。`LP.VALUE_TOLERANCE` 虽声明为 `1e-8`，但 `isNoSlack()` 调用 `Utility.compareGt(value, VALUE_TOLERANCE)`；该函数内部又叠加全局 `EPS=1e-6`，实际只有 `value>1.01e-6` 才被视为正值。因此上述 `2.03e-7` 残量被错误判成0，Phase-I提前结束，移除人工变量后真实成本 RMP 仍不可行。

第二项已采用最小正式修复：让 Phase-I 判零直接使用本类声明的精确阈值，`isNoSlack()`改为 `value > VALUE_TOLERANCE`；同类的 `branchImpliedPenaltyValue()`也采用相同直接比较。全局 `Utility.EPS`未修改，repair、pricing、真实RMP重建和不可行证书流程均未改变。修复后，处于 `[1e-8,1.01e-6]` 的人工残量会继续触发现有 Phase-I 定价，直至真正降到 `1e-8` 以下或exact repair证明节点不可行；最终真实成本RMP重建仍作为一致性检查。

不能用把全局 `Utility.EPS` 从 `1e-6` 缩到 `1e-8` 的方式修这一处问题。当前 `compare*` 在73个源码文件中约有1577处调用，同时承担PWLF端点衔接、函数占优、时间窗边界、整数性识别、reduced-cost闭合和候选去重等语义。全局缩小容差可能使接近整数的CPLEX值被误判为分数、微小PWLF端点误差形成裂缝或额外分段，并令dominance保留更多近重复状态。这里的错误不是全局容差取值错误，而是调用方已经声明`VALUE_TOLERANCE=1e-8`后又使用会额外叠加`EPS`的比较函数；因此应只修局部阈值比较。

不应在“Phase-I声称归零，但恢复真实目标后RMP仍不可行”时直接剪掉节点。该状态只证明当前restricted columns仍不足，并不是完整列空间不可行证书。现有`repairMasterPhaseOne()`已经具有正确的剪枝路径：人工量仍为正、且内部与列化外包exact pricing在同一dual下全部闭合时，才返回`INFEASIBLE`。最小安全修复仍是让人工量判定真正使用`VALUE_TOLERANCE`，使该残量继续走现有Phase-I循环；最终真实RMP仍不可行应保留为不变量异常，不能静默剪枝。

## 2. 第三台的四项底层执行异常

第三台四项不呈现为普通模型不可行或求解器状态失败，而是 JVM/原生进程异常：

1. `n060-set02/m4/family/high/narrow/F=3/TI`：HotSpot `EXCEPTION_ACCESS_VIOLATION (0xc0000005)`，运行约 9687 秒后在 `java.util.ArrayList.add` 的 `aastore` 路径崩溃。
2. `n040-set02/m2/family/high/wide/TI`：同样的 `EXCEPTION_ACCESS_VIOLATION`，运行约 7648 秒后在相同 `ArrayList.add/aastore` 路径崩溃。
3. `n050-set01/m2/family/base/zero/F=3/TI+SRI`：Java 层出现 `ArrayStoreException`，栈顶同样是 `ArrayList.add`，调用位置为 rank-1 pricing 的 `insertPreparedPackedLabel()`。
4. `n060-set05/m4/random/high/wide/TI`：进程以 Windows `0xC0000374` 退出，即原生 heap corruption，没有正常 Java 异常和正式求解收尾。

普通 `ArrayList` 的 backing array 是 `Object[]`，项目也没有使用 `Unsafe`、`VarHandle` 或反射替换 `elementData`；因此任意 `Label` 在正常 JVM 语义下不应使 `ArrayList.add()`抛 `ArrayStoreException`。该异常与同一主机两次在相同 `aastore` 位置发生的 native access violation、另一次原生堆损坏相互印证，更符合 JVM/JIT、内存或 CPU 稳定性问题，而不是 rank-1 label 类型设计错误。第三台为 i9-14900K、Oracle JDK 21.0.7，崩溃时仍有大量可用物理内存，也不支持普通 Java heap OOM 的解释。

当前证据只能把第三台四项归为平台级异常，不能仅凭日志在 JDK、CPU、内存或持续并发负载之间进一步定责。正式实验中应把它们单列为 execution failure，并在稳定环境或单并发下重跑；不能把它们计为 TI/TI+SRI 超时，也不能据此评价算法性能。

## 3. 当前结论

第一项已完成最小修复和定向测试。第二项已通过只在异常条件下启用的诊断 Phase-I 定位为局部判零阈值错误，并完成两行局部阈值修复；临时诊断开关与slack打印已经撤掉，prepared child的正式fail-fast一致性检查保留。主线232个源文件干净编译通过，机器数边界、after-cut Phase-I、strong-branching Phase-I和正式配置四项回归均通过。第三台四项属于一致的底层执行异常链，优先采用稳定性检查与重跑，不应先修改定价算法。两类失败的性质不同，后续结果汇总必须分别标记。
