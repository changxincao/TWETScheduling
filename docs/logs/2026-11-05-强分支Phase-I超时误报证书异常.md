## 日志与调用链

stderr在PC.repairMasterPhaseOne:1267抛出异常，调用链来自repairStrongBranchingPhaseOne、solveStrongBranchingRmpTrial、Tree.tryTwoStageStrongBranching。现场为试算节点id=368、depth=13，internalClosed=false、outsourcingClosed=true。

从远端live.log提取到唯一一条time_limit定价返回：`Pricing[GCNGBBStyleNgDssrPricing[FindFeasible]] node=368 improved=false addedColumns=0 ... time=61858.518 ms ... generated 0 columns (time limit reached)`，同条附录明确`ng-DSSR reason=time limit reached, pricingCall=3832, nodePricingCall=27, repairPricing=true ... rounds=33`。这说明该次修复定价执行33轮DSSR、累计约61.86秒后被全局时限打断；不能把返回0列解释为“穷尽搜索且没有修复列”。stdout最后仍是该次DSSR第33轮收尾，没有正常formalRun finished行。

具体顺序如下：

1. repairMasterPhaseOne的循环入口尚未超时，开始修复定价。
2. generateColumnsFromEngine在定价返回后检查到时限（PC:1493），记录time_limit并返回空GeneratedColumnIds；它在该分支不会调用observeCertifiedReducedCosts，因此没有非负reduced-cost证书。这一行为正确：中断搜索不能伪造完整证书。
3. repairMasterPhaseOne看到generated.isEmpty后退出内层循环；后续engine因时限不再运行。repairPending仍为true，本轮没有加列，internalClosed仍false。
4. PC:1260先进入`if (!addedInThisPass)`，将“无新增列且缺证书”视为契约错误并抛异常。它没有先判断无新增列是否由正常超时导致。
5. finally仍会清理repair模式，但异常跳过其后PC:1279已有的超时返回。solveStrongBranchingRmpTrial在修复调用后的超时处理（约PC:475）和Tree已有的hasTimeLimitedTrial收尾也因此无法执行，最终调度器记录FAILED。

outsourcingClosed=true在本例仅表示未启用列化外包，不需要外包定价证书；本例run.properties明确outsourcingModel=not-applicable，不能据异常文字推断跑了外包。

## 最小修复方向与影响范围

应让正常超时优先于“无列且缺证书”的契约检查：每轮engine循环返回后，先检查isTimeLimitReached并退出Phase-I循环，继续走已有finally清理和超时返回；上层已有StrongBranchingTrialResult的timeLimited及Tree正常TIME_LIMIT收尾可承接。非超时且搜索确已结束却没有证书的情况仍须报错，不能全局捕获吞异常，也不能直接把试算节点判不可行或删除。

这项缺陷将特定超时运行误分类并阻断最终结果写出，不是一次错误的不可行剪枝；本次现场没有把缺证书当作可用下界继续搜索。此前正常完成的结果不因这个退出分支自动失效。本项最后完整节点367报告UB=9961、bound=9662.311828、gap约2.9986%，只能作为此前合法快照，不冒充异常时的最终summary。
