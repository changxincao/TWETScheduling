# 60-3 W100 ng-DSSR 慢点与 subtree elimination 分析

## 结论

`wet060_001_3m`、W100、同 fixed seed 的 ng-DSSR 求解用时 3972.082s。`subtree arc elimination`
自身并不是直接热点：178 次调用只耗时 1.430s。但本次配置同时打开 hard subtree 和 pricing-only
subtree，而 `Tree.applySubtreeArcElimination()` 中 hard 模式优先，因此实际会把固定弧写入子节点
`arcState`，pricing-only 开关在这里没有生效。

hard subtree 的间接代价很大。每次 RMP 重建时，`LP.buildArcBranchConstraints()` 会为每条
required/forbidden arc 建一行，并逐行扫描全部 restricted columns。ng-DSSR exact 日志中的
`arcForbid` 平均为 240.1、最大为 456；strong branching 共执行 7120 次 trial RMP，平均每个 trial
有 3372.9 条 restricted columns。对应 strong-trial model build 累计 617.484s，平均 86.725ms；
作为参照，严格同 seed 的 time-indexed no-cut 为 108.539s/11520 次，平均 9.422ms。两种算法的
列结构和树不同，不能把全部差值严格归因于 subtree，但代码复杂度、arc 行数量和实测 build
差异共同说明 hard subtree 是本次 ng-DSSR master 侧的重要放大器。

## 总时间拆分

3972.082s 中最主要的三项为：

1. Heuristic pricing：1526.966s/5314 次，占 38.4%。其中 2898 次成功、2416 次失败，共加入
   67962 条列。每次失败后进入 exact，失败次数与 exact 调用次数恰好同为 2416。
2. ng-DSSR exact pricing：1307.227s/2416 次，占 32.9%，共加入 154768 条列。2223 次找到负列，
   193 次完成闭合。
3. Master LP：约 1015s，占 25.6%。其中 strong-trial RMP 为 946.440s/7120 次；178 次正式分支
   每次测试 20 个候选的左右两侧，正好形成 178×20×2=7120 次 trial。

三项合计已经解释约 96.9% 的总时间。root 只耗时 65.197s，真正的退化发生在 root 以后。

## exact pricing 内部

2416 次 exact 共执行 3938 轮 DSSR，平均 1.63 轮，最大 6 轮。轮数频率为：
1轮 1374 次、2轮 688 次、3轮 248 次、4轮 89 次、5轮 14 次、6轮 3 次。因此本例不存在几十轮
或上百轮 DSSR 长尾，ng-set 更新不是首要原因。

exact 内部累计：

- completion bound：811.170s，约占 exact 的 62.1%；
- midpoint probe（包含最终被复用的 F/B 扩展）：440.253s，约占 33.7%；
- join：44.401s，约占 3.4%；
- probe 之外单独记录的 forward/backward 扩展合计仅约 2.773s。

所以当前 join、source-aware dominance graph 和 DSSR 轮数都不是这组数据的核心慢点。exact 的
核心是每次 dual 改变后重复构造 completion bound 和执行 midpoint labeling；整体流程的核心则是
heuristic/exact 交替产生大量列，再由强分支重复重建带大量 hard arc 行的 RMP。

## 当前判断

本次 `subtree arc elimination=1.430s` 只能说明判弧计算便宜，不能说明 hard 继承没有代价。
它的主要成本被计入后续 `master LP model build time`，而不是 subtree 计时。结合历史记录中 hard
subtree 会过滤 child 列、扰动 RMP/dual 并导致 residual graph 冷启动的结果，当前默认同时开启
hard 与 pricing-only 不是待验证的参数选择，而是已经确认的配置回归。2026-06-17 的严格对照已
证明主线应使用 `hard=false, pricingOnly=true`：hard 组为 `786.962s/117 nodes`，pricing-only
组为 `597.417s/149 nodes`；hard 虽少处理节点，但 exact、heuristic、master LP 和列池都更重。

## 配置回溯

这次没有只拿当前日志与近期“best”日志比较，因为近期日志继承了同一个错误。回溯结果如下。

1. `Tree.applySubtreeArcElimination()` 的实际优先级没有歧义：hard=true 时直接调用
   `applyTo()`；只有 hard=false 且 pricingOnly=true 时才调用 `applyToPricingOnly()`。两个开关
   同时为 true 并不是“同时应用两种 fixing”，而是只走 hard。
2. 2026-06-17 的专题记录已经明确禁止把两者同时打开，并把
   `hard=false, pricingOnly=true` 定为主线建议。历史诊断中 pricing-only 子节点为
   `forbidden/pricingOnly=1/1186`；误开 hard 后变为 `1187/0`，restricted columns 和定价轨迹
   随即改变。
3. 2026-07-24 的提交 `8c46b90c` 在整理默认配置时，把
   `bidirectionalCompletionBoundSubtreeArcElimination` 从 false 改成 true，同时也把
   pricing-only 改成 true。这一步与 6 月已经确认的结论冲突，是本次配置回归的来源。
4. 2026-07-26 的 `applyBestPricingModeDefaults()` 又把这组冲突值复制进 ng-DSSR profile。
   runner 后续读取系统属性时以 profile 当前值为默认，因此没有显式覆盖的启动都会继续得到
   hard=true、pricingOnly=true。
5. 7 月 14 日、7 月 24 日和当前 60-3 W100 的多批“best”日志均显示两个开关同时为 true。
   因此这些近期运行只能说明它们彼此配置一致，不能证明配置正确；此前按近期日志复核而判定
   “最好配置均已打开”的做法漏掉了同源默认值污染。

其余当前 ng-DSSR 核心参数逐项对照后与已记录结论一致：nearest 自动 `floor(n/10)`、C1000、
K20、`minimumNewPairsSegment`、source-aware dominance、group-envelope prefilter、
visit-profile pruning、allCycles completion bound、midpoint 总 pop 10000、time-indexed root
preprocessing 和 seed 200、strong phase2=0，以及关闭 RMIH、time-indexed pre-heuristic、dual
stabilization、warm-start 和 relaxed-column 返回。旧 midpoint 字段
`maxCandidates=5/moveRatio=0.15/timeTolerance=0.2` 虽仍出现在配置快照中，但当前 normal
ng-DSSR 固定 time-probe 不读取它们；这是配置表残留，不是本次性能错误。

当前 60-3 W100 日志关闭了 node-progress/heartbeat 等实时诊断，这不改变算法结果和耗时主线，
但不符合后续测试必须可实时监测的启动约定。当前只完成配置、代码和历史日志审计，没有重新运行
实验，也没有修改求解逻辑。正式修正应同时把全局默认和 ng-DSSR profile 改为
`hard=false, pricingOnly=true`，并拒绝两个开关同时为 true，避免再次静默退化为 hard 模式。
