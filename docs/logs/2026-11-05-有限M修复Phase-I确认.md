# 有限M修复的Phase-I确认

## 1. 修改范围

只修改`PC.java`的两个有限M修复出口：普通节点/strong trial的`repairInfeasibleMaster`，以及实验性全行`repairDomainFilteredStrongBranchingMaster`。原来正人工slack或正违规竞争列直接返回INFEASIBLE，现在转入已有通用Phase-I确认。M数值、默认profile、正常M修复成功路径、pricing算法、既有NG/after-cut Phase-I流程均未修改，远端未连接或更新。

确认时保留已有合法列和原来的人工行范围，使用零真实成本、单位人工成本；切换前后reset定价器，不沿用M目标的闭合证书。Phase-I归零后移除违规竞争列、恢复真实目标；普通修复再接回原来的seed筛选出口，domain路径仍由外层筛选。只有正人工残差与全部必要列族同dual精确闭合同时成立时才判不可行。M阶段或Phase-I阶段超时都沿已有超时出口返回，不转成不可行。缺失Phase-I闭合证书仍报契约错误，不静默丢弃节点。

顺带删除了两个旧出口专用、现在已经无读者的局部生成列计数；通用Phase-I的生成列计数和诊断保留。实现没有新增参数、目标惩罚策略或新的定价器。

## 2. 反例与回归

新增`src/TWETBPC/LP/FiniteMRepairConfirmationTest.java`，测试中生成完整两任务文件，由正式reader读取，列成本使用真实evaluator。有限M目标仍为2.5576718514、人工量为正，缺失singleton列的reduced cost为7.4423281486，TI返回闭合证书0。这证明反例机制没有因为改数据或列成本而消失。

同一测试只换回HEAD中的旧PC编译运行，完整树仍返回错误incumbent 50.005，触发预期失败；其余依赖和测试不变。新PC下TI及TI+SRI配置、默认M加确认及直接Phase-I共4次完整树都得到UB=LB=10，均3节点。该两任务反例未实际分离active SRI，带active SRI的目标和证书兼容由既有`StrongBranchingPhaseOnePricingTest`覆盖，不将配置名称等同于此反例实际加cut。

新增回归另外覆盖24个修复出口（TI/TI+SRI × 单分支行/全行 × 确认可行、确认不可行、M直接成功、M内超时、Phase-I内超时、缺失证书）、2个正式节点修复和1个纯调度正竞争列出口。真实不可行例禁止全部内部进入任务1的弧，剩余费率段也不能外包任务1，随后使用真实TI定价闭合。M成功例断言不调用Phase-I；超时例断言不关闭、不判不可行、不把repair结果复用入队，并清理模式开关。缺证书例断言拒绝判不可行。纯调度竞争列例先确认slack为0而竞争列为正，随后确认成功移除竞争列、保留合法列且全局Pool真实成本不变。

全行M在原反例上可能直接补列成功，因此测试对其确认出口确定性停止M阶段补列，不提供假闭合证书；纯调度竞争列出口同样采用该控制方式。这些是控制流覆盖，不是新增自然发生的有限M错误反例。超时和缺证书也使用确定性注入，不依赖wall-time波动。

共10个回归入口全部通过：新增测试、PhaseOneRepairTimeoutTest、AfterCutPhaseOneRepairTest、StrongBranchingPhaseOnePricingTest、LPRestrictedColumnMembershipTest、CertifiedNodeBoundTrackingTest、TreeFinalBoundTest、BestBpcProfilesTest、StructuredArcFlowBranchingTest、TimeIndexedGraphOptimizationTest。独立智能体静态复核未发现模式、缓存、证书、seed筛选衔接问题。结果在`docs/logs/data/20261105-finite-m-confirmation/`；编译和分阶段输出在`.codex-tmp/finite-m-confirmation/`。

## 3. 边界

本次确认并修复的是有限M正残差不能证明不可行的问题，不宣称所有输入已获正确性证明。未跑大规模性能实验；正常M成功路径不增加Phase-I，额外确认只发生在原正残差退出路径。未改ALNS、join缓存或其他已记录审查项，未更新远端及正式结果。
