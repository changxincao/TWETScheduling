# ALNS插入与停滞修复及n60对照

## 1. 修改范围与原因

本次只修复 `src/HEU/EngineALNS.java` 的两处已复现问题，不改VND邻域、接受规则、ALNS时限、扰动参数、正式profile、pricing或远端。修复前基线为当前工作区中这两处尚未修改的版本，HEAD为`0400b4b6eddc4fabfa0a1fa81a64e5bedc0f967e`；两组公共依赖保持相同。

1.1 插入评价原先构造原始前向函数后，调用`merge2Segments`，错误使用该函数尾值作为下界。现在仅在这个调用处直接使用既有`findMinimalShiftedSumValue`精确拼接，保留原有setup成本、时间平移和不可行/上界过滤。共用`merge2Segments`及其其他调用不动。后向函数已经包含等待的最小化语义，因此不额外构造前缀最小化函数；没有加入新的缓存或额外函数链。代价是以前被错误提前排除的位置现在会实际扫描，这是恢复正确评价，不承诺每次插入更快。

1.2 每轮破坏前保存全局最好目标值。修复及VND结束后，先按原规则保存候选中的新最好解，再将最终全局最好值与轮前快照比较。有实际改进才重置停滞、扰动放大计数和删除比例；无改进仍按旧流程累加。VND即时保存好解的行为不动；仅扩大扰动时仍不清零停滞。此改动每轮只增加一个标量快照，不复制解或扫描历史。

## 2. 正确性检查

新增`src/HEU/ALNSRepairRegressionTest.java`。原两任务外包反例中，旧版将真实0成本插入判为`1e10`，Greedy选择成本5的外包；新版插入为0，修复后无外包、总成本0。使用旧版class运行同一回归，确实在该断言失败，避免测试只验证新旧都能通过的情形。

独立整数时间DP对拍392个插入位置，覆盖空机器、首/中/末位置、不同有序子集、setup time/setup cost、纯调度及带外包数据，全部通过。四任务停滞反例关闭墙钟限制、停滞上限设1：新版第1轮改善后继续执行第2轮，第2轮抽取删除比例时上界为初始0.2；没有把VND改进误计为停滞。第2轮无改进之后正常停止，未改变停止语义。另通过既有`OutsourcingMoveConsistencyTest`的14,168项检查。

测试边界：补充构造中曾遇到硬窗仅在一个时间点接触的序列，旧完整PWLF评价也返回BigM，而独立DP存在有限成本；与此前组件审查记录的端点现象一致，本次没有修改或定性该公共函数语义，也没有将该构造计入上述通过数量。本次枚举对拍采用非退化窗口，已知两任务误剪反例仍单独保留。不能据此宣称所有硬窗边界均已验证。

## 3. n60实验口径

选6份正式纯调度输入，每份2个随机种子，共12组旧/新配对、24次ALNS。random来自`experiment-suite/formal/instances/data`；family来自`experiment-suite/family-count-balanced-20260914/instances/data`，F=3。选择在查看结果之前确定，不因结果更换输入。

两版采用`BestBpcProfiles.NG_DSSR`的seed配置：ALNS 60,000ms、连续无改进80轮、关闭SA、使用best历史、SegmentPool关闭。Utility随机种子为2026110501/2026110502，ALNS种子分别与`0x5DEECE66D`异或。每个配对核对起始机器序列完全一致。不是读取已有正式seed，也不覆盖正式seed；比较的是相同起点下的启发式输出，未运行B&P全树。

本机最多2个实际JVM同时运行，每个`-Xmx3g`。同一配对串行，两个种子反转旧/新执行顺序。沿用轮级软时限：一次VND跨过60秒仍完成当轮，因此实际耗时可能略超60秒；另有300秒外部保护，任何触发都应标成未完成，不当作正常结果。计时包含初始构造与ALNS，不含最终结果校验。保留墙钟、主线程CPU、轮数、最终目标及原始路线，输入和class的SHA-256见实验manifest。

当前判断为：两处明确衔接错误已修复，应保留正确语义；本批中规模纯调度的启发式结果变化不大，没有稳定的大幅提升或明显额外时间开销。固定60秒预算下，正确重置并不保证每个随机种子的目标更优。维持其他参数，不根据这6例继续调删除比例或停滞上限，不据此宣称整树时间改善，也不要求重新生成历史正式seed。
