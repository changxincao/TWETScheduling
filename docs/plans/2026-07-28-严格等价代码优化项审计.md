# 严格等价代码优化项审计

## 1. 审计边界

本次只检查附件中九类优化建议与当前代码的对应关系，不修改算法代码，也不启动求解。严格等价的含义仍是：pricing engine 调用顺序、DSSR 的 Tmid/轮次/top-C/K/更新顺序、返回列及排序、restricted column ID 集合及顺序、strong branching 评分和分支树、certificate/fixing/writeback 均不改变。

需要补充一个边界：ALNS 使用墙钟时间终止时，即使只增加诊断计时，也可能轻微改变最后执行的迭代数。因此 VND operator 计时必须由诊断开关控制；若要逐项比较列和分支树，应使用非绑定总时限或固定迭代数的诊断入口。

## 2. 当前结论

### 2.1 应优先实施

1. **拆分 LP 建模、求解和解读取时间。** 当前 `LP.solveRelaxation()` 把 `buildModel()`、`cplex.solve()` 和 dual/value 读取记在同一个 master LP 时间中；`Tree` 中名为 `*_rmp_build` 的统计只覆盖 `LP.construct()`，没有覆盖 CPLEX 矩阵构造。因此现有日志无法判断 strong trial 慢在 Java/Concert 建模还是 simplex。应先按 variables/objective、coverage、machine/branch、cut、repair、solve、extract 分段计时。该修改只增加粗粒度计时，不改变调用顺序。

2. **复用普通 time-indexed 的大数组 scratch。** `TimeIndexedGraphSolver` 每次 pricing 都重新分配 `dist`、`predState` 和 `predAddedJob`，在大 horizon 下单次可产生十几 MB 的短命数组。engine-local buffer 按当前 `stateCount` 完整重置即可保持严格等价，同时明显降低分配和 GC；不应复用任何旧 dual 下的数值。

3. **引入最小版不可变列结构共享。** 当前 temporary `TWETColumn` 进入 `Pool` 后，sequence、signature、jobs 和 jobVisitCounts 会再次构造；同 sequence 成本改善时也重新构造全部结构。建议先引入只包含这四项的 `ColumnPattern`，temporary candidate、Pool column 和成本改善 header 共享它，并缓存一次只读 sequence view。不要第一步就把全部 arc posting、adjacency 和 cut 系数塞入该对象。

4. **若继续重点优化 time-indexed SRI，则实现 packed residual。** 当前每个 rank-1 label 扩展都会 clone `byte[activeCuts]`，并逐 cut 扫描。现有 residual 严格为 0/1，适合用 `long`/`long[]` 表示。该修改能降低状态复制和逐 cut 判断，但不能消除 horizon 与 residual 组合造成的 label 膨胀。实现时必须分别保持 forward、backward、join、dominance 的现有更新顺序，并按 active cut index 递增累加 dual，避免改变浮点求和顺序。

### 2.2 先完成 LP 计时，再决定范围

5. **LP 系数缓存有价值，但不能一次做成全局 posting 系统。** coverage 已使用 O(1) 的 jobVisitCounts，主要问题只是 `n × restricted columns` 扫描；arc/adjacency 行仍会反复扫描 sequence；SRI 行还会为每个 `(cut,column)` 重建 scope/memory membership 并扫描 sequence。建议顺序为：
   - 先把 cut 编译成可复用的 scope/memory 表，去掉每次系数计算的 boolean 数组分配；
   - 在 `ColumnPattern` 中按紧凑 primitive 数组缓存 directed arc multiplicity/adjacency；
   - 只有 LP 分阶段统计仍证明行构造占主导时，再增加稀疏 `(cutId,columnId)` 系数缓存。

   暂不建立全局 `arcKey -> columnIds` posting。它会增加列池常驻内存、restricted 交集和顺序恢复逻辑，当前没有证据表明优于按 restricted column 顺序读取列内缓存。cut ID 当前不可变，因此 `(cutId,columnId)` 缓存语义可行，但必须稀疏或有界。

6. **有界堆只替换“大 M、小 K”的位置。** `LP.resetRestrictedColumnsByCurrentReducedCost()`、外包对应入口和 time-indexed root seed 选择可以从全排序改为 bounded heap，并在最后按原 comparator 排序。Arc strong candidate 最多约 O(n^2)，而且 `Tree` 当前需要完整 candidateCount；phase1/phase2 数量更小，不值得为它们增加统一堆框架。root seed 还要先排除已经是 root seed 的同 signature 列，否则只保留 K 个候选会改变“跳过重复后继续补足 K 个”的语义。

### 2.3 可做但优先级低

7. **time-indexed candidate 扫描只做小改。** dual-window evaluator 失败前不必先构造 signature；重复 job 可在回溯时用 epoch 数组同步判断；最终可直接复用 `ColumnPattern`。不建议给每个时空 state 增加 `depth` 数组，只为精确预分配少量返回 sequence 的容量会额外增加 O(nH) 内存，收益不抵成本。

8. **ng-DSSR repeated-segment scratch 暂不改。** 当前每条 witness 分配两个 `n+1` 整数数组；一轮可能扫描到 top-C 上限，但找到 K 个有效更新后即停止，且 `n` 通常为 40--100。其中 `middleMarks` 已用 mark 避免清零，`lastPosition` 的短数组填充很便宜。只有后续 allocation profile 证明该处显著时，才值得改为 solver-local epoch scratch。

### 2.4 当前不建议实施

9. **不缓存 Node 的 time-indexed arc lookup。** 当前 lookup 只在存在时空禁弧时构造一个 O(n^2) 的 `BitSet[]` 只读视图，已经避免了热循环中的 HashMap 查询。跨 pricing 缓存需要覆盖 forbid/replace/merge/copy/writeback 的全部失效路径，复杂度高于当前可见收益。

10. **不把 static time-indexed tables 提升到全局 Context。** 普通 no-cut 与 rank-1 主线本来互斥；rank-1 已与其 no-cut delegate 共享同一 `StaticPricingData`。pre-heuristic 当前默认关闭，root preprocessor 又是短生命周期独立 context。继续全局化主要会延长大 penalty table 的存活时间，实际重复构造很有限。

## 3. 当前代码中已经完成的相关优化

ng-DSSR top-C witness 池已经是 `SequenceSignature` 哈希表加有界 `TreeSet`，不存在附件之外所说的线性 sequence 去重和每次全排序；no-SRI 主线也已经在分配 SRI 容器前返回。初始列构造已经用本次 build 的 `evaluatedSequenceIds` 避免同一历史 sequence 重复 evaluator。这三项不应重复修改。

## 4. 推荐实施顺序

1. LP/VND 诊断计时，其中 VND 统计默认关闭。
2. time-indexed primitive scratch 复用。
3. 最小版 `ColumnPattern`，先只消除 candidate 到 Pool 的重复结构构造。
4. 根据 LP 计时结果，优先做 compiled cut coefficient 和列内 arc/adjacency 缓存；再判断是否需要稀疏 cut-column cache。
5. 仅在保留 time-indexed SRI 为核心实验方法时，实现 packed residual。
6. 最后考虑目标明确的 bounded heap 和 candidate 小优化。

每项应独立提交。除 wall-clock 诊断外，结构等价测试至少比较：每轮 pricing 返回 signature/成本/顺序、restricted IDs 及顺序、active cuts、strong candidate/side score、节点创建和关闭顺序、最终 objective/bound。

## 5. 各项优化的原流程、目标流程和收益来源

### 5.1 LP 分阶段计时

原流程中，外层只记录一次 `LP.solveRelaxation()` 总时间，而该方法内部依次重建 CPLEX model、调用 `cplex.solve()`、读取 dual 和变量值。另一方面，strong trial 日志中的 `*_rmp_build` 只覆盖 Java 侧的 `LP.construct()`，它主要设置 node、restricted IDs 和 active cuts，并未构造 CPLEX 矩阵。因此当前日志中的 master LP 时间无法区分“逐行添加 Concert term 很慢”和“CPLEX simplex 很慢”。

目标流程是在现有调用位置周围增加粗粒度计时，分别记录 variables/objective、coverage、machine/branch、cut、repair、`cplex.solve()` 和 solution extraction。该项本身不加速，只负责决定后续优化方向：若 build 占主导，列结构和系数缓存有意义；若 solve 占主导，在保持模型、basis 和算法流程不变的条件下，Java 缓存不会解决主要时间。

### 5.2 time-indexed primitive scratch

原流程每次创建 `TimeIndexedGraphSolver` 时，都按 `stateCount=(n+1)(H+1)` 新建一个 `double[] dist` 和两个 `int[] predecessor` 数组。一次 pricing 完成后 solver 被丢弃，下一次 pricing 又分配相同数量级的数组。以 `n=60`、`H=20000` 为例，这三组数组的裸数据约为 19.5 MB，数百次 pricing 会形成大量短命内存和 GC 压力；而 DP 本来就必须重新覆盖这些状态。

目标流程由 pricing engine 持有可扩容 scratch。新一轮若容量足够就复用，否则扩容；每次仍对当前有效前缀完整重置，绝不读取上一轮 dual 下的距离和 predecessor。它省掉的是重复分配和回收，不省略 DP 扫描，也不改变状态顺序。

### 5.3 最小版 ColumnPattern

原流程中，pricing 先构造一个 `id=-1` 的 temporary `TWETColumn`。构造过程复制 sequence、构造 `SequenceSignature`、构造 jobs bitset 并统计 jobVisitCounts。`LP.addOrImproveColumn()` 随后只把 sequence 等字段传给 Pool；Pool 先重新构造 signature 做查询，新增列时又构造一个正式 `TWETColumn`，把上述结构再做一遍。同 sequence 获得更低成本时，Pool 也会重建全部结构，尽管序列本身没有变化。

目标流程把不随成本变化的 sequence、signature、jobs 和 jobVisitCounts 放进不可变 `ColumnPattern`；列对象只保存 id、cost、source、seed 等 header。temporary candidate 进入 Pool 后复用同一 pattern，成本改善只创建新 header。收益来自每条入池列少一次 sequence 复制、signature 构造、bitset 构造和计数扫描，并减少 GC。第一步不加入 arc、adjacency 和 cut cache，避免把一个局部结构共享修改扩大为全局索引重构。

### 5.4 packed rank-1 residual

原流程为每个 rank-1 label 保存一个长度等于 active-cut 数量的 `byte[] residual`。每次扩展先 clone 整个数组，再逐 cut 判断 memory、scope 和 residual；join 与 dominance 也逐 cut 扫描。当前 residual 只可能是 0 或 1，所以一个 cut 实际只需要一个 bit。

目标流程在 active cuts 不超过 64 时使用一个 `long`，更多时使用 `long[]`；按 job 和 arc 预计算 retain/toggle masks。扩展时先用位运算更新 residual，只对发生 carry 或 dominance correction 的 bit 按 active-cut 顺序累加 dual。这样可把一次 label state 复制从几十或上百字节降到 8 字节或少量 `long`，并减少无关 cut 的分支判断。它只能降低每个 label 的处理成本，不能减少 horizon、cut-state 组合或 label 总数，因此不能单独解决 SRI 图膨胀。

### 5.5 LP 系数缓存

原流程每次重建 RMP/strong trial model 时都重新生成矩阵。coverage 已经使用 jobVisitCounts，但仍按 job 扫描所有 restricted columns；每条 active branch arc 会再次扫描所有列的 sequence；每个 SRI `(cut,column)` 不仅扫描 sequence，还会重新构造 scope/memory membership 数组。strong branching 反复使用大量相同列和 inherited cuts，因此这些工作会重复。

目标流程分三步：先把每个 immutable cut 编译成可复用 membership；再让 ColumnPattern 保存紧凑 arc/adjacency 数据；只有计时仍证明 cut row 构造很重时，才增加有界或稀疏的 `(cutId,columnId)` coefficient cache。构造每一行时仍按 restricted column 顺序添加 term，保证 CPLEX 输入顺序不变。全局 arc posting 暂不采用，因为它需要额外做 restricted-set 交集、顺序恢复和大规模常驻索引。

### 5.6 bounded top-K

原流程在若干入口先收集全部 M 个候选并完整排序，再只使用前 K 个，复杂度为 `O(M log M)`。目标流程扫描时维护容量 K 的 worst-first heap，扫描结束后只对 K 个幸存者按原 comparator 排序，复杂度变为 `O(M log K)`。

该修改只适合 root seed 或 restricted-column reset 这种 M 很大、K 很小的入口。strong branching 的 arc candidate 通常只有 `O(n^2)`，而且 Tree 仍需要完整 candidateCount；phase1/phase2 列表更小，因此替换收益很低。root seed 还必须先正确处理已存在 seed 的 signature，否则简单的 K 容量堆会改变“跳过重复后继续补足 K 条”的结果。

### 5.7 其余小项

time-indexed candidate 可把 signature 构造移动到 dual-window evaluator 通过之后，并在 sequence 回溯时顺便判断重复 job；这些只减少少量最终候选扫描。不能为了精确 sequence 容量给所有时空 state 增加 depth，因为它会新增一个 `O(nH)` 整数数组。

Node arc lookup 当前只是每轮构造一个 `O(n^2)` 的引用数组，已经避免热循环 HashMap；跨轮缓存需要管理所有 fixing/writeback 失效路径。static pricing data 在 rank-1 与 no-cut delegate 之间已经共享。ng repeated-segment 的数组只有 `n+1`，优先级均明显低于上述项目。

## 6. 逐项实施与测试

### 6.1 P0：RMP 分阶段计时

2026-07-28 首先只实现 RMP 诊断计时，没有修改建模顺序、CPLEX 参数、pricing、repair 或 strong branching 流程。诊断由系统属性 `twet.bpc.masterLpPhaseTiming=true` 单独开启；关闭时不执行各阶段的 `nanoTime()` 和字符串格式化。记录项为 model initialization、variables/objective、coverage/machine rows、branch rows、cut rows、repair rows、`cplex.solve()` 和 solution extraction，并明确区分 rebuild 与 resolve。

在 `wet040_001_2m`、ALNS 关闭、`maxNodes=1` 的小规模诊断中，共记录 72 次 RMP。内部 `totalMs` 合计 7657.920 ms，现有 PC 外层计时合计 7659.292 ms，仅相差 1.372 ms，说明分段基本闭合。40 次 `strong_branching_light_repair_rmp` 合计 7101.788 ms，其中：

1. CPLEX solve 为 4799.726 ms，占 67.6%；
2. model rebuild 为 2227.642 ms，占 31.4%；
3. rebuild 内 coverage/machine rows 为 1836.184 ms，占 rebuild 的 82.4%；
4. solution extraction 为 71.939 ms，其他未归类时间仅 2.483 ms。

同配置关闭计时后，objective、bound、pool、strong trial 次数和有效性均未变化；总时间分别为 22.364 s 与 20.655 s。单次 wall time 存在约 1.7 s 波动，不能据此认定为诊断开销，但诊断默认关闭，因此不影响正式实验。该结果已经证明后续若优化 strong-trial RMP，首要 Java 侧目标应是 coverage row 构造；同时约三分之二时间仍在 CPLEX solve 内，严格保持模型与求解流程时无法由 Java 缓存消除。

### 6.2 P0：VND 算子计时

新增默认关闭的 `twet.alns.vndOperatorTiming` 诊断。一次 ALNS 开始时清零，结束时汇总每个 VND 算子的 `searchBest()` 时间、`commit()` 时间、调用次数和实际改进次数；开关关闭时不读时钟、不维护统计容器，也不输出日志。算子构造、shuffle、调用顺序、最佳 move 和接受逻辑均未改变。

在 `wet040_001_2m` 上使用固定随机种子、ALNS 无 wall-clock 截止、`maxNoImprove=5`、不进入 BPC 节点的诊断中，开关开启和关闭均得到初始目标 22750，时间分别为 2.428 s 和 2.504 s。开启统计时，VND 算子累计约 2309.6 ms，其中 `CrossExchangeOperator.searchBest()` 为 1382.3 ms，`PathInsertOperator.searchBest()` 为 753.0 ms，两者合计占已记录算子时间的约 92.5%；所有 commit 合计不足 60 ms。该项只用于定位，不据此修改 VND 算子。

### 6.3 time-indexed primitive scratch：测试后不保留

曾实现 engine-local `dist/predState/predAddedJob` 复用，并保证每轮完整重置当前 `stateCount`。结构测试中，同一 engine 连续复用和每轮重新分配得到的 certificate、列数量、列顺序、sequence 与成本逐项一致。

跨进程 root-only 对照受机器状态影响很大：首次复用/不复用为 45.782/67.084 s，但复用组复测又达到 63.831 s，不能把整轮差值归因于数组复用。同一 JVM、同一 LP、交替执行两条路径的定向基准进一步显示：

1. 每组 50 次 pricing：复用 1401.291 ms，重新分配 1381.938 ms；
2. 每组 300 次 pricing：复用 21950.830 ms，重新分配 21838.625 ms。

复用没有稳定收益，反而慢约 0.5%--1.4%，说明当前主要成本是 `O(n^2H)` 图扫描，三块 primitive 数组的 TLAB 分配并非热点。该实现、测试开关和临时 benchmark 已全部撤回，主线保持原状。

### 6.4 最小版 ColumnPattern：保留

本项只抽取列中不随 id、成本、来源和 seed 标记变化的结构：sequence、sequence signature、job bitset 和 job visit counts。pricing candidate 新增到 Pool 时，正式列直接复用 candidate 的 `ColumnPattern`；同 signature 获得更低成本时，仅替换列 header，并继续复用 Pool 中原有 pattern。arc 系数仍按原 sequence 计算，没有加入 adjacency、cut coefficient 或其他缓存。系统属性 `twet.bpc.shareColumnPattern=false` 保留了旧构造路径，用于严格 A/B。

定向结构测试验证了以下语义：共享前后 sequence、signature、job coverage、重复 job 次数和所有普通 arc visit count 完全一致；sequence 视图不可修改；成本改善仍保留原 Pool pattern，并维持原 source/seed 更新规则。`ColumnPatternSharingTest`、`TimeIndexedGraphOptimizationTest` 和 `LPRestrictedColumnMembershipTest` 均通过。

在同一 JVM 内交替执行 100,000 条长度为 12 的不同候选列入池操作时，共享路径为 111.597 ms，旧路径为 145.403 ms，旧路径耗时约为共享路径的 1.303 倍。该基准覆盖候选构造和 Pool 入池，因此收益来自消除第二次 sequence 复制、signature 构造、bitset 构造和 visit-count 扫描。

`wet040_001_2m`、ALNS 关闭、`maxNodes=1` 的完整 root 对拍结果如下：

1. 开启共享：objective 62989，bound 22490，36 轮 pricing，13482 条 RMP/Pool 列，4 次 exact，valid；
2. 关闭共享：objective 62989，bound 22490，36 轮 pricing，13482 条 RMP/Pool 列，4 次 exact，valid。

两组 root 时间分别为 14.401 s 和 14.407 s，差异可以忽略；总时间分别为 27.978 s 和 26.500 s，主要受 CPLEX 和机器状态波动影响，不能据此评价该局部优化。由于结构和完整流程严格一致，且定向热路径有稳定收益，本项默认开启并保留。

### 6.5 coverage row 列主序构造：保留

原路径对每个 job 扫描一次全部 restricted internal columns，重复读取同一列并查询 visit count。新路径先为所有 job 创建表达式，再按 `restrictedColumnIds` 顺序只扫描一次列，通过列的 job bitset 把非零 visit count 分发到对应覆盖行。每行的变量 term 仍按原 restricted-column 顺序加入；覆盖行创建顺序、外包项、右端项和 set-covering 方向均未改变。系统属性 `twet.bpc.buildCoverageRowsByColumn=false` 保留原路径供 A/B。

在 `wet040_001_2m`、ALNS 关闭、`maxNodes=1`、开启 RMP 分阶段计时的两轮相反顺序 A/B 中：

1. 第一轮旧/新 coverage 累计为 2576.795/1741.153 ms，新路径下降 32.4%；
2. 第二轮旧/新 coverage 累计为 2498.131/1508.990 ms，新路径下降 39.6%；
3. 两轮平均 coverage 从 2537.463 ms 降至 1625.072 ms，下降约 35.9%；
4. 两轮平均 model build 从 3242.190 ms 降至 2342.907 ms，下降约 27.7%。

四组均得到 objective 62989、bound 22490、36 轮 pricing、13482 条 RMP/Pool 列和 `valid=true`。CPLEX solve 仍有独立波动，因此不使用总 wall time 评价该 Java 构造优化。focused 编译、`ColumnPatternSharingTest` 和 `LPRestrictedColumnMembershipTest` 通过。

### 6.6 SRI cut/column 系数缓存：保留分页缓存

40-2 time-indexed + SRI、ALNS 关闭、`maxNodes=1` 的初始诊断中，共有 46 次 model rebuild。cut rows 累计 71893.718 ms，占 build 78554.976 ms 的 91.5%；coverage 和 branch rows 分别只有 4706.151 ms 和 292.620 ms。该 active-cut 场景中，cut 系数重算才是 RMP 构造的主要热点，普通 arc/adjacency branch row 不值得为了不足 0.3 秒的累计时间给全部列增加常驻索引。

首先单独测试了在 `TWETCut` 创建时编译 scope/memory membership。full、node-memory 和 arc-memory 的 2 万条随机序列对拍全部一致，200 万次 evaluator 微基准从 385.263 ms 降到 229.200 ms；但真实 no-strong root 的 cut rows 为旧/新 6186.741/6291.480 ms，完整 strong root 的新路径也没有下降。该改动没有端到端收益，已经连同测试开关和临时测试完整撤回。

随后实现严格 `(cutId,columnId)` 系数缓存。缓存位于全局 `CutPool`，因此正式 LP 与 strong-trial LP 共享；cut ID 和 column ID 均不可变，同一 sequence 的成本改善不影响系数。实现按 4096 个 column ID 分页，页只在实际访问时分配；每项使用 `short` 保存非负整数系数和未缓存哨兵，超过 `Short.MAX_VALUE` 的极端系数不缓存并继续现算。默认总容量为 16,777,216 项，约 32 MiB 裸系数；达到容量后不再分配新页，已有缓存继续命中。系统属性 `twet.bpc.cacheSubsetRowCoefficients=false` 可恢复原路径。

同一 40-2 SRI root 的结果为：

1. 关闭 strong branching：cut rows 6186.741 → 5209.097 ms，下降 15.8%；总时间 84.732 → 81.365 s；
2. 开启原有 40 次 strong trial：cut rows 71893.718 → 17237.178 ms，下降 76.0%；model build 78554.976 → 23707.400 ms，总时间 211.051 → 145.329 s，下降 31.1%。

开关两侧均为 objective 62989、bound 22526.814815、286 轮 pricing、46832 条 RMP/Pool 列和 `valid=true`。`CutPoolCoefficientCacheTest` 覆盖零系数、分页边界、全局容量、最大可缓存系数、超界退化和关闭开关；cut ID 不可变、active-memory merge、child cut 继承、列结构共享和 restricted-column membership 回归均通过。

### 6.7 bounded top-K：只保留 reduced-cost 筛列

repair 成功和 child 首次 LP 后的 restricted-column reset 原本会收集所有 reduced-cost 合格列、完整排序，再在保留全部正值列后截到 `branchSeedColumnLimit=5000`。新路径在扫描时维护容量为 5000 的 worst-first heap；由于正值列数量要到扫描结束后才完全确定，heap 先保留前 5000 个普通候选，随后按剩余名额从最差端裁掉，再按原 comparator 排序。正值列的保留和原 restricted 顺序不变；普通候选仍按 reduced cost、column ID 排序。列化外包列使用同一规则。系统属性 `twet.bpc.boundedReducedCostColumnSelection=false` 保留旧路径。

定向随机候选基准使用同 comparator、`K=5000`，并逐项核对输出 ID 与完整排序前 K 一致。去掉预热后的平均结果为：

1. `M=10000`：4.002 → 2.750 ms，快 1.455 倍；
2. `M=50000`：17.555 → 4.666 ms，快 3.762 倍；
3. `M=100000`：31.499 → 4.930 ms，快 6.390 倍；
4. `M=500000`：215.954 → 7.721 ms，快 27.971 倍。

40-2、ALNS 关闭、`maxNodes=2` 的完整开关对拍中，两侧均为 bound 22490、2 nodes、57 轮 pricing、18185 条列；node 1/2 的 strong candidateCount、top preview、左右 side bound、score 和最终选中 arc 逐项一致，总时间为 41.210/41.095 s。小池上整体收益不可见，但大池下选择热路径的定向收益明确，因此默认开启。

strong branching candidate 暂不改：候选通常至多 `O(n^2)`，并且 Tree 需要完整 candidateCount 和排序后的 preview。time-indexed root seed 也暂不改：当前排序后会跳过 main Pool 中已有 signature 并继续向后补足 200 个新 seed，同时可能改善已有列成本；简单前 200 heap 会改变补位和改善顺序。

### 6.8 rank-1 packed residual：保留

time-indexed rank-1 pricing 原来为每个 label 保存 `byte[activeCuts]`。每次 processing 扩展先复制整段数组，再逐 cut 判断 scope、node/arc memory 和奇偶 residual；join 与 dominance 也逐 cut 扫描。由于 residual 始终只有 0/1，新路径按 active-cut 顺序压入 `long[]`，并预先为 job/arc 构造 retain、toggle 和 scope mask。扩展先用位运算得到新状态，只对实际发生 carry 或 dominance correction 的 bit 按 cut 下标递增累加 dual，因此浮点累加顺序仍与旧循环一致。等待弧继续共享只读 residual，bucket、label ID、candidate 顺序和 sequence 恢复均未改变。

系统属性 `twet.bpc.packedRank1Residual=false` 保留旧 `byte[]` 后端用于 A/B；`twet.bpc.verifyPackedRank1Residual=true` 只用于诊断，会在真实 labeling 中同时执行旧公式，并逐次核对 forward、backward、source prepend、join 和 dominance。40-2 time-indexed + SRI root 的双算运行覆盖 89 条 active cuts，没有出现 shift、residual 或 dominance 不一致。

同一 `wet040_001_2m`、ALNS 关闭、strong branching 关闭、`maxNodes=1` 的顺序反转对照结果为：

1. 旧后端两次 exact pricing 累计分别为 49.366 s 和 49.115 s；
2. packed 后端关闭双算诊断后为 27.443 s，相对两次旧后端平均值下降约 44.3%；
3. 三组均得到 bound 22526.814815、286 次 pricing、46832 条 Pool/RMP 列、235 条 cutPool cut、89 条 active cuts和 `valid=true`；
4. packed 双算诊断组因同时执行两套公式为 68.852 s，只用于正确性，不用于性能比较。

`ActiveCutInheritanceTest`、`CutPoolActiveRank1MemoryMergeTest`、`CutPoolCoefficientCacheTest`、`LPRestrictedColumnMembershipTest`、`StrongBranchingPhaseOnePricingTest` 和 `TimeIndexedGraphOptimizationTest` 均通过。该项没有减少 horizon 或 residual 组合数量，但显著降低了每个 rank-1 label 的状态复制和 cut 扫描成本，因此默认开启并保留。

### 6.9 time-indexed candidate 重复扫描：只保留两项小改动

`ColumnPattern` 接入后，普通和 rank-1 time-indexed candidate 仍先显式构造一次 `SequenceSignature`，随后 `TWETColumn(sequence,...)` 又在新建 `ColumnPattern` 时复制 sequence 并构造第二次 signature。现在改为每个候选只构造一个 `ColumnPattern`，map key 直接取该 pattern 的 signature，轻量列头复用同一个 pattern。rank-1 dual-window 候选先完成 evaluator 回刷和负 reduced-cost 检查，只有真正保留时才构造 pattern/signature。该调整不改变 signature 内容、候选 ID、heap comparator 或返回顺序。

repeated-job 判定原来为每个候选新建 `boolean[n+1]`。现在每个 solver 只保留一份 `int[n+1]` marks，每检查一条候选递增 epoch；仍按原 sequence 顺序扫描并在第一次重复时返回。50 万条长度为 12、`n=60` 的定向基准中，原布尔数组路径为 25.437 ms，epoch 路径为 12.664 ms，局部约快 2.01 倍。20 万条候选的完整 pattern 构造基准中，原“独立 signature + 列内 pattern”路径为 40.467 ms，新路径为 34.221 ms，局部约快 1.18 倍。

没有给全部时空 state 增加 `depth`。该数组会增加 `O(nH)` 常驻内存，只为少量最终候选预分配 sequence 容量，不抵成本。也没有改变 pre-heuristic 对 repeated pseudo-schedule 的拒绝规则，exact pricing 仍允许原有 repeated sequence。

普通 time-indexed 40-2 root 得到 bound 22487.647059、211 次 pricing、45113 条列和 `valid=true`；rank-1/SRI root 仍得到 bound 22526.814815、286 次 pricing、46832 条列、89 条 active cuts 和 `valid=true`。后者 exact 时间受机器状态影响从前一轮 27.443 s 波动到 39.135 s，因此不把 root wall time 归因于本项，只采用上述同 JVM 定向基准评价局部收益。`ColumnPatternSharingTest`、`StrongBranchingPhaseOnePricingTest` 和 `TimeIndexedGraphOptimizationTest` 均通过。

### 6.10 time-indexed lookup 与 static table：测试后不改

primitive scratch 已在第 6.3 节证明没有收益并完整撤回。本项继续单独量化剩余两个建议。`Node.createTimeIndexedPricingOnlyArcLookup()` 当前只在节点存在时空禁弧时，把按 pair 保存的 `BitSet` 引用复制到长度 `O(n^2)` 的数组；不复制 BitSet，也不在热循环查询 HashMap。`n=40`、16400 条时空禁弧、10 万次构造的定向基准中，单次 lookup 平均约 10.023 微秒。即使按 40-2 SRI root 的 286 次 pricing 全部重建，合计也只有约 2.9 ms，远低于 pricing 与 LP 时间。跨轮缓存反而必须覆盖 forbid、replace、merge、copy、preprocessing writeback 和 fixing 中途修改等全部失效路径，因此不实施。

`StaticPricingData` 的完整 penalty/duration table 在同一实例上的单次构造平均约 0.905 ms。普通 time-indexed engine 在生命周期内只构造一次；rank-1 engine 已把同一份数据传给其 no-cut delegate。pre-heuristic 当前默认关闭，root preprocessor 又是独立短生命周期 context。把该表提升到全局 `TWETBPCContext` 只会增加大 penalty table 的存活时间，无法获得可见收益，因此不修改。

临时基准源码已删除，Node、Context、static table 与 lookup 失效语义均保持现状。

### 6.11 ng-DSSR repeated-segment scratch：测试后不改

当前 `addMinimumNewPairsRepeatedSegment()` 为每条待检查的非基本 route 分配 `lastPosition` 和
`middleMarks` 两个 `n+1` 整数数组。为区分“减少分配”和“改变扫描逻辑”的影响，本次只在临时
基准中实现了两种严格等价后端：其一把两个数组都改为 solver-local epoch scratch；其二只复用
数组，仍按原逻辑对 `lastPosition` 执行 `fill(-1)`，仅让 `middleMarks` 的 mark 跨调用递增。
20,000 组随机 sequence/ng-set 对拍中，两种后端与原方法的返回值、added-pair 顺序和最终
ng-set 逐项一致。

在 `n=60`、长度 21、含一个完整重复段的 500,000 次更新基准中，全 epoch 后端因每个 sequence
元素增加 epoch 判断，中位耗时反而由约 154.5 ms 增至约 182.5 ms。复用数组但保留 `fill` 的
后端中位耗时约 120.7 ms，局部快约 21.9%，但绝对节省只有约 68 ns/route。即使按极端
`candidate C=1000`、91 轮 DSSR 且每轮全部扫描计算，累计也仅约 6 ms；真实流程找到 K 个有效
更新后还会提前停止。因此该处分配不是可见热点，不值得给 solver 增加可重入 scratch 状态。
临时基准源码已删除，主线重复段选择、缺失 pair 数、span tie-break 和更新顺序均未修改。

### 6.13 packed residual 语义与旧 VRP 的 SRI 系数路径

packed residual 的每个 bit 不是“是否经过该 cut”，而是当前 limited-memory 有效段内 scope
命中次数除以 2 后的余数：0 表示偶数次、没有未配对命中，1 表示奇数次、留下一个未配对命中。
前向扩展先按当前 arc/job memory 清除不再保留的旧 bit，再对当前 scope job 翻转 bit；只有
保留后为 1 且本次需要翻转的 bit 才形成一次 `1 -> 0` carry，并减去对应 cut dual。scope、
retain 与 toggle mask 只依赖本轮 active cut 的 scope/memory 和扩展 job/arc，不依赖 label
或 dual 数值，因此可在一次 pricing 开始时预计算。`residualWordCount=(activePricingCuts+63)/64`，
一次 pricing 内固定；cut separation、inactive removal 或 dual 活跃集合变化后的下一次 pricing
会按新的 active cut 数重建 masks 和 label residual 长度。

旧 VRP `BPC.LP.LP` 没有 `(cutId,routeId)` 系数缓存。新增三元素 SRI 时，它利用
`cus2schedule` 的 customer-to-route 倒排表统计既有 route 命中 cut customer 的数量，命中至少
两个时写系数 1；新增 route 时，则逐条 active SRI 调用 `route.contains()` 检查三个 customer，
同样在命中至少两个时写系数 1。

这里所谓旧 VRP 的“持久 CPLEX 模型”，只指一个 `LP` 对象/节点的列生成与割平面循环：
`Construct()` 创建一次 `IloCplex`，后续 `AddColumn()` 和 `AddSRCut()` 直接向该模型增量追加
变量与约束，反复求解，直到 `Clear()` 才释放；它不是整棵分支树共享一个 CPLEX 模型。当前
TWET 在单个 `LP` 的普通列生成循环中同样会通过 `addColumns()` 增量加列，并用
`resolveCurrentModel()` 重解，因此“TWET 每轮 pricing 都重建 RMP”的说法不准确。

进一步检查后确认，TWET 原先在 cut loop 中重建 RMP 没有必要，已经按旧 VRP 的方式改为增量
维护：`addCuts()` 直接给当前全部内部列计算系数并向活模型增加 `IloRange`，后续新列仍由
`addColumnToCurrentModel()` 补该行系数；inactive cut 或 rank-1 memory 旧版本则直接从活模型
删除对应 row。PC 在这两种变化后统一调用 `resolveCurrentModel()`，不再执行 `buildModel()`。
`ActiveCutInheritanceTest` 新增了活模型验证：加入一条系数为 1、rhs 为 0 的 SRI 后当前 RMP
立即不可行，删除该 row 后恢复可行，证明修改不只是更新 active cut ID。

现在与旧 VRP 的单节点 cut/column 增量维护方式已经一致。仍然存在的模型重建只来自确实替换
restricted column set、repair/真实目标切换，以及每个正式节点和 strong-trial 的独立初始模型。
全局 immutable ID 缓存仍可跨这些 `LP` 对象复用 `(cutId,columnId)` 结果，但先前在“cut loop
每轮重建”口径下测得的缓存收益不能直接外推到新流程，后续性能比较应以增量 cut 版本重新测量。
