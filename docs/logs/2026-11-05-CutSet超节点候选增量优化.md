# CutSet 超节点候选增量优化

2026-11-05。按用户本轮授权，只处理全局审查第4项的 supernode CutSet 重复扫描；前三项（有限M修复结束判定、ALNS插入函数契约、ALNS停滞计数）仅作解释，没有修改。默认分支配置和远端程序保持不变。

## 1. 修改内容

原实现对每个seed的每个扩张前缀，重新扫描整个集合到所有候选组的连接流；加入新组后还重新构造完整入边mask并求和。同一LP快照下这些组间流量不变，旧成员的贡献没有必要反复计算。

`StructuredArcFlowBrancher.buildSupernodeCutSetCandidateSpecs` 现在预计算组间双向流量、各组进入流和组大小。每次加入组G，仅累加G对剩余组的连接贡献，并使用 `z(S并G)=z(S)+z(G)-A(S,G)` 更新边界。source进入流包含在z(G)中，组内弧排除，sink不计入进入流。没有改变0.999合并阈值、seed和组遍历顺序、首次/后续affinity比较规则、n−1规模上限、分数性容差、去重、三位距离排序或Cluster→CutSet→Arc层级。

增量求和与旧求和的浮点顺序不同，因此没有声称所有double逐bit相同。按总弧流量量级及每条链O(n²)的累加项数设置保守舍入带；仅当affinity比较、分数性判断或三位排序分界可能受尾差影响时，按旧循环次序复算。边界复算直接按from-major访问弧，不创建临时mask。最终进入候选池的少量supernode CutSet仍按实际mask重新求值，再生成分支界。普通singleton CutSet路径不改。

组表额外空间为O(g²)，非临界扩张为O(g³)，g是超节点数；临界复算保留原算法语义，因此不能承诺所有数值输入的最坏复杂度均降为三次方。

## 2. 验证结果

Java21目标编译通过，既有 `StructuredArcFlowBranchingTest` 通过。新增 `SupernodeCutSetIncrementalTest` 固定改动前完整扫描逻辑为reference，覆盖singleton、多组合并、交错编号、巨型组、断开集合、source流、无效sink/self项、十进制流量、affinity容差和分数性/三位排序临界点。150组测试、3978个候选全部通过：集合、生成顺序和三位桶排序一致，最大边界差为7.11e-15，输入流矩阵未被修改。测试也在旧生产实现上运行通过，避免reference仅迎合新实现。

另外用已有独立时间DP及集合分割oracle，对两个小实例分别开启NG-DSSR、TI、TI+SRI的supernode CutSet并完整求解，共6次UB/LB均等于精确最优值（30和28）。其中一个NG实例处理4节点、实际发生2次StructuredArcFlowBrancher分支，其余5次根闭合。这是衔接回归，不是大规模性能实验。临时入口为 `.codex-tmp/cutset-incremental-20261105/CutSetTreeAudit.java`。

同一次本机微基准，对16条路线等权混合、无超节点合并的流图，预热后测量中位数：

早期版本虽然已增量维护，但临界复算仍创建mask，n100约137ms；去掉该临时mask、保留同一求和次序后降到约48ms。仅报告候选构造收益，不推断总求解加速，更不保证family的合并组场景有相同倍数。benchmark可通过 `SupernodeCutSetIncrementalTest benchmark` 复跑，无速度断言。

本次不调整CutSet开关、候选数量、根fixing、probe、修复算法或任何正式实验参数；没有上传、替换远端JAR或重启求解。审查前三项和已知NG join BitSet生命周期问题仍未修复。
