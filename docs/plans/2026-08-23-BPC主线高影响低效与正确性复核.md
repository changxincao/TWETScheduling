# BPC 主线高影响低效与正确性复核

本轮根据此前 ng-DSSR、time-indexed、rank-1/SRI、strong branching 和 RMP 的专项记录，重新检查当前源码。审查只保留三类事项：可能破坏定价证书或剪枝正确性的错误；已有日志证明占用大量时间的实现；以及会随 label、column、cut 或 strong trial 数量乘法放大的冗余。只影响备用 dominance backend、默认关闭诊断或理论收益不足几个百分点的项目不再列为待优化项。本轮未修改算法，也未运行长算例；审查后仅按正式数据口径调整实验基础设施。

## 1. 主要结论

当前 normal no-SRI ng-DSSR 主线没有发现新的高优先级正确性错误，也没有发现尚未识别的、会随 label 或 join pair 数量显著放大的实现冗余。source-aware dominance、group-envelope join、completion bound、midpoint probe、DSSR 的 top-C/K 更新、Phase-I repair 和最终真实成本回刷之间的证书口径一致。历史上容易被重复提出的 join 顺序、同签名提前判重、completion-bound transition-only、启发式 seed 缓存和 warm start 均已有反例或 A/B 结果，不应重新接入。

ng-DSSR profile 当前包含完整 time-indexed root preprocessing。经讨论决定保持开启，并把它视为正式 NG_DSSR 方法的固定组成，而不是按时间尺度切换的可选项；论文和实验配置中需要明确说明这一点。时间倍率则只属于数据生成：放大后的 processing time、due date 和 setup time 现在由 suite generator 写入独立 `.dat`，runner 不再接受或执行 `timeScale`。

剩余两个真正的大头是 strong trial 的 RMP 重建和 SRI 下的列-cut 建模乘积。它们都是结构性成本，当前没有证据表明可以通过删除一段“过度防守”代码安全消除。前者若要优化，需要可回滚的 CPLEX model/basis 生命周期；后者若要优化，需要先量化新增列接入 active cuts 的 Java/Concert 时间。二者都不应与已经证明无效的小常数优化混在一起。

## 2. ng-DSSR 主线

### 2.1 当前真实热点

近期正确配置的 `60-3/W100` 中，ng-DSSR 总时间为 3321.319s，heuristic、exact 和 master LP 分别约为 1415.481s、1291.962s 和 490.4s。exact 内 completion bound、midpoint probe 和 join 分别约为 248.709s、303.966s 和 33.408s；DSSR 平均约 1.70 轮、最大 5 轮。另一个 `50-3/W100` 中，heuristic 为 49.115s/337 次，exact 为 23.650s/99 次，exact 内 completion bound、midpoint 和 join 为 15.411/6.978/0.912s。由此可见当前慢点是 changing dual 下反复执行启发式和 exact 初始化，不是 join、dominance graph 或 DSSR 长尾。

completion bound 和 midpoint probe 虽然计时较大，但不是纯额外工作。completion bound 在一次 exact 的全部 DSSR 轮之间复用，并在历史 W300 日志中剪掉约 67% 的 forward 和 80% 的 backward 扩展；选中 Tmid 的 probe label 会直接继续正式扩展，只有未选候选的浅 probe 工作被丢弃。历史 W300 汇总中，真正丢弃的 probe 工作约 18.1s/765.5s，只有约 2.4%，不满足本轮“高影响”标准。

启发式 pricing 也不能因为失败次数多就跳过。历史困难节点中，exact 加列并改变 dual 后的 24 次启发式重启有 9 次重新找到列；直接按“上一次失败”退避会把这些调用推给更重的 exact。当前主要耗时仍在 ADD/EXCHANGE 的 PWLF move 评价，seed 收集、排序、true-cost 回刷和状态应用都不是主要占比。

### 2.2 没有发现新的过度防守

最终候选统一用 evaluator 恢复全域真实成本并按 true dual 重算 reduced cost 是必要步骤。half-domain/Tmid、dual profitable window 和部分 join 路径中的 inferred reduced cost 只可用于候选排序，不能直接返回 Master。required-outsourcing job 和 branch/pricing-only arc 的兼容性检查同样不能删除；此前启发式曾因局部 move 未阻止 required-outsource job 回插而产生真实缺口。

top-C=1000、每轮最多更新 K=20 条有效非基本列也不是重复保存。C 控制 join witness 阈值，K 控制本轮实际加强的 route 数；历史对 C/K、top20 和冲突候选的实验显示，扩大候选或更新数只会在部分困难 certificate 上减少一轮 DSSR，同时增加 labeling 状态成本，完整 root 没有稳定收益。当前 TreeSet/map 维护已经避免每次全排序。

当前保留的 message-only histogram、reachable summary 和少量标量计数确实还有微小热路径写操作，但历史量级只对应数百万次简单自增/比较，相对于 PWLF、dominance 和数亿扩展没有高影响证据。本轮不建议继续为了这些统计增加更多开关和状态分支。

### 2.3 正确性复核

Phase-I 中“完整搜索但没有候选”与“超时/未完成”已经由 exact-round completion 状态区分；只有队列完整耗尽或 pre-certificate 闭合才返回非负证书。PricingMode 也已经统一驱动 engine、SRI、root preprocessing 和 fixing，残留旧 flag 不会再给不支持 cut dual 的 engine 加 SRI 行。

legacy M repair 没有 Phase-I 那样显式组合内部/外包 certificate 的状态字段，但当前 ng-DSSR best profile 不走该入口。time-indexed no-cut/rank-1 的 exact engine 在未超时时本身是完整 oracle，时间限制也在 PC 外层阻止错误闭合，因此本轮没有找到现行 profile 下的错误不可行判定调用链。

## 3. time-indexed 与 rank-1/SRI

普通 time-indexed 主线已经完成等待 predecessor 压缩、空禁弧快路径、静态数据复用、cleanup、候选延迟物化和目标成本延迟恢复。其剩余的 `O(n^2H)` 状态/弧扫描随 horizon 线性放大，是模型本身的复杂度，不是当前实现多扫了一遍。没有发现新的高影响正确性或冗余问题。

rank-1 pricing 已使用 packed residual、延迟 label 物化、严格预 dominance、packed mask 单次构造和默认关闭热统计；RMP 侧已有 SRI coefficient cache、inactive-page 回收和 job-to-column posting。历史 A/B 中 packed residual 使 exact pricing 约从 49.1s 降到 27.4s，延迟 label 物化又使 root 约下降 10.8%；SRI row posting 使候选扫描下降约 61%。这些已是当前主线。

剩余潜在大项位于 `LP.addColumnToCurrentModel()`：每条新增内部列仍遍历全部 active SRI rows，计算系数并把非零项接入 IloColumn。加 cut 时已有 column posting，但“加列找相关 cut”尚无对称的 active-cut posting。它的复杂度为 `newColumns × activeCuts`，理论上会在 cut 多且每轮返回大量列时放大。不过当前日志只证明 SRI 的 master LP/resolve 很慢，没有把新增列的 cut wiring 与 CPLEX solve 分开，因此不能直接认定这是当前主瓶颈。若继续优化 SRI，下一步只需增加默认关闭的隔离计时，记录每轮新增列数、active cuts、候选/非零 cut terms 和 Concert 接线时间；只有该时间达到总 solve 的显著比例，才实现 job-to-active-cut 保守 posting。

## 4. strong branching 与 RMP

当前每个正式节点和 strong-trial side 都创建独立 LP；首次 solve 会 `cplex.end()` 后重新建立 IloCplex 模型。正确配置的 60-3/W100 有 7120 次 strong trial，strong-trial LP 累计约 946.4s；修正 subtree 配置后总 master LP 仍约 490.4s。这个成本是真实大头。

但它不是一项可直接删除的防守。trial 内可能加入列、进入 repair、切换 Phase-I objective，并继承不同 branch rows/cuts；跨 side 复用同一个 model 必须完整回滚变量、行、目标、active cuts、penalty 列、solution/basis 和所有 Java 索引。当前节点内的 CG 已经增量添加列和 cut，并不会每次 pricing resolve 都重建模型。因而“每个 trial 重建”应记录为下一阶段架构课题，而不是当前可安全修补的循环冗余。

普通 child 先继承父 restricted set、出队求带新 branch row 的 RMP、repair 后再按 reduced cost 筛列，是项目对齐旧 VRP 的既定生命周期。strong trial 已有 lightweight/domain-filtered seed。直接把所有 child 都提前按新域过滤会改变 repair 起点和列生成轨迹，不能仅凭 restricted set 较大就认定为优化。

同理，strong candidate=20 是算法强度参数，不是实现错误。当前 phase2 已关闭，进一步减少候选可能降低 trial 时间，但需要整树 A/B，不能作为“明显低效”直接改。

## 5. 正式实验配置口径

`BestBpcProfiles.applyNgDssrDefaults()` 继续固定设置 `enableTimeIndexedRootPreprocessingForNgDssr=true`。正式比较中的 NG_DSSR 因此始终包含一次 time-indexed root preprocessing，所有时间尺度使用同一 profile，不按算例或倍率切换。这样保留了此前多数完整求解中更稳定的 compact window、elementary seed 和 paper graph fixing 收益；代价是大 horizon 下也必须支付该预处理成本，结果解释时应把它计入 NG_DSSR 总时间并明确披露。

时间倍率不再属于求解入口。`FormalExperimentSuiteGenerator` 在生成 suite 时把 processing time、due date 和 setup time 同比放大并写入 `formal-v1/instances/` 下的独立 `.dat`；seed 和三种算法的 manifest 行直接引用同一个最终文件。`FormalExperimentRunner`、`FormalExperimentDataFactory.Scenario` 和 run metadata 已删除 `timeScale`，旧 manifest 若继续传该参数会直接报错，避免静默读取基础实例。当前 pilot 仍使用 1/5/10 三档；最终 `[5,15]`、`[15,25]` 抽样倍率应在正式数据生成时写入文件和 metadata，而不是由 runner 临时处理。

## 6. 本轮不建议修改的项目

不再实现 completion-bound transition-only，因为 BigM 窗口反例证明会改变 eligibility；不做同签名 ng 候选预检查，历史弱 RMP 诊断 4021 个候选仅拒绝 3 次；不做启发式跨 dual seed/column cache，失效协议复杂且 seed collect 不是热点；不扩大 top-C/K，不恢复 warm start/non-best 列；不并行 F/B completion bound，因为正式批处理要求每个 solver 单线程且服务器外层并行；不改普通 child 的 repair 生命周期；不对 SRI 直接减少论文 cut family 或 cut 轮数来伪装实现加速。

本轮使用两路独立只读检查分别覆盖 ng-DSSR 与 time-indexed/SRI/RMP。两路均未发现新的高优先级 correctness bug。若继续做实现优化，只值得隔离测量 SRI 新列接 cut 的成本，以及单独设计 strong-trial model reuse 原型。除此之外，三条 pricing 主线已不存在证据充分的明显实现低效。
