# 正式计算实验基础设施

本文记录三种精确定价方法、外包模型实验、数据派生、结果输出和服务器批处理的统一入口。当前目标不是立即跑完全部矩阵，而是先固定可复现的配置、数据生成规则和输出口径，使后续更换服务器后只需要调整 manifest 即可运行。

## 1. 三种算法的固定配置

正式入口统一使用 `BestBpcProfiles`，版本为 `2026-08-16-v2`。三个 profile 分别是 `NG_DSSR`、`TIME_INDEXED` 和 `TIME_INDEXED_SRI`。它们共享 ALNS 60 秒初始解、best history、20 个 strong branching 候选、关闭第二阶段、dual-bound pruning、关闭 dual stabilization、RMIH 和 route enumeration。每个子 JVM 都强制 CPLEX 单线程。repair 口径不应放在公共配置中：ng-DSSR 使用 Phase-I repair；普通 time-indexed 和 rank-1/SRI time-indexed 根据 2026-07-23 的同起点 A/B 继续使用旧 M repair。

`NG_DSSR` 使用 nearest K，K 自动取任务规模的十分之一；DSSR 使用 C=1000、K=20 和 `minimumNewPairsSegment` 更新；启用 incremental sourced dominance graph、group-envelope join 预筛、visit-profile 剪枝、all-cycles completion bound、midpoint probe、root time-indexed preprocessing 和最多 200 条 elementary seed 列。hard subtree elimination 关闭，只保留 pricing-only fixing；历史和同节点 warm start 关闭；time-indexed preheuristic 关闭。

`TIME_INDEXED` 使用 dual window、每次最多返回 300 条精确列和 paper arc fixing，不使用外部启发式 pricing，不加 rank-1 cut。`TIME_INDEXED_SRI` 在相同图定价基础上启用 arc-memory rank-1 cut、最多 8 个 cut rounds、每个 job 最多出现在 20 条 active cuts 中，并在 cut loop 中执行 fixing。

这些值来自最近几轮已经反复使用的正式配置，不再从历史日志穷举重新挑参。集中 profile 的作用是防止 runner 之间复制后漂移；后续若确需改参数，应修改 profile 版本和对应回归测试，而不是在单个实验入口临时覆盖。

## 2. 实验矩阵与数据规则

数据生成入口为 `Common.FormalExperimentSuiteGenerator`。默认从 40、50、60、100 个任务的单机基准派生多机实例。60 个任务没有原始单机目录时，确定性截取 100-task 基准的前 60 行形成派生集。任务数不超过 60 时生成 2、3、4 台机器；100-task pilot 生成 2、3、4、5 台机器。现有数据文件不会被覆盖。

机器转换继续使用 `ETConverter` 的确定性 sequence-dependent setup time，平均 setup 水平约为平均处理时间的 0.5，并通过 Floyd 闭包保证三角不等式。正式 scenario 在内存中派生，不修改源文件：处理时间、due date、release time 和 setup time 同比例缩放；due window 以原 due-window 中点为中心重设；setup cost 由 `setupCostCoefficient * setupTime` 控制。当前 manifest 将 setup cost 系数固定为 0，setup time 已存在；setup cost 或 setup 强度的额外实验应作为独立扩展块，不与所有时间尺度和窗口档位做全因子乘积。

纯调度比较默认使用 n=40/50/60，m=2/3/4，时间尺度 1/5/10，due-window 半宽为平均处理时间乘以 0/2/6 后再随时间尺度同步放大。三种算法在同一个 scenario 下共享完全相同的固定初始列快照。n=100 只生成数据并进入 `instances.tsv`，默认不进入完整精确求解矩阵，待 pilot 确认可计算性后再加入。

外包实验不与时间尺度矩阵做全因子乘积。默认在原时间尺度和中等窗口上比较 SP1 `columns` 与 SP2 `masterVariables`，并分别生成外包单位费率 0.75/1.00/1.25 和折扣强度 0/0.15/0.30 的实验。当前令任务外包基数 `b_j=p_j`，使用三段连续数量折扣函数。这些费率是可运行的 pilot 档位，不是最终论文校准值；正式计算前应先确认不会造成全外包或完全不外包，再冻结参数。

## 3. 固定初始列和公平比较

每个 scenario 先执行一次 `FormalExperimentRunner --action=seed`。该步骤在目标 scenario 上运行统一 ALNS 和初始列构造，并将 initial sequences、incumbent sequences 和 SHA-256 fingerprint 写入 UTF-8 seed 快照。三个算法随后读取同一快照，但仍用各自目标数据的 evaluator 重新计算列成本，不跨实例复用数值。

manifest 用 `dependsOn` 显式连接 seed run 和 solve run。seed 失败时，依赖它的求解任务写为 `BLOCKED`，不会在缺少固定起点时偷偷改用另一套初始列。已有 `SUCCESS` 标记的任务会跳过，便于服务器断点续跑。每个 solve 的 `run.properties` 同时写入 seed 文件路径和 SHA-256 fingerprint，三种算法的结果可以直接核对是否使用了完全相同的 sequence 快照。

## 4. 输出与实时监测

每个正式 run 都有独立目录。`live.log` 在求解过程中持续写入，已打开 stage heartbeat 和 node progress summary，可以实时查看 node、incumbent、bound、gap 和阶段耗时；高频 pricing 诊断默认关闭，不进入热循环。

求解结束后，核心文件包括：一行结果 `core-summary.csv`，组件调用和耗时 `components.csv`，节点过程 `nodes.csv`，最终 incumbent 列 `columns.csv`，列池聚合 `pool-summary.csv`，cut 明细 `cuts.csv`，外包决策 `outsourcing.csv`，配置快照和 Markdown 摘要。正式入口额外开启 `writeDetailedBPCArtifacts`，输出全局列池 `pool-columns.csv` 和逐机器、逐任务完工时间及成本分解 `incumbent-schedule.csv`。这两份大文件只在求解结束后构造，普通入口默认关闭，因此不影响 pricing、LP 或 branch-and-bound 热路径。

调度器还为每个子 JVM 写出 `stdout.log`、`stderr.log`、`status.txt`、`args.txt` 和成功标记。核心结果与辅助诊断分文件保存，后续汇总不需要解析超长求解日志。

## 5. 服务器运行入口

先编译项目并确保 CPLEX jar 和 native library 可用。生成实验包：

```powershell
java -cp "target/classes;D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/lib/cplex.jar" Common.FormalExperimentSuiteGenerator --dataRoot=data --outputRoot=experiment-suite/formal-v1 --casesPerSize=3 --sizes=40,50,60,100 --timeLimitSeconds=10800 --maxNodes=100000
```

启动最多四个独立 JVM：

```powershell
java -Djava.library.path="D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/bin/x64_win64" -cp "target/classes;D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/lib/cplex.jar" HEU.ExperimentBatchScheduler experiment-suite/formal-v1/manifest.tsv 4
```

`ExperimentBatchScheduler` 不在单个 JVM 中开四个求解线程，而是维持最多四个独立子 JVM；每个子 JVM 内部 CPLEX 固定为一线程。任一任务结束后，调度器立即提交下一个依赖已满足的任务。除总 `manifest.tsv` 外，生成器还在 `manifests/` 下分别生成定价比较、外包模型比较、外包价格和折扣实验入口，每个子 manifest 自带所需 seed 任务。迁移到服务器时需要携带代码、编译产物或构建脚本、data、生成后的实验包、CPLEX jar/native library，并修改服务器上的 CPLEX 路径。

## 6. 当前验证和边界

已完成 profile 回归、固定 seed 序列化、数据派生、manifest 依赖、四进程调度成功/跳过/失败传播，以及求解后 CSV 写出的 focused 测试。所有测试均通过。本轮没有启动长时间 CPLEX 正式算例，因此当前确认的是基础设施和配置口径，而不是整套实验的运行时间或论文结论。

正式大批量运行前仍建议先取每个实验块各一个小样本做服务器 smoke test，确认 CPLEX native library、`live.log` 增长、三算法 seed fingerprint 一致、输出目录和磁盘占用正常。之后再直接使用同一 manifest 扩大 `casesPerSize` 或追加 n=100 pilot。

## 7. 数据库存量与 formal-v1 的准确含义

当前原始 Tanaka 单机数据包含 `n=40,50,100,150,200,250,300,350,400,450,500` 共 11 个规模，每个规模 125 个实例，总计 1375 个原始实例。`n=60` 不是原始 benchmark 规模，而是从 100-task 实例按固定任务前缀派生的算法压力测试规模。现有多机数据中，原始规模的 `m=2/4` 基本已有完整 125 个实例；`m=3/5` 和 `n=60` 目前只准备了少量 pilot 文件。

当前 `experiment-suite/formal-v1` 使用 `casesPerSize=3`，因此只包含 39 条实例记录：`n=40/50/60` 各为 3 个 case × 3 个机器数，共 27 条；`n=100` 为 3 个 case × 4 个机器数，共 12 条。完整 manifest 的 1188 行不是 1188 个不同数据实例，而是 243 个共享 seed 任务和 945 个求解任务：定价比较 729 个，外包 formulation 比较 54 个，外包价格 81 个，折扣 81 个。243 个 seed 来自 27 个主比较实例 × 3 个时间尺度 × 3 个窗口场景；每个 seed 随后被同场景的三种定价算法复用。

因此 `formal-v1` 当前是用于验证实验结构、依赖、输出和服务器并发的 pilot 包，不是已经冻结的论文正式样本。直接把 125 个实例全部与机器数、时间尺度、窗口和三种算法做全因子会产生数万次长求解，不适合作为默认方案；但只取文件编号最前面的 3 个也缺少代表性。正式版本需要先根据 125 个实例的生成分组或可观察属性确定分层抽样，建议每个 `(n,m)` 单元先取 5--10 个代表实例，并把 n=100 作为独立 scalability/pilot，而不是继续沿用“前 3 个”的临时口径。

## 8. 与旧 VRP 输出的字段审计

旧 VRP 的 `Configure/Utility` 主要输出初始成本、root 下界、cut 后 root 下界、最终上下界、总时间、节点数、列数、各类 cut 数量和时间，以及 preprocess、初始解、route generation、add columns、column generation 和 cut separation 时间；同时打印最终 route/bid 明细。

当前 TWET 输出已经覆盖并超过其中大部分内容：`core-summary.csv` 保存状态、初始 incumbent、最终 root bound、最终上下界、gap、总时间、节点和剪枝统计、列池/cut 池规模、pricing/cut/branch 次数及解验证；`components.csv` 按 pricing engine、master LP phase、cut generator 和 brancher 给出调用次数、产出和耗时；`nodes.csv` 保存逐节点过程；`columns.csv`、`pool-columns.csv`、`incumbent-schedule.csv`、`outsourcing.csv` 和 `cuts.csv` 分别保存最终机器列、完整列池、逐任务时间与成本分解、外包决策和 cut 的 scope/memory。配置快照、实时日志、上下界一致性验证和 seed fingerprint 是旧 VRP 没有的。

本次已补齐前三个低频结构化字段。共享 seed 任务在自己的 `run.properties` 中记录构造耗时、初始/初始 incumbent 列数和 fingerprint；每次正式求解的 `core-summary.csv` 增加初始列接入耗时、root preprocessing 是否应用及其耗时、cut 前 root bound、root 新增 cut 数和 root cut separation 耗时。这些统计只在初始化、root 闭合和 cut generator 返回时更新，不进入 pricing 热循环。

route generation 与向 CPLEX 增量加列仍没有强行拆成旧 VRP 的 `dp_time/ac_time`：当前 pricing engine、master LP solve、model build 和 strong-trial setup 已经给出更适合本实现的阶段口径。除这两个旧名称没有字面一一对应外，旧 VRP 用于论文分析的核心结果、root、cut、节点、列和最终路径信息已覆盖，并且额外提供了完整列池、逐任务时间/成本分解、cut memory、配置快照、解验证和共享 seed 指纹。

## 2026-08-16 三小时时限与独立参数复核

正式求解时限由 7200 秒统一调整为 10800 秒。`TWETBPCConfig`、`FormalExperimentRunner`、`FormalExperimentSuiteGenerator` 和现有 `formal-v1` manifest 已保持一致；主 manifest 的 945 条 solve 任务和四个分组 manifest 的对应任务均显式写入 10800 秒，243 条只负责生成共享初始列的 seed 任务不设置求解时限。

独立只读智能体再次从 profile、实际 engine 装配和最近有效运行记录复核三套参数。ng-DSSR 的 nearest `floor(n/10)`、C1000/K20、`minimumNewPairsSegment`、source-aware dominance、两项 join 预筛、all-cycles completion bound、`hard=false/pricingOnly=true`、Tmid probe、root preprocessing/seed 200、Phase-I repair 和 strong phase2=0 均一致；time-indexed no-cut 与 rank-1/SRI 也没有装配错配。当前仍有少数有效值继承 `TWETBPCConfig` 默认值，例如 NG exact 5000、Tabu 300/30/50/30、DSSR 轮间 Tmid reuse、branch seed 5000 和 CPLEX `auto`。正式 runner 每次创建全新配置，因此当前实验口径确定；后续若要防止默认值演化造成 profile 漂移，可再将这些次级值显式写入 profile，本轮不改变它们。

## 2026-08-16 错误日志与输出开销复核

正式批处理的每个子 JVM 独立写 `stdout.log` 和 `stderr.log`；异常退出时 Java stack trace 保留在 `stderr.log`，`status.txt` 写入 `FAILED` 和退出码，不生成 `SUCCESS`，依赖任务标记为 `BLOCKED`。求解已经开始后发生异常时，逐事件 flush 的 `live.log` 仍保留异常前最后一个阶段。直接绕过批处理器运行 `FormalExperimentRunner` 时只有控制台 stack trace 和已经写出的部分文件，因此正式服务器实验必须通过 `ExperimentBatchScheduler` 启动。

实时记录只发生在 pricing、LP、cut、branch、node 和少量预处理阶段边界，不在 label、arc 或 PWLF 热循环中输出；node summary 每个节点最多一行，高频 pricing details 与 hot-path diagnostics 默认关闭。`pool-columns.csv` 和 `incumbent-schedule.csv` 等大文件只在正常求解结束后生成。审计发现内部已有 dual-bound 剪枝计数，但最终结构化摘要漏写，本次已将 `prunedByDualBoundCount` 补入 Markdown 和 `core-summary.csv`，不增加新的运行时统计。
