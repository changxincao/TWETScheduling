# 2026-05-24 pricing 剩余性能复查记录

这轮只做静态复查，不改代码。复查范围按当前默认主路径来定：`HeuristicPricingEngine -> GCBidirectional -> PaperDominanceGraph`，不把已经退居 fallback 的旧 `ExactPricingEngine + DominanceGraph` 当成当前主要矛盾。

先说结论。当前 pricing 主链上那些最显眼、最低级的冗余已经基本清掉了：启发式 seed 选择已经改成 top-K heap，accepted move 后的 route profile 也已经改成局部重建；双向 exact pricing 已经有 terminal-job bitset、group 级时间/成本下界、组内 lazy compaction、以及 normal label 的端点 O(1) 最小值读取。现在剩下的热点主要有两类：一类是启发式邻域枚举中“先做重计算、后做便宜过滤”的顺序问题；另一类是 `PaperDominanceGraph` 里仍然存在的结构性图维护开销。

1. `HeuristicPricingEngine` 当前最值得继续动的点，不是再改 `apply()->rebuild()`，而是把 cheap check 提前到 expensive merge 前面。现在 `evaluateRemove()`、`evaluateAdd()`、`evaluateExchange()` 都是先算 `candidateCost`，再判断 `isRemoveCompatible()` / `isInsertCompatible()`。但后者只是看分支禁弧，是 O(1) 的便宜判定；前者会走 `removeCost()` / `insertOrReplaceCost()`，其中 `insertOrReplaceCost()` 还会调 `merge3Segments()` 做函数拼接。也就是说，当前大量本来会被禁弧直接剪掉的候选，仍然先付了一次分段函数拼接成本。这是现在 heuristic pricing 里最清晰、最稳妥的下一刀。

2. `HeuristicPricingEngine` 里 `tryAddNegative()` 仍然保留了 `hasDuplicateJobs(sequence)`。从当前状态不变量看，这层大概率已经退化成防御性检查：seed 来自当前列池，tabu move 生成时又已经靠 `state.used[job]` 防止 add/exchange 产生重复 job。因此这部分不是大热点，但严格说仍然有一点重复扫描序列的冗余。是否删除可以放在禁弧 cheap check 前移之后再看。

3. `GCBidirectional` 主链已经没有明显傻瓜级冗余。当前 `joinFromBackward()` 不再扫 `0..n` 全量 terminal，而是只扫 `activeForwardTerminalJobs`；组内也会把已支配的 forward label 物理压掉，同时重算当前 live label 的 `minForwardReducedCostByLastJob` 和 `minForwardEllByLastJob`。这条线上剩下的性能问题更偏“结构性不可避免”：每个 backward label 仍然需要按 terminal group 做下界筛选，过筛后仍然要对 surviving pairs 做 join 函数最小值评估。这里我暂时没有再看到一个像前几轮那样明显、低风险、立刻该动的点。

4. `PaperDominanceGraph` 仍然是 exact pricing 里最像“还能继续提速”的地方。虽然 `roots`、邻接表和 subset candidate 过滤都已经收紧过，但 `deleteNode()` 里仍然会对每个 predecessor 收集一遍 compatible successors，再做一次 maximal frontier 过滤。它比原来的全量前驱×后继笛卡尔积已经好很多，但图规模大时，这里依然是结构性开销。另外，`findTerminalSupersetNodes()` / `findImmediateSubsetNodes()` 依旧是基于图遍历加 visited set 的在线搜索，是否还能再降，要么得进一步收紧图的 cover 关系，要么得引入更重的索引结构，这一层就不是“轻量优化”了。

5. 当前默认主路径是 `enableHeuristicPricing=true` 且 `enableBidirectionalPricing=true`。因此真正该盯的是 `HeuristicPricingEngine + GCBidirectional + PaperDominanceGraph`。旧的 `ExactPricingEngine + DominanceGraph` 还保留在配置 fallback 里，但不应再作为当前主要性能判断依据。

当前判断是：如果下一步继续做 pricing 性能优化，优先级应当是 `HeuristicPricingEngine` 里把禁弧兼容性判断前移，再看是否删掉重复 job 防御性检查；exact 侧则继续盯 `PaperDominanceGraph.deleteNode()` 的重连成本。双向 join 本身暂时没有发现新的明显冗余。

同日已先落地第一步低风险优化：`HeuristicPricingEngine.TabuRouteState` 的 `evaluateRemove()`、`evaluateAdd()`、`evaluateExchange()` 现在先做 `isRemoveCompatible()` / `isInsertCompatible()` 这类 O(1) 的禁弧兼容性检查，再决定是否进入 `removeCost()` / `insertOrReplaceCost()` 的 `merge2Segments/merge3Segments` 评估。这样可以避免本来就会被分支禁弧直接剪掉的候选先付一次分段函数拼接成本。此次不改 tabu 邻域、接受规则和 reduced-cost 增量公式，只调整 cheap check 与 expensive merge 的顺序。

验证方面，`git diff --check` 通过，`HeuristicPricingEngine.java` focused `javac` 编译通过。额外尝试运行 `HEU.SmallBPCBatchTest` 做一轮真实 heuristic pricing 路径回归，但命令行环境缺少 CPLEX runtime `ilog.concert.IloNumExpr`，因此本次停在编译验证，没有做成端到端运行。

继续清理后，`tryAddNegative()` 里的 `hasDuplicateJobs(sequence)` 也已删除。当前 heuristic pricing 的 seed 来自现有列池，而 tabu move 生成阶段又通过 `state.used[job]` 保证 add/exchange 不会把已在序列中的 job 再插入一次，因此这层重复 job 扫描已经退化成防御性检查。删除后每次尝试把负列候选放入本地池时，少做一次整序列线性扫描。当前仍保留的序列合法性检查主要是 `isSequenceCompatible()` 的分支禁弧判定和后续的 signature 去重。

2026-05-24 补充：本轮又加入了一层 root no-cut pricing 的 `pi_j=0` singleton-only 剪枝。具体做法是：当且仅当当前节点仍满足根节点、无 cut dual、无 branch dual、setup 满足三角不等式且允许等待时，若某个任务 `j` 的 `pi_j=0`，则不再允许它与其他真实 job 形成多任务列，只保留 singleton 可能性。原因是此时任意包含 `j` 的多任务列都可以删除 `j` 而不使 reduced cost 变差，所以当前这一轮 pricing 无需继续为它枚举和其他任务相连的状态。单向 `GC` 和双向 `GCBidirectional` 都加了这层预处理、注释和 `zeroDualSingletonOnlyJobs` 日志统计；双向里额外保留了 `source->j` 与 `sink->j` 这两条 singleton 生成路径，避免把合法单任务列一并剪掉。

但从实际验证看，这条优化在当前 no-outsourcing root 基准上还没有真正触发。已经用当前代码重跑 `wet021_001_2m`，以及 10 个 15 任务 no-outsourcing 子算例；single / bidirectional 的 exact pricing 日志里 `zeroDualSingletonOnlyJobs` 都是 0。也就是说，在这批 root LP 上所有 job dual 都严格大于 0，这条预处理当前只是在代码里作为安全的结构化剪枝准备好，并未带来可观察的算量下降。现阶段它更大的价值是把条件、日志和实现路径先固定下来，后续一旦出现 `pi_j=0` 的 root no-cut pricing 场景，就可以直接从日志确认是否被触发，而不需要再临时加诊断代码。

2026-05-24 再补两点后续思路。第一，双向 labeling 的中间资源理论上可以额外引入“已访问任务个数”这一维，把 `S` 集合大小当成 join / dominance 的一个资源摘要；source 和 sink 不计入，最大值可再结合 `Cmax` 做上界估计。但当前判断是这条路意义不大，因为真正控制可达深度的仍然是 completion 时间与函数域，不是访问个数本身；若只多挂一维集合大小，大概率只会增加状态和占优比较成本，暂不实现。第二，当前 root 节点在按 `pi_j` 收紧完任务时间窗以后，可以再取所有任务右端时间窗的最大值，得到一轮 pricing 专用的局部 `Cmax` / horizon。这样 midpoint 不再机械地取全局 `CmaxH/2`，而是贴近当前 root LP 真正还可能出现完成时间的区域，理论上可以缓解 no-outsourcing root 场景下 backward 半边完全长不出真实标签的问题；非根节点仍继续使用较松的全局 `CmaxH`，因为那时通常不存在同样强的动态硬窗收缩。

2026-05-24 晚些时候继续把第二条思路真正落到了代码里，并先在 `wet021_001_2m` 上做了两轮诊断。第一版是最直接的 `tMid = pricingHorizon / 2`。这版确实让 backward 从“完全没有真实标签”变成了能正常扩展和 join，但对当前 hybrid-B 结构来说切得太左：`pricingHorizon=1209, tMid=604.5` 时，forward 侧只保住了 `fw kept/dominated=10/1`，而 backward 直接膨胀到 `bw kept/dominated=54053/625941`，最终 bidirectional exact 一轮耗时上升到 `67.971s`，明显比 single 的 `20.805s` 更差。由此可见，这个局部 horizon 思路本身不是错的，但“直接对半切”不适合当前先完整跑 forward、再跑 backward 的 hybrid-B 流程。

随后把实现收成一个更保守的 root-only 版本：仍然用当前 profitable windows 的最右端点计算 `pricingHorizon`，但只有在 root dual 窗口确实收紧时才启用，并把 midpoint 右偏到 `tMid = 0.75 * pricingHorizon`，避免 backward 再次爆炸。为了支撑这个版本，还顺手补齐了两个底层稳健性修正：一是 `PiecewiseLinearFunction.copy()` 允许复制被裁成单点域的函数，二是 `mergeMinimum()` 在两侧函数只有零长度交集时改走 disjoint merge 分支，避免 local horizon 把半域裁成单点后在 dominance graph 里直接崩掉。

这版在 `wet021_001_2m` 上的结果是可接受且明显强化的：single 仍然在 root 闭合，`PaperDominanceExactPricing=12.574s`；bidirectional 也在 root 闭合，但 `BidirectionalPricing=2.136s`，日志里可以看到 `pricingHorizon=1209.0, tMid=906.75`，并且 backward / join 都真正工作了，`bw kept/dominated=343/2273`，`join pairs tried/set/lb/time/funcEval/funcPruned=481928/140384/311208/1501/28835/28835`。继续在 `wet020_001_2m` 和 `wet021_001_2m` 两个 20+ 任务 no-outsourcing 算例上复跑后，single 平均 `exact=9.946s, solve=10.740s`，bidirectional 平均 `exact=1.373s, solve=2.037s`，最终 incumbent 和 bound 保持完全一致。当前因此保留的实现不是“局部 horizon 直接二分”，而是“root-only 局部 horizon + 右偏 midpoint”。
2026-05-29 更新：早期记录中的 `pi_j=0 singleton-only` 口径已经废弃。当前所有 GC pricing 统一改为 `zeroDualExcludedJobs`：仅在根节点且没有 active cuts 时触发，预处理出 `pi_j=0` 的 job 后直接加入 source/sink 初始 `visitedSet`，后续 reachable set 只按父 reachable、visited 和 direct feasibility 过滤，不再允许 singleton 旁路。双向 join 的 visited 交集检查同步忽略这些 source/sink 共同预标记的 excluded job，避免把非真实访问标记误判为路径冲突。代码已同步到 `GC`、`GCBidirectional`、`GCNGBBStyleBidirectional`、`GCBBStyleBidirectionalFullDomain`、`GCBBAsymmetricBidirectional` 和 `GCBBStyleBidirectionalFullDomainNodeJoin`。

## 2026-07-17 启发式 pricing 有效搜索与空转诊断

当前结论不是“启发式 pricing 大部分时间无用”。按 50-job 两个完整 no-SRI 日志统计，返回至少一列的调用占启发式耗时约 75%--81%。但产出高度集中：`addedColumns>100` 的调用只占约 14%--15% 的时间，却贡献约 78%--85% 的全部新增列；相反，`addedColumns=0` 或不超过 10 的调用消耗 46%--64% 的时间，只贡献约 2%--3% 的列。这里的主要浪费位于低产调用和单个 seed 的搜索尾部，而不是 seed 收集、排序或列构造。

旧 50-2 逐 10 步日志的离线模拟显示：若一次调用前 20 步合计产出不超过 175 条，则跳过后 30 步，可省该批日志约 18.2% 的启发式搜索时间，仅少 21/21121 条候选，约 0.10%。但这是调用级汇总，若直接实现需要把 30 个 seed 都先跑 20 步并保存状态，控制流偏重，暂不采用。

因此新增了只在 `heuristicPricingDiagnostics` 打开时生效的诊断：记录所选 seed 中正值列数量、heuristic/exact/other 来源，以及每个 seed 前 20 步与剩余步骤是否产生负列。最新 40-2 root-only 采样共 59 次启发式调用、1752 个 seed：1066 个 seed 前 20 步无产出，其中只有 3 个在后续恢复产出，复活率约 0.28%；前 20 步有产出的 686 个 seed 中，345 个后续仍有产出。所选 seed 仅 306/1752 为当前正值列，来源则为 heuristic 1554、exact 93、other 105，说明当前 lowest-reduced-cost seed 几乎被历史启发式列占满。

由此得到两个后续候选。第一，最直接且实现简单的是单 seed 固定规则：至少跑 20 步；若前 20 步一条新负列也没有，则结束该 seed，其他 seed 和 exact pricing 流程不变。它不影响 BPC 正确性，只改变启发式搜索路径；按当前样本看误伤概率很低，但仍需在多个 40/50-job 算例完整 A/B 后才能默认开启。第二，可以测试给当前 LP 正值列或最近 exact 列保留少量 seed 配额，避免 30 个 seed 长期被历史 heuristic 列占满；该方向目前只有来源统计，没有收益证据，暂不改排序规则。

### 单 seed 前 20 步零产出提前停止 A/B

已增加独立开关 `heuristicPricingStopUnproductiveSeedAfter20`，默认关闭。启用后，每个 seed 仍按原规则运行；只有完成前 20 次 tabu 迭代且本 seed 尚未向本次调用的候选集合加入任何新负列时，才结束该 seed。已有产出的 seed、其他 seed、后续启发式调用及 exact pricing 均保持原流程。判断直接使用本地负列候选集合的增量，不依赖诊断统计开关。

40-2 root-only 同配置 A/B 中，关闭/开启后的 LP bound 均为 22490，incumbent 均为 22582，结果有效。总时间由 71.869s 降到 65.463s，root node 时间由 46.569s 降到 40.131s，启发式 pricing 由 25.474s/60 次降到 20.026s/52 次，约减少 21.4%；tabu 迭代由 54879 降到 43661，约减少 20.4%，共提前结束 903 个无产出 seed。pool 为 12122 对 12043，整体列规模接近。

50-2 root-only 对照中，LP bound 同为 39364.5，incumbent 同为 39598。历史关闭口径的 root node 为 243.263s，启发式 pricing 为 96.307s/149 次；开启后分别为 238.575s 和 90.687s/121 次，root 约快 1.9%，启发式约快 5.8%。但 pool 从 22308 增到 24457，master LP 时间基本不变，较大的 RMP 抵消了部分启发式收益。

当前结论是这条规则确实可以削减无效 seed 尾部，两个算例均保持相同 root bound 并减少启发式耗时，但端到端收益受列生成路径和 RMP 规模影响，幅度约为 1.9%--8.9%。因此暂时保留独立开关且默认关闭；至少还需要一个 50-3 算例和完整分支树 A/B，确认节点数与最终总时间不退化后，再决定是否默认开启。

### 启发式单次返回列少的机制

当前一次 HeuristicPricing 调用从 restricted RMP 中按 reduced cost 选择 30 条兼容 seed，每条 seed 最多做 50 次 tabu 迭代。每次迭代会枚举全部 REMOVE、未访问 job 的全部 ADD 和 EXCHANGE，但只保留 reduced cost 最好的一个 move、沿这一条轨迹前进一步，并只把该步形成的一个序列送入负列候选池。其他已完成成本评价的负邻居不会作为列保留。因此默认设置下一次调用理论上只检查约 30×(1+50)=1530 个轨迹状态；再经过 active signature/本轮 signature 去重、负 reduced-cost 判断、分支兼容和必要的 dual-window 真成本复核后，临近闭合时只返回 0--5 条列是正常结果。maxHeuristicPricingColumns=1500 和 local pool=5000 通常不是限制来源。

当前最直接的后续实验不是继续增大 seed、迭代数或返回上限，而是在 findBestMove 扫描时保留静态 top-L 个负 move：搜索状态仍只应用最优 move，但把其余 top-L 邻居对应的序列也送入现有去重和真成本检查。这样可复用已经支付的邻域评价成本，提高每轮列产出；风险是增加较弱列和 RMP 规模，应使用固定 L=3/5 做完整树 A/B。该思路尚未实现。
### Seed 同 reduced-cost 排序与非 best 负邻居诊断

本轮先不实现 top-L 邻居回收，只调整 seed 的同 reduced-cost 排序：仍先按 reduced cost 从小到大；相同则优先当前 LP 正值列，再优先任务数更多的列，最后按 column ID。Tabu 的 move 选择、状态更新和最终列返回均不变。40-2 root-only 与上面的 stop20-off 基线保持同一配置，bound/incumbent 仍为 22490/22582；root node 时间由 46.569s 降到 34.366s，HeuristicPricing 由 25.474s/60 次降到 18.787s/53 次，pool 由 12122 变为 14271。该单次结果说明新排序在本例中有正收益，但 seed 改变会连带改变列生成和 LP 路径，不能把 26.2% 的 node 降幅解释为稳定常数收益，后续完整树实验再判断是否默认长期保留。

同时增加仅在 `heuristicPricingDiagnostics` 打开时生效的负邻居计数，不构造这些非 best move 的 sequence，也不把它们加入候选池或主问题。此次 53 次 HeuristicPricing（含 3 次 FindFeasible）共评价到 4,979,245 个负 move，其中最终被应用的 best move 为 15,340 个，剩余非 best 负 move 原始上界为 4,963,905，占 99.692%。普通 50 次调用的非 best 计数平均 95,893.5，中位数 61，P90 为 331,042，最大 859,727，说明大量机会集中在 root 前段少数调用。这个数是 move 评价次数，不是唯一 sequence 数；它尚未扣除同一路径在不同 seed/迭代重复出现、active-RMP 重复、当前调用内 signature 重复、分支兼容和 dual-window 真成本复核，因此只能证明“被丢弃的负邻居很多”，不能直接声称可新增约 496 万条列。若后续真正实现，应只保留固定 top-L 并走现有完整过滤，不能全量收集。

### Seed 排序多算例 A/B 补充

本轮只比较 seed 同 reduced-cost 时的顺序变化，不继续细化非 best 负 move 统计。新顺序为：先按 reduced cost，再优先当前 LP 正值列，再优先较长序列，最后按 column ID。排序本身的计算开销可以忽略，实际影响来自 seed 改变后生成列批次、LP dual 路径和后续 pricing 轮次发生变化。

40-2 同配置 root-only 对照中，root node 由 46.569s 降到 34.366s，约减少 26.2%；总时间由 71.869s 降到 56.694s，约减少 21.1%；HeuristicPricing 由 25.474s/60 次降到 18.787s/53 次。pool 从 12122 增到 14271，bound/incumbent 均保持 22490/22582。

40-3 使用旧 `HeuristicPricingEngine.class` 与新 class 做了严格 class-only A/B，其余 class、命令和配置完全相同。root node 由 19.480s 降到 18.132s，约减少 6.9%；总时间由 34.661s 降到 34.108s，约减少 1.6%；HeuristicPricing 总时间均为 9.493s，但调用次数由 37 降到 34；LP 时间由 8.084s 降到 6.494s，约减少 19.7%。pool 从 8154 增到 8502，bound/incumbent 均保持 15611.75/15675。

50-2 与当天改动前同配置记录相比，root node 由 243.263s 降到 195.703s，约减少 19.5%；总时间由 304.393s 降到 255.962s，约减少 15.9%；LP 时间由 120.881s/189 次降到 69.294s/163 次，约减少 42.7%。HeuristicPricing 调用由 149 次降到 123 次，但总时间反而由 96.307s 增至 101.807s，说明本例提速不是单次启发式更快，而是更早生成了对 RMP 有用的列，减少了 LP/pricing 轮次。pool 从 22308 增到 23629，bound 保持 39364.5，incumbent 从 39598 改善到 39581。该组不是 class-only 严格 A/B，因此主要作为趋势证据。

当前结论是保留新顺序。三个算例都没有观察到时间退化，root 改善约为 6.9%--26.2%，总时间改善约为 1.6%--21.1%；但它不是稳定的固定比例提速。主要代价是 pool 通常增加约 4%--18%，完整分支树上的收益仍取决于增加的列能否抵消后续 master 成本。

### 非 best 负 move 的逐迭代分布

保持上一节的新 seed 顺序不变，只在 `heuristicPricingDiagnostics` 开启时增加逐 tabu 迭代计数；不构造非 best move 的 sequence，也不改变 move 选择、Tabu 轨迹或返回列。40-2 root-only 结果仍为 pool=14271、bound/incumbent=22490/22582，与新顺序基线一致；总时间受本机并发负载影响，不作为本次判断依据。

53 次 HeuristicPricing 共执行 51427 次 tabu 迭代，记录 4963905 次非 best 负 move，平均每轮 96.52 个，最大 839 个。但分布高度不均匀：33334 轮即 64.82% 为 0；1 个占 1.55%；2--4 个占 2.05%；5--9 个占 1.55%；10--49 个占 5.21%；50--99 个占 6.24%；100--499 个占 8.97%；至少 500 个占 9.62%。只有 18093 轮存在非 best 负 move；在这些非零轮中平均为 274.36 个。

按迭代位置看，1--10、11--20、21--30、31--40、41--50 轮的平均非 best 负 move 数分别为 91.62、104.50、102.43、134.43、23.68；存在至少一个的比例分别为 41.90%、34.41%、29.99%、38.37%、24.44%。该结果说明机会不是均匀分布，前 40 轮少数重尾邻域贡献了绝大多数候选，最后 10 轮明显下降。

这些原始负 move 不等于“一定有用的列”。计数发生在 signature 去重和 dual-window 真实成本复核之前，同一 sequence 可能在不同 seed、不同迭代重复出现，也可能已在 active RMP 或本次候选池中；若启用了 dual window，窗口口径下为负的 move 回到真实成本后还可能不负。即使是真实、唯一的负 reduced-cost 列，批量加入大量高度相似的列也会扩大 RMP，未必降低端到端时间。因此后续若实验，应只保留每轮除 best 外的固定 top-3/top-5，构造 sequence 后完整复用现有 `tryAddNegative()` 的 active 去重、调用内去重和真实成本复核，再做完整树 A/B；不应把约 496 万次原始 move 全量入池。

### 全量非 best 负 move 的有界候选池 A/B

本轮按“最多保留 5000 条候选，最终返回最好的 1500 条”实现了独立实验开关 `heuristicPricingCollectNonBestNegativeMoves`，默认关闭。开启后，每轮 REMOVE/ADD/EXCHANGE 中所有负 reduced-cost move 都可以竞争本次调用的候选池，但 Tabu 状态仍只应用原来的 best move，因此状态轨迹本身不变。5000 被解释为保留容量而不是搜索停止条件：候选池满后用最差候选堆淘汰当前第 5000 名，并继续当前 seed 和后续 seed。否则得到的只是按 seed/迭代顺序遇到的前 5000 条，不是全局最好的 5000 条。为控制开销，常规/compact-window 路径先用当前第 5000 名的 reduced cost 和序列长度做廉价预筛，只有可能进入池的 move 才复制 sequence、做 signature 去重并进入现有列检查；dual-window 路径不能用受限 reduced cost 提前淘汰，仍须先回刷真实成本。

40-2 root-only 严格 A/B 中，两组均关闭单 seed 前 20 步提前停止，其他 runner、ALNS、strong branching 和 ng-DSSR 配置完全一致。关闭该开关时总时间为 73.854s，root node 为 44.581s，master LP 为 15.323s/97 次，HeuristicPricing 为 24.153s/53 次并加入 13909 列，exact 为 2.834s/10 次并加入 353 列，最终 pool=14271，bound/incumbent=22490/22582。开启后在 180s 上限结束，总时间 180.977s，root node 已达到 155.793s，master LP 增至 89.733s/128 次，HeuristicPricing 增至 53.793s/100 次并加入 86979 列，exact 也没有减少而是增至 5.339s/13 次，pool 膨胀到 87060；bound/incumbent 仍为 22490/22582，说明没有获得 relaxation 或定价轮次收益。

开启组的 100 次启发式调用共观察 35427994 个负 move，其中 33725363 个被当前第 5000 名直接挡掉，仍构造了 1702631 条 sequence，并发生 1132924 次候选替换；各次调用的候选池合计保留 284751 条，最终向主问题返回 86979 条。主要退化不只是收集逻辑本身翻倍了启发式时间，更重要的是每轮大量返回高度相似的弱负列，使普通 RMP 和 strong trial RMP 都显著变大，master LP 时间约增至 5.86 倍，而 exact 次数没有下降。

当前结论是该全量策略保留为默认关闭的诊断开关，不作为生产配置。若把“首次达到 5000 即停止”作为硬搜索预算，计算会更便宜，但结果受 seed 顺序强烈影响，不能再称为“最后选全搜索空间中最好的 1500 条”。后续若还测试非 best 邻居，只应考虑每轮固定 top-3/top-5 或更严格的多样性筛选，避免再次把候选池和 RMP 灌满。

### 候选池与单次返回上限统一为 300 的 A/B

为区分候选规模与非 best move 收集本身的影响，在同一 40-2 root-only 配置下补做了 300/300 对照。三组均得到相同的 root bound/incumbent 22490/22582，且 valid=true。原始默认路径（不收集非 best，5000/1500）总时间/root 为 73.854s/44.581s，pool=14271，Master LP=15.323s，HeuristicPricing=24.153s/53 次。将候选池和单次返回上限都收紧到 300、仍不收集非 best 后，总时间/root 降为 53.798s/33.046s，pool=7188，Master LP=9.699s，HeuristicPricing=18.132s/64 次；说明控制单轮列规模可以减少 RMP 和强分支 LP 负担，收益明确。

同样采用 300/300，但打开非 best 负 move 收集后，总时间/root 为 124.607s/92.823s，pool=29254，Master LP=25.090s，HeuristicPricing=60.252s/135 次。虽然比 5000/1500 全量收集的 180.977s 时间上限、pool=87060 和 Master LP=89.733s 明显改善，但仍远差于 300/300 且不收集非 best。原因是每次调用仍会扫描全部非 best 邻居并尽量返回 300 条，导致调用轮数和累计列数继续增加，exact 调用也没有减少。

当前因此把 heuristicPricingPoolSize 与 maxHeuristicPricingColumns 的默认值统一改为 300；heuristicPricingCollectNonBestNegativeMoves 继续默认关闭。实验目录分别为 ab-heur-nonbestpool-300-40-2-off-20260717a 和 ab-heur-nonbestpool-300-40-2-on-20260717a。


进一步按调用拆分后，300/300 且关闭非 best 的默认路径共调用 HeuristicPricing 64 次，合计加入 7084 条，平均 110.69 条、中位数仅 9 条；其中只有前 20 次加满 300，之后 44 次合计只加 1084 条，13 次返回 0。开启非 best 后，普通 HeuristicPricing 调用增至 130 次，合计加入 27576 条，平均 212.12 条、中位数 300；前 90 次连续加满 300。另有 5 次 repair FindFeasible 也全部加满 300，最终启发式共加入 29076 条。也就是说，退化的直接原因仍是非 best 邻居长期提供大量浅负、相似列，使 300 上限在多数轮次持续饱和；这既把总列量放大约 4.1 倍，也把普通启发式调用从 64 次推到 130 次。


继续保留候选池 300、仅把单次返回上限降到 50 后，40-2 root-only 仍得到相同 bound/incumbent 22490/22582 和 valid=true，但总时间/root 退化到 174.621s/141.516s。Pool 降到 9642，Master LP 仅 11.388s，说明限制返回列确实消除了大部分 LP 膨胀；代价是启发式调用达到 223 次、HeuristicPricing=121.740s，exact 也有 18 次。普通启发式 218 次中有 180 次加满 50，另有 5 次 repair 全部加满，合计新增 9539 条。与返回 300 时的 135 次调用、60.252s 启发式相比，把同一批负候选拆成 50 条小批次会反复重跑完整 seed/Tabu 邻域，重复搜索成本远大于 LP 节省。因此默认返回上限继续保持 300，不改为 50；全量非 best 收集仍默认关闭。

继续按完全相同口径测试候选池 300、单次返回上限 100。40-2 root-only 仍为 bound/incumbent 22490/22582、valid=true，nodeTime/总时间为 59.954s/77.373s，明显优于返回 50 的 141.516s/174.621s，也优于全量非 best 返回 300 的 92.823s/124.607s，但仍慢于默认关闭非 best 收集时的 33.046s/53.798s。返回 100 时普通启发式 150 次，其中 122 次加满 100，平均每次加入 83.86 条；HeuristicPricing 为 48.603s/151 calls，Master LP 为 7.734s/193 calls，exact 为 2.246s/10 calls，pool=12821。该结果说明在全量非 best 实验模式下，100 条比 50 条更好地平衡了重复 Tabu 搜索与 RMP 批量大小；但全量扫描非 best 邻域本身仍有明显额外成本，因此不据此修改默认配置，默认继续关闭非 best 收集并返回最多 300 条轨迹列。

进一步比较默认关闭非 best 收集与全量非 best 返回 100，可以确认差距不来自 exact 或 Master LP。后者额外加入 5595 条启发式负列，只把 exact 从 13 次、3.664s 降到 10 次、2.246s，并把 Master LP 从 9.699s 降到 7.734s；但启发式调用从 64 次增至 151 次，时间从 18.132s 增至 48.603s，最终 nodeTime 多 26.908s。原因是负 reduced cost 只对应生成时的当前 dual，不代表该列在重解后的新 dual 下仍有作用；同一 seed 邻域产生的大量 non-best 列结构高度相关，真正进入基或改变 dual 方向的列很少。PC 每次收到一批启发式列后立即重解 LP，并从前置启发式重新开始 pricing，因此全量 non-best 模式会形成“当前 dual 下找很多相似负列—加入一批—dual 改变—重新完整搜索”的长尾。默认模式只保留实际采用的 best-move 轨迹，搜索更早停止，列也更分散；虽然总列数更少，闭合效率反而更高。

### 标准轨迹保护与每 seed 非 best 多样化池

为避免上一版全局 non-best top-K 被少数 seed 的高度相似邻居占满，本轮把标准轨迹和额外邻居完全拆开。标准候选池固定保持 OFF+300 的原始语义：仍只接收 seed 初态和每轮实际采用的 best move，达到 300 条后停止本次搜索。打开实验开关时，每轮邻域评价只轻量暂存 reduced cost 最小的 3 个 move，确定实际采用的 best move 后排除它，最多把另外 2 个 move 构造成 sequence；每条 seed 使用独立 top-10 池，最后把各 seed 的附加列排序、按 signature 去重后追加到标准列之后。附加池不参与 Tabu 状态转移，不挤占标准 300 条，也不改变标准搜索的停止条件。配置为 `heuristicPricingNonBestMovesPerIteration=2` 和 `heuristicPricingNonBestColumnsPerSeed=10`，总附加列理论上不超过 30×10=300；总开关继续默认关闭。

关闭开关后用最新 class 重跑 40-2 root-only，得到 pool=7188、LP=104 次、pricing=77 次/新增7176、HeuristicPricing=64 次/新增7084、exact=13 次/新增92，bound/incumbent=22490/22582。这些结构化指标与 2026-07-17 的 OFF+300 记录逐项一致，证明新代码在开关关闭时没有改变标准列集合和求解路径；本机负载差异使 nodeTime 从历史 33.046s 变为 43.223s，不作为算法差异。

打开每 seed top-10、每轮 runner-up top-2 后，结果仍为 bound/incumbent=22490/22582、valid=true，但 pool 增至9929，LP 增至113次，pricing 增至86次/新增9917，HeuristicPricing 为67次/新增9798，normal exact 增至16次（node summary 含 repair 入口共19次），nodeTime=50.621s。新策略确实把旧全局 non-best 模式的 pool=29254 和 HeuristicPricing=135次大幅压下来了，但相对 OFF+300 仍多生成2741条列，并增加9次LP和3次exact，没有减少闭合轮次。前几轮每次通常只追加约26--56条去重后的 extra，但这些列仍不足以抵消更大的 RMP 和改变后的 dual 路径。

当前结论是实现保留为默认关闭的受控实验开关，不作为最好配置。结果说明“按 seed 配额保证多样性”能够解决少数 seed 垄断全局候选池的问题，却仍不能证明 non-best 邻居对后续 LP 有足够的边际价值；在这个算例上，标准 best-move 轨迹仍更有效。实验目录为 `ab-heur-protected-off300-equivalence-40-2-20260718e` 和 `ab-heur-protected-perseed10-top2-40-2-on-20260718a`。
### 每 seed 多样化池的 40-3 补充 A/B

继续用相同 root-only 配置测试 `data/40-3/wet040_001_3m`。原始时间算例上，关闭/开启每 seed top-10 后的 bound/incumbent 均为15611.75/15675、valid=true。开启后 root node 从32.140s降到30.413s，约改善5.4%；pricing 从48次、18.329s降到35次、13.167s，HeuristicPricing 从43次、16.579s降到31次、11.651s，normal exact 从5次、1.749s降到4次、1.516s。代价是 pool 从6653增到7771，虽然LP轮数从83降到71，但更大的RMP使LP时间从11.937s升到15.363s。这个算例中，额外列确实减少了后续启发式和exact重启，收益刚好超过了RMP增大成本。

### 每 seed 多样化池的 50-2 补充 A/B

在 `data/50-2/wet050_001_2m` 上继续做相同 root-only 对照，solve limit 只为避免截断而提高到600s，其他配置与40-job实验一致。关闭/开启后的 bound/incumbent 均为44353/44607、valid=true。开启每 seed top-10 后，root node 从253.310s增至316.055s，约退化24.8%；总时间从314.053s增至376.509s。Pool从11372增至16421，约增加44.4%；LP从177次/49.153s增至197次/77.521s，pricing从163次/200.678s增至186次/234.474s，HeuristicPricing从137次/177.202s增至157次/210.150s，normal exact从26次/23.476s增至29次/24.324s。

该结果说明在50-job上，按seed限制多样性仍不能保证额外列有效。附加列没有减少heuristic或exact闭合轮次，反而同时扩大正式RMP和strong trial RMP；增加的LP成本是主要退化来源。结合40-2退化、原始40-3约5.4%改善、40-3 timeX10退化，当前证据已足够支持继续默认关闭该策略，不再扩大测试规模。实验目录为 `ab-heur-protected-off300-50-2-20260718a` 与 `ab-heur-protected-perseed10-top2-50-2-on-20260718a`。

这里需要区分“单次相同 dual”与“完整列生成过程”。在第一次启发式调用中，ON 确实完整保留 OFF 的标准轨迹列：50-2 首次 OFF 返回291条标准列，ON仍返回同口径的291条，再追加22条额外列。固定当前RMP和dual时，ON列集是OFF列集的超集；但这些列加入后PC会立即重解LP，并从前置启发式重新开始pricing。此后两组的dual、seed reduced cost排序、Tabu best move和后续标准轨迹全部分叉，ON完整运行的最终列池不再保证包含OFF完整运行的最终列池。因此“多列不会使固定RMP目标变差”成立，但不能推出列生成轮数和运行时间不会变差。50-2中ON的pool增加44.4%，heuristic调用137->157、exact调用26->29、LP调用177->197，说明附加列没有替代后续定价，反而造成更多重解和更大的正式/strong-trial RMP；这才是退化的直接原因。

这些附加列自身为当前dual下的负reduced-cost列，但每轮只从同一seed、同一当前sequence的一组ADD/REMOVE/EXCHANGE邻域里选择runner-up，因此覆盖任务和弧结构高度相关。它们在当前dual下分别看都有改善方向，但进入同一个RMP后会竞争相同coverage/machine资源，通常只有少数能进入基，其余很快随dual变化失效。50-2的分项时间支持这一解释：普通after-pricing重解由2.521s/136次增至4.140s/156次；strong branching仍同为40次trial，但light-repair RMP由46.439s增至73.178s，单次由1.161s增至1.829s。与此同时exact新增列由166条降为111条且调用26->29，说明附加列既没有覆盖后续exact需求，也把正式和trial RMP都做重了。

当前决定保持 heuristicPricingCollectNonBestNegativeMoves=false，主线继续只返回标准 best-move 轨迹列；源码默认值和 runner 均未显式开启，因此无需额外代码修改，实验实现保留用于复现。若以后继续研究，优先方向不是直接改变 non-best 的静态数量，而是先按 OFF 轨迹加列并重解 LP，再用新 dual 重新计算暂存 runner-up 的 reduced cost，仅激活仍为负且与 active/标准列结构差异足够大的列。该方案直接针对“旧 dual 下负、重解后失效”和“同邻域高度相关”两个问题，但需要跨重解的候选生命周期及多样性定义，当前没有稳定收益证据，暂不实现。
