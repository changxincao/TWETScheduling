# 2026-05-24 pricing 剩余性能复查记录

这轮只做静态复查，不改代码。复查范围按当前默认主路径来定：`HeuristicPricingEngine -> GCBidirectional -> PaperDominanceGraph`，不把已经退居 fallback 的旧 `ExactPricingEngine + DominanceGraph` 当成当前主要矛盾。

先说结论。当前 pricing 主链上那些最显眼、最低级的冗余已经基本清掉了：启发式 seed 选择已经改成 top-K heap，accepted move 后的 route profile 也已经改成局部重建；双向 exact pricing 已经有 terminal-job bitset、group 级时间/成本下界、组内 lazy compaction、以及 normal label 的端点 O(1) 最小值读取。现在剩下的热点主要有两类：一类是启发式邻域枚举中“先做重计算、后做便宜过滤”的顺序问题；另一类是 `PaperDominanceGraph` 里仍然存在的结构性图维护开销。

1. `HeuristicPricingEngine` 当前最值得继续动的点，不是再改 `apply()->rebuild()`，而是把 cheap check 提前到 expensive merge 前面。现在 `evaluateRemove()`、`evaluateAdd()`、`evaluateExchange()` 都是先算 `candidateCost`，再判断 `isRemoveCompatible()` / `isInsertCompatible()`。但后者只是看分支禁弧，是 O(1) 的便宜判定；前者会走 `removeCost()` / `insertOrReplaceCost()`，其中 `insertOrReplaceCost()` 还会调 `merge3Segments()` 做函数拼接。也就是说，当前大量本来会被禁弧直接剪掉的候选，仍然先付了一次分段函数拼接成本。这是现在 heuristic pricing 里最清晰、最稳妥的下一刀。

2. `HeuristicPricingEngine` 里 `tryAddNegative()` 仍然保留了 `hasDuplicateJobs(sequence)`。从当前状态不变量看，这层大概率已经退化成防御性检查：seed 来自当前列池，tabu move 生成时又已经靠 `state.used[job]` 防止 add/exchange 产生重复 job。因此这部分不是大热点，但严格说仍然有一点重复扫描序列的冗余。是否删除可以放在禁弧 cheap check 前移之后再看。

3. `GCBidirectional` 主链已经没有明显傻瓜级冗余。当前 `joinFromBackward()` 不再扫 `0..n` 全量 terminal，而是只扫 `activeForwardTerminalJobs`；组内也会把已支配的 forward label 物理压掉，同时重算当前 live label 的 `minForwardReducedCostByLastJob` 和 `minForwardEllByLastJob`。这条线上剩下的性能问题更偏“结构性不可避免”：每个 backward label 仍然需要按 terminal group 做下界筛选，过筛后仍然要对 surviving pairs 做 join 函数最小值评估。这里我暂时没有再看到一个像前几轮那样明显、低风险、立刻该动的点。

4. `PaperDominanceGraph` 仍然是 exact pricing 里最像“还能继续提速”的地方。虽然 `roots`、邻接表和 subset candidate 过滤都已经收紧过，但 `deleteNode()` 里仍然会对每个 predecessor 收集一遍 compatible successors，再做一次 maximal frontier 过滤。它比原来的全量前驱×后继笛卡尔积已经好很多，但图规模大时，这里依然是结构性开销。另外，`findTerminalSupersetNodes()` / `findImmediateSubsetNodes()` 依旧是基于图遍历加 visited set 的在线搜索，是否还能再降，要么得进一步收紧图的 cover 关系，要么得引入更重的索引结构，这一层就不是“轻量优化”了。

5. 当前默认主路径是 `enableHeuristicPricing=true` 且 `enableBidirectionalPricing=true`。因此真正该盯的是 `HeuristicPricingEngine + GCBidirectional + PaperDominanceGraph`。旧的 `ExactPricingEngine + DominanceGraph` 还保留在配置 fallback 里，但不应再作为当前主要性能判断依据。

当前判断是：如果下一步继续做 pricing 性能优化，优先级应当是 `HeuristicPricingEngine` 里把禁弧兼容性判断前移，再看是否删掉重复 job 防御性检查；exact 侧则继续盯 `PaperDominanceGraph.deleteNode()` 的重连成本。双向 join 本身暂时没有发现新的明显冗余。

同日已先落地第一步低风险优化：`HeuristicPricingEngine.TabuRouteState` 的 `evaluateRemove()`、`evaluateAdd()`、`evaluateExchange()` 现在先做 `isRemoveCompatible()` / `isInsertCompatible()` 这类 O(1) 的禁弧兼容性检查，再决定是否进入 `removeCost()` / `insertOrReplaceCost()` 的 `merge2Segments/merge3Segments` 评估。这样可以避免本来就会被分支禁弧直接剪掉的候选先付一次分段函数拼接成本。此次不改 tabu 邻域、接受规则和 reduced-cost 增量公式，只调整 cheap check 与 expensive merge 的顺序。

验证方面，`git diff --check` 通过，`HeuristicPricingEngine.java` focused `javac` 编译通过。额外尝试运行 `HEU.SmallBPCBatchTest` 做一轮真实 heuristic pricing 路径回归，但命令行环境缺少 CPLEX runtime `ilog.concert.IloNumExpr`，因此本次停在编译验证，没有做成端到端运行。

继续清理后，`tryAddNegative()` 里的 `hasDuplicateJobs(sequence)` 也已删除。当前 heuristic pricing 的 seed 来自现有列池，而 tabu move 生成阶段又通过 `state.used[job]` 保证 add/exchange 不会把已在序列中的 job 再插入一次，因此这层重复 job 扫描已经退化成防御性检查。删除后每次尝试把负列候选放入本地池时，少做一次整序列线性扫描。当前仍保留的序列合法性检查主要是 `isSequenceCompatible()` 的分支禁弧判定和后续的 signature 去重。

2026-05-24 补充：本轮又加入了一层 root no-cut pricing 的 `pi_j=0` singleton-only 剪枝。具体做法是：当且仅当当前节点仍满足根节点、无 cut dual、无 branch dual、setup 满足三角不等式且允许等待时，若某个任务 `j` 的 `pi_j=0`，则不再允许它与其他真实 job 形成多任务列，只保留 singleton 可能性。原因是此时任意包含 `j` 的多任务列都可以删除 `j` 而不使 reduced cost 变差，所以当前这一轮 pricing 无需继续为它枚举和其他任务相连的状态。单向 `GC` 和双向 `GCBidirectional` 都加了这层预处理、注释和 `zeroDualSingletonOnlyJobs` 日志统计；双向里额外保留了 `source->j` 与 `sink->j` 这两条 singleton 生成路径，避免把合法单任务列一并剪掉。

但从实际验证看，这条优化在当前 no-outsourcing root 基准上还没有真正触发。已经用当前代码重跑 `wet021_001_2m`，以及 10 个 15 任务 no-outsourcing 子算例；single / bidirectional 的 exact pricing 日志里 `zeroDualSingletonOnlyJobs` 都是 0。也就是说，在这批 root LP 上所有 job dual 都严格大于 0，这条预处理当前只是在代码里作为安全的结构化剪枝准备好，并未带来可观察的算量下降。现阶段它更大的价值是把条件、日志和实现路径先固定下来，后续一旦出现 `pi_j=0` 的 root no-cut pricing 场景，就可以直接从日志确认是否被触发，而不需要再临时加诊断代码。

2026-05-24 再补两点后续思路。第一，双向 labeling 的中间资源理论上可以额外引入“已访问任务个数”这一维，把 `S` 集合大小当成 join / dominance 的一个资源摘要；source 和 sink 不计入，最大值可再结合 `Cmax` 做上界估计。但当前判断是这条路意义不大，因为真正控制可达深度的仍然是 completion 时间与函数域，不是访问个数本身；若只多挂一维集合大小，大概率只会增加状态和占优比较成本，暂不实现。第二，当前 root 节点在按 `pi_j` 收紧完任务时间窗以后，可以再取所有任务右端时间窗的最大值，得到一轮 pricing 专用的局部 `Cmax` / horizon。这样 midpoint 不再机械地取全局 `CmaxH/2`，而是贴近当前 root LP 真正还可能出现完成时间的区域，理论上可以缓解 no-outsourcing root 场景下 backward 半边完全长不出真实标签的问题；非根节点仍继续使用较松的全局 `CmaxH`，因为那时通常不存在同样强的动态硬窗收缩。

2026-05-24 晚些时候继续把第二条思路真正落到了代码里，并先在 `wet021_001_2m` 上做了两轮诊断。第一版是最直接的 `tMid = pricingHorizon / 2`。这版确实让 backward 从“完全没有真实标签”变成了能正常扩展和 join，但对当前 hybrid-B 结构来说切得太左：`pricingHorizon=1209, tMid=604.5` 时，forward 侧只保住了 `fw kept/dominated=10/1`，而 backward 直接膨胀到 `bw kept/dominated=54053/625941`，最终 bidirectional exact 一轮耗时上升到 `67.971s`，明显比 single 的 `20.805s` 更差。由此可见，这个局部 horizon 思路本身不是错的，但“直接对半切”不适合当前先完整跑 forward、再跑 backward 的 hybrid-B 流程。

随后把实现收成一个更保守的 root-only 版本：仍然用当前 profitable windows 的最右端点计算 `pricingHorizon`，但只有在 root dual 窗口确实收紧时才启用，并把 midpoint 右偏到 `tMid = 0.75 * pricingHorizon`，避免 backward 再次爆炸。为了支撑这个版本，还顺手补齐了两个底层稳健性修正：一是 `PiecewiseLinearFunction.copy()` 允许复制被裁成单点域的函数，二是 `mergeMinimum()` 在两侧函数只有零长度交集时改走 disjoint merge 分支，避免 local horizon 把半域裁成单点后在 dominance graph 里直接崩掉。

这版在 `wet021_001_2m` 上的结果是可接受且明显强化的：single 仍然在 root 闭合，`PaperDominanceExactPricing=12.574s`；bidirectional 也在 root 闭合，但 `BidirectionalPricing=2.136s`，日志里可以看到 `pricingHorizon=1209.0, tMid=906.75`，并且 backward / join 都真正工作了，`bw kept/dominated=343/2273`，`join pairs tried/set/lb/time/funcEval/funcPruned=481928/140384/311208/1501/28835/28835`。继续在 `wet020_001_2m` 和 `wet021_001_2m` 两个 20+ 任务 no-outsourcing 算例上复跑后，single 平均 `exact=9.946s, solve=10.740s`，bidirectional 平均 `exact=1.373s, solve=2.037s`，最终 incumbent 和 bound 保持完全一致。当前因此保留的实现不是“局部 horizon 直接二分”，而是“root-only 局部 horizon + 右偏 midpoint”。
2026-05-29 更新：早期记录中的 `pi_j=0 singleton-only` 口径已经废弃。当前所有 GC pricing 统一改为 `zeroDualExcludedJobs`：仅在根节点且没有 active cuts 时触发，预处理出 `pi_j=0` 的 job 后直接加入 source/sink 初始 `visitedSet`，后续 reachable set 只按父 reachable、visited 和 direct feasibility 过滤，不再允许 singleton 旁路。双向 join 的 visited 交集检查同步忽略这些 source/sink 共同预标记的 excluded job，避免把非真实访问标记误判为路径冲突。代码已同步到 `GC`、`GCBidirectional`、`GCNGBBStyleBidirectional`、`GCBBStyleBidirectionalFullDomain`、`GCBBAsymmetricBidirectional` 和 `GCBBStyleBidirectionalFullDomainNodeJoin`。

## 2026-07-17 启发式 pricing 有效搜索与空转诊断

当前结论不是“启发式 pricing 大部分时间无用”。按 50-job 两个完整 no-SRI 日志统计，返回至少一列的调用占启发式耗时约 75%--81%。但产出高度集中：`addedColumns>100` 的调用只占约 14%--15% 的时间，却贡献约 78%--85% 的全部新增列；相反，`addedColumns=0` 或不超过 10 的调用消耗 46%--64% 的时间，只贡献约 2%--3% 的列。这里的主要浪费位于低产调用和单个 seed 的搜索尾部，而不是 seed 收集、排序或列构造。

旧 50-2 逐 10 步日志的离线模拟显示：若一次调用前 20 步合计产出不超过 175 条，则跳过后 30 步，可省该批日志约 18.2% 的启发式搜索时间，仅少 21/21121 条候选，约 0.10%。但这是调用级汇总，若直接实现需要把 30 个 seed 都先跑 20 步并保存状态，控制流偏重，暂不采用。

因此新增了只在 `heuristicPricingDiagnostics` 打开时生效的诊断：记录所选 seed 中正值列数量、heuristic/exact/other 来源，以及每个 seed 前 20 步与剩余步骤是否产生负列。最新 40-2 root-only 采样共 59 次启发式调用、1752 个 seed：1066 个 seed 前 20 步无产出，其中只有 3 个在后续恢复产出，复活率约 0.28%；前 20 步有产出的 686 个 seed 中，345 个后续仍有产出。所选 seed 仅 306/1752 为当前正值列，来源则为 heuristic 1554、exact 93、other 105，说明当前 lowest-reduced-cost seed 几乎被历史启发式列占满。

由此得到两个后续候选。第一，最直接且实现简单的是单 seed 固定规则：至少跑 20 步；若前 20 步一条新负列也没有，则结束该 seed，其他 seed 和 exact pricing 流程不变。它不影响 BPC 正确性，只改变启发式搜索路径；按当前样本看误伤概率很低，但仍需在多个 40/50-job 算例完整 A/B 后才能默认开启。第二，可以测试给当前 LP 正值列或最近 exact 列保留少量 seed 配额，避免 30 个 seed 长期被历史 heuristic 列占满；该方向目前只有来源统计，没有收益证据，暂不改排序规则。

### 单 seed 前 20 步零产出提前停止 A/B

已增加独立开关 `heuristicPricingStopUnproductiveSeedAfter20`，默认关闭。启用后，每个 seed 仍按原规则运行；只有完成前 20 次 tabu 迭代且本 seed 尚未向本次调用的候选集合加入任何新负列时，才结束该 seed。已有产出的 seed、其他 seed、后续启发式调用及 exact pricing 均保持原流程。判断直接使用本地负列候选集合的增量，不依赖诊断统计开关。

40-2 root-only 同配置 A/B 中，关闭/开启后的 LP bound 均为 22490，incumbent 均为 22582，结果有效。总时间由 71.869s 降到 65.463s，root node 时间由 46.569s 降到 40.131s，启发式 pricing 由 25.474s/60 次降到 20.026s/52 次，约减少 21.4%；tabu 迭代由 54879 降到 43661，约减少 20.4%，共提前结束 903 个无产出 seed。pool 为 12122 对 12043，整体列规模接近。

50-2 root-only 对照中，LP bound 同为 39364.5，incumbent 同为 39598。历史关闭口径的 root node 为 243.263s，启发式 pricing 为 96.307s/149 次；开启后分别为 238.575s 和 90.687s/121 次，root 约快 1.9%，启发式约快 5.8%。但 pool 从 22308 增到 24457，master LP 时间基本不变，较大的 RMP 抵消了部分启发式收益。

当前结论是这条规则确实可以削减无效 seed 尾部，两个算例均保持相同 root bound 并减少启发式耗时，但端到端收益受列生成路径和 RMP 规模影响，幅度约为 1.9%--8.9%。因此暂时保留独立开关且默认关闭；至少还需要一个 50-3 算例和完整分支树 A/B，确认节点数与最终总时间不退化后，再决定是否默认开启。

### 启发式单次返回列少的机制

当前一次 HeuristicPricing 调用从 restricted RMP 中按 reduced cost 选择 30 条兼容 seed，每条 seed 最多做 50 次 tabu 迭代。每次迭代会枚举全部 REMOVE、未访问 job 的全部 ADD 和 EXCHANGE，但只保留 reduced cost 最好的一个 move、沿这一条轨迹前进一步，并只把该步形成的一个序列送入负列候选池。其他已完成成本评价的负邻居不会作为列保留。因此默认设置下一次调用理论上只检查约 30×(1+50)=1530 个轨迹状态；再经过 active signature/本轮 signature 去重、负 reduced-cost 判断、分支兼容和必要的 dual-window 真成本复核后，临近闭合时只返回 0--5 条列是正常结果。maxHeuristicPricingColumns=1500 和 local pool=5000 通常不是限制来源。

当前最直接的后续实验不是继续增大 seed、迭代数或返回上限，而是在 findBestMove 扫描时保留静态 top-L 个负 move：搜索状态仍只应用最优 move，但把其余 top-L 邻居对应的序列也送入现有去重和真成本检查。这样可复用已经支付的邻域评价成本，提高每轮列产出；风险是增加较弱列和 RMP 规模，应使用固定 L=3/5 做完整树 A/B。该思路尚未实现。
### Seed 同 reduced-cost 排序与非 best 负邻居诊断

本轮先不实现 top-L 邻居回收，只调整 seed 的同 reduced-cost 排序：仍先按 reduced cost 从小到大；相同则优先当前 LP 正值列，再优先任务数更多的列，最后按 column ID。Tabu 的 move 选择、状态更新和最终列返回均不变。40-2 root-only 与上面的 stop20-off 基线保持同一配置，bound/incumbent 仍为 22490/22582；root node 时间由 46.569s 降到 34.366s，HeuristicPricing 由 25.474s/60 次降到 18.787s/53 次，pool 由 12122 变为 14271。该单次结果说明新排序在本例中有正收益，但 seed 改变会连带改变列生成和 LP 路径，不能把 26.2% 的 node 降幅解释为稳定常数收益，后续完整树实验再判断是否默认长期保留。

同时增加仅在 `heuristicPricingDiagnostics` 打开时生效的负邻居计数，不构造这些非 best move 的 sequence，也不把它们加入候选池或主问题。此次 53 次 HeuristicPricing（含 3 次 FindFeasible）共评价到 4,979,245 个负 move，其中最终被应用的 best move 为 15,340 个，剩余非 best 负 move 原始上界为 4,963,905，占 99.692%。普通 50 次调用的非 best 计数平均 95,893.5，中位数 61，P90 为 331,042，最大 859,727，说明大量机会集中在 root 前段少数调用。这个数是 move 评价次数，不是唯一 sequence 数；它尚未扣除同一路径在不同 seed/迭代重复出现、active-RMP 重复、当前调用内 signature 重复、分支兼容和 dual-window 真成本复核，因此只能证明“被丢弃的负邻居很多”，不能直接声称可新增约 496 万条列。若后续真正实现，应只保留固定 top-L 并走现有完整过滤，不能全量收集。

### Seed 排序多算例 A/B 补充

本轮只比较 seed 同 reduced-cost 时的顺序变化，不继续细化非 best 负 move 统计。新顺序为：先按 reduced cost，再优先当前 LP 正值列，再优先较长序列，最后按 column ID。排序本身的计算开销可以忽略，实际影响来自 seed 改变后生成列批次、LP dual 路径和后续 pricing 轮次发生变化。
