# Codex `work3` 对话历史显示异常诊断

2026-09-01 核查任务 `work3`（thread `01a05003-d4cf-7183-a254-34a395b17826`）时，确认用户在界面中看不到后半段历史不是原始消息丢失，而是回合生命周期状态与历史读取结果不一致。

原始会话文件位于：

`C:\Users\Changxin\.codex\sessions\2026\08\30\rollout-2026-08-30T08-13-45-01a05003-d4cf-7183-a254-34a395b17826.jsonl`

核查时文件约 83.4 MB，包含 83 条 user-role message、229 条 assistant-role message。异常回合 `01a05698-3439-7bb1-87b9-2f3c3fd1fb54` 在 `2026-08-31T06:53:30.631Z` 收到 `task_started`，但 JSONL 中没有同一 turn id 的 `task_complete` 或 `turn_aborted`。该异常开始以后，原始文件仍保存了 27 条用户消息、104 条助手消息，并且有 23 个后续 task 正常完成，说明数据仍在。

应用读取接口却把异常回合报告为长期 `inProgress`，并把大量后续消息聚合进该回合；桌面日志在重新打开任务时又报告 `latestTurnStatus=interrupted`、`markedStreaming=true`、`turnCount=5`。同一个回合同时表现为 API 的 `inProgress` 与桌面恢复状态的 `interrupted`，且 `turnCount=5` 明显低于原始消息数量。这一状态不一致足以解释前端只显示少量历史或无法逐条加载后续对话。

进一步用 Codex app-server 在会话副本上重建历史时，得到更直接的错误：`expected ordinal 5488, got 5487`。逐行核查发现 JSONL 第 5488、5489 行都使用了 `ordinal=5487`；前一条是异常回合末尾的 token-count 事件，后一条是应用重新开始后写入的 `thread_settings_applied`。因此，真正阻止历史投影的直接原因是事件序号在应用恢复时重复，孤立未闭合 turn 是同一次中断留下的相关状态症状，而不是唯一根因。投影器在重复点停止，后续原始消息虽然存在，却无法进入正常的 turn 索引，界面因此只能显示重复点以前的少量历史。

修复前先复制完整会话，在副本中将第 5489 行及其后所有事件的 `ordinal` 统一增加 1。副本验证结果为：序号断点由 1 降为 0，app-server 可正常重建 55 个 turns，异常回合被识别为 `interrupted`，其后的回合重新独立出现。随后在 Codex 完全退出后对原文件执行同样的机械修复，共顺延 4547 条事件；原件备份到 `C:\Users\Changxin\.codex\repair-backups\work3-20260901-142139\`。重新打开后，界面历史恢复。最终文件共有 10045 行，末序号 10044，序号断点为 0。

最终结论：这是 Codex Desktop 在异常回合后恢复写入时复用了上一事件序号，造成 durable rollout 投影失败的本地会话历史 bug，不是 context compaction，也不是消息内容丢失。若提交 bug，应提供 thread id、异常 turn id、Codex Desktop release `26.825.51511`、`expected ordinal 5488, got 5487`，以及桌面日志中的 `latestTurnStatus=interrupted / markedStreaming=true / turnCount=5`。
