# 当前代码多模块交叉复核

本轮确认两项残留：详细排程回算遗漏首任务在全局 horizon 的退化边界，会使结果导出失败；TI+SRI 独立候选堆没有同步普通 TI 的过期项压缩，保留多余对象。没有确认新的 NG-DSSR 定价、CB、半域占优或主问题证书错误。此次只检查、复现和记录，没有修改正式源码、求解配置或远端任务，不把零新发现当作任意输入的正确性证明。

四名审查者分别负责 PWLF/NG 扩展与单点、NG CB/join、普通 TI/TI+SRI、LP/PC/Tree 修复及分支。NG 扩展与 CB 审查者互相核对 store 前剪枝、方向等待、Tmid 取整和替代 split；TI 与 master 审查者交叉检查候选堆是否影响 top-K；主线程独立复跑两项诊断，并核对最终输出调用链。没有重启已故障的 Java LSP，没有把并发上限拒绝的额外智能体计入审查人数。

## 2. 详细排程回算的首任务 H 边界

`TWETColumnEvaluator.evaluate()` 已单独接住首任务 `p[j]+s[0][j]==CmaxH` 的有限值，但 `evaluateTiming()` 仍调用 `Solution.calCost()`。旧的首任务构造执行 `penalty.setDomain(H,H)`，公共零宽裁剪按原契约清空函数；随后 `calCost` 直接读取 `lastF.tail.end`，抛出空指针。正式 runner 显式开启详细导出，`BPCResultWriter.writeDetailedArtifacts()` 会调用这一入口。普通配置默认关闭详细输出，不等于正式导出不会暴露此问题。

最小输入为一个任务、一台机器，`p=1`、due 为零、早晚罚权均为 1、setup 全零；自然计算出 `H=1`，未手工修改 Data 或罚函数。`evaluate([1])=1`，但 `evaluateTiming([1])` 在 `Solution.java:1215` 失败。固定同一合法 seed，仅切换详细导出开关，NG、TI、TI+SRI 共六次整 solver 调用：关闭时三者均正常返回 `UB=LB=1`；开启时三者均在 Writer325 → evaluateTiming121 → calCost1215 失败。固定 seed 只是隔离输出链，不说明这个输入的普通启发式初始化也能通过。

这属于此前记录已排除补丁范围的 `evaluateTiming→Solution` 残留，不是最近的 add/shift 修正引入的回归，也不是发现错误的定价下界。本次首次补齐整 solver 导出证据。对于正加工时间、非负 setup 且粗窗不再收紧全局 H 的多任务纯调度输入，原 horizon 严格大于每个首任务最早完成时刻，可以排除这条精确触发链；本轮没有逐份重审正式集合，不能把任务规模大直接当作排除证明。外包粗窗可能收紧全局 H，因此不能推广为一般输入不受影响。

最小修正方向是让 timing 所用的首任务 forward 构造同样接收合法 H 点，保持公共 `setDomain(H,H)` 契约；不要捕获异常后跳过明细、填造完成时间，或为此改全部启发式函数。此轮尚未实施。

## 3. TI+SRI 候选堆的过期对象

`TimeIndexedGraphRank1CutPricingEngine.rememberCandidate()` 遇到同签名更优候选时替换 map 并追加 heap。map 未满 K 时，`isPotentialTopCandidate` 直接放行，超额淘汰也不执行，因而旧对象可一直保留到此次 pricing 结束。map 满时惰性清理也只清堆顶。普通 TI 已在对应入口按过期比例重建堆，SRI 的独立实现未同步。

真实 labeling 诊断使用三任务两机器，`p=50`，due 为 `100/150/150`，早晚罚权均 1、setup 全零，自然 `H=200`。只为隔离此机制注入受控对偶：job 为 `(100,100,0)`、machine 为 `-100`、三元 SRI dual 为 `-1`；没有声称这些数值已在正式 RMP 出现。full/node/arc memory × heuristic/exact 六组结果一致：有效候选 5、物理 heap 149、过期 144、返回 5 列、bestRC 为 -99。公开 `price()` 同样能进入此分支。配置上限 300，但 heuristic 有效 K 为 50，所以 heuristic 已实测物理 heap 超过 K；exact 本例未超过 300，不夸大为 exact 已实测超上限。

对象身份检查仍能得到有效的最差候选，最终从 map 取值排序，不会因旧堆项返回旧列或破坏原 top-K 语义。问题是额外对象引用、堆维护和内存寿命；没有仅由 K 决定的物理堆容量上界，不等于固定有限搜索中的无限循环或跨调用泄漏。未量化正式实例的总时间/OOM影响，不能拿此诊断解释历史 SRI pricing 爆炸的全部原因。

最小方向是同步普通 TI 的 `heap.size()>2*map.size()` 重建逻辑，保留 Candidate、ID、比较器和 map；清理引用不会立即缩小 PriorityQueue 的底层数组，也不能预先宣称收益很大。此轮尚未实施。

## 4. 本轮验证与后续边界

61 项已有回归重新编译、以当前 solver JAR 优先运行，全部通过，覆盖端点、CB/delta/尾格、traced join、占优、修复成功/不可行/超时、分支、禁弧存储、TI 维护等。另重跑 120 组小实例的独立原始目标最优值对照，三算法、Arc/Cluster、显式/列化外包及不同 tariff 均无不一致，其中 30 组实际进入多节点。这里只把它作为这些输入的证据，不将所有 ROOT_PROCESSED 状态一概称为全树最优证明。

两项新诊断由主线程独立复跑并与审查者交叉确认。证据放在 `data/20261108-current-code-review/`：`TimingBoundaryAudit.java`、`horizon-single.dat`、六次调用输出、`SriHeapProbe.java`、`heap.dat`、六组堆输出、回归退出码 CSV 及 120 组 oracle 输出。诊断 fixture 不纳入正式性能统计；运行中的远端长 join 任务未查询、修改或中断。

当前结论是两项范围明确的残留，一项在最终时间回算，一项在 TI+SRI 候选维护；NG-DSSR 主体本轮未确认新的正确性或效率缺陷。没有据此修源码或部署，后续修改仍应围绕各自最小入口验收，不扩大公共 PWLF 或正式求解策略。
