## 2. 分工与实施约束

最初按模块分配过写入任务，随后用户明确要求“一个人改，其余人检查”。收到要求后立即中断四个智能体的写入，保留已经产生的局部草稿，由主线程统一审阅、修改和集成；之后所有源码、测试及文档修改均由主线程完成。不能把最终分工倒写成从未有过初始草稿。四个智能体均按用户指定使用`gpt-6.1-sol`、`max`，转为只读交叉检查：Helmholtz/Kant检查add与trim，Hume检查标量/融合及独立oracle，Kierkegaard检查CB、评价器、Phase-I和验收范围。没有多方继续并发修改或各自提交。

目标是保留原顺序扫描和正常连续输入快路径，仅端点事件做局部检查，真实补片才分配新段。scalar/traced不物化短片；融合不使用新增全函数回退；CB不全局放宽merge，候选成功后辅助点单独复用公共接收且不含当前任务成本。Phase-I窗内0窗外M须有真实物理段，保留原窗口口径，不另修delta metadata。

## 4. 实际修改

1. **shift左裁**。仅修`trimToDomain`：删除条件由带容差的`end<=domainStart`改为实际`end<domainStart`，同时入口和截头采用真实几何比较，保留恰好接触左界的点，不把实际分离但相差不到EPS的区间误收。shift公式、右裁及零宽metadata清空规则不改。

2. **普通add**。仍一次顺序扫描，不建端点表、不反复回扫输入。普通区间保留原相加；共同换段、点交集或有下一段的末端才补核。普通内部事件可由一方连续或双方同向跳跃直接跳过；其余读取真实闭覆盖的有限左右值。只有端点新低值低于两侧可表达值超过原EPS才接收。起终点、单侧耗尽、真正整体点不用内部快路。推进依据实际段端点，避免EPS把不同的短区间当成同一个结束点。

短平台左右各最多`0.0005`，按补片前紧邻区间半长限宽；半长不超过EPS则只覆盖该条紧邻极短区间，不继续向外吞。流水输出接回其余区间，后续段从已有尾端之后输出，不重写补片、不截掉段链。平台在真实点`t`拆成两条同值正长半片，使直接读取`t`仍能识别接点；不增加补宽，也不制造内部零长残段，方向最小化可重新合并。整条计算域本身也为点时才保留整体点例外。输入函数不修改，不做用户已否决的成本交点保护。

3. **快速最小和及traced join**。linked、固定flat view及shifted查询共享局部端点补核，直接比较真实值，不铺近似平台。NG traced查询保持同样的实际交集与共同端点规则，新低值与对应forward/backward来源同时更新；相等时保留原代表，不引入source相同等新门槛。真正不相交的区间不按EPS虚构交集。

4. **融合插入**。linked/flat两套同步：前缀与任务相加的端点新低值在交付过去区间后才进入`runningMin`；后缀共同终点暂留旧段，供下一个前缀接点匹配。suffix已是后缀最小化的非减函数，因此无需再额外窥探更右侧段。最后实际时刻的最新值必须交付给后缀，同时刷新尾状态，随后才执行既有`endpointLowerBound`和成本截断。保留原常数成本、有限上界和调用合同，没有物化全函数fallback。方法注释同步写明输入prefix/suffix已做方向最小化，不再用存在旧漏点的addShifted结果定义正确性。

5. **列成本评价器**。保留任务硬窗和原计算顺序。后续任务自然共享shift/add补丁。首任务`p+s==H`不经过add，单独从原任务函数读取H处真实有限值，以原正宽metadata接收整体点；`p+s>H`不救回，M或非有限端点不救回。继续原setup、前缀最小化与尾值读取，不另设第二套H平台。

6. **CB有限点接收与Phase-I表示**。CB移位后仅局部识别实际整体有限点，允许其先按方向取小并形成合法等待闭包，再加当前任务成本；普通空函数、窄段及M不冒充整体点。成功候选中的辅助U/R若仍为整体点，通过与全域零函数相加复用上述接收，既不重复加当前任务成本，也不回写F/B。全局正长merge门槛不放开。

Phase-I任务函数统一为完整`[0,CmaxH]`物理段，窗内真实成本0、窗外M，复用已有`setDomain(...,true)`及退化硬窗政策；临时全域零函数在复制后释放，job0直接保留全域零。这样恢复普通F右端H/B左端0的不变量，两种delta传播不再因Phase-I短物理域误裁。两个delta builder、队列和merge算法不另加补丁。

生产修改只涉及`PiecewiseLinearFunction`、`GCNGBBStyleBidirectionalNgDssr`、`CompletionBoundCalculator`、`TWETColumnEvaluator`四个文件；公共方法调用方会自然获得补丁行为，不能说其他调用方数值完全不可能变化。没有调整probe阈值、初始中点、DSSR、memory、分支、profile、TI网络、外包模型或有限M确认流程；远端未连接、未部署、未停启。

## 6. 性能与未扩大处理的边界

正常连续20段add单独做三轮交错JVM微测试，旧版均值约256ns/次，新版约335ns/次（约增加31%，绝对约0.079微秒），checksum均为7100000。原始输出见`add-benchmark.json`。本轮是正确性补丁，不宣传为add加速，更不能据此推断整树加速/退化比例。实现保持线性扫描、普通段不分配补片，不增加全表、事件缓存或head反复重扫。完整求解性能尚未重测。

额外运行旧`PiecewiseLinearFunctionPropertyTest`，补丁前后均为26通过、2警告、7失败，报告逐字节一致，SHA-256为`E3DD4CDF8A5CC95FE8A463180E7EAC03DA42EC246E6A3C73DF284CDFCE737EB2`。其中有两项将原本要求正长重叠的merge用于不相交域，另五项为旧随机非frontier路径；本轮未修改其生产算法或掩盖失败。因此“30项通过”不等于这个历史广义property程序全部通过。

另保留一项人为极端输入诊断：旧`evaluate`按EPS定位，在反向normalize合并后遇到距离断点约EPS的查询点，可能跳过真实段。诊断例中新add的`t=5`可读为-11，反向normalize后数学闭值仍-11，但旧evaluate(5)可读成5。该定位问题未通过改公共EPS、evaluate或normalize扩大修复；诊断保存在测试的`eps-diagnostic`模式及结果文件。它证明通用求值在这种输入下不自洽，但尚未证明当前主线能够生成这种输入，不能列为已确认的正式求解故障或本次补丁实际残留故障。

重现该诊断：第一个函数为`[0,5]:8; [5,5.000001]:-4; [5.000001,10]:-4`，第二个为`[0,5]:-7; [5,10]:9`。反向最小化后平台合并为`[0,5.000001]:-11`，但浮点减EPS的严格定位与绝对差判等之间留有旧数值缝隙。运行新专项的`eps-diagnostic`参数可输出三种值；默认30项回归不把这个诊断打印解释为已通过的精确读值断言。

用户指出正常补片不会这么窄后，进一步核对：`[5,5.000001]`是诊断源码手工预置的原邻段，不是0.0005补片自行细分产生的。该例中的平台右端受这个已有极短邻段限制，反向合并后才暴露旧定位缝隙；没有给出正式输入或实际label产生该邻段的调用轨迹。因此撤回将它直接表述为当前主线残留问题的定位，仍按此前约定不扩大极端短段处理、不改evaluate；也不反向声称全库存在大于EPS的统一最小段长保证。

本次用户确认的工程判断与此前第7项极短段讨论一致：确实承认段长或查询点与断点距离小到EPS量级时可能出现上述数值问题，但一般流程不太容易缩到这个量级。正常补片采用0.0005半宽，随后方向最小化会吸收孤立低点，不能将每轮新补点等同于对旧平台不断细分、一路缩到EPS。因此先保留现有实现，不修改evaluate、不增加新合并或防御分支，实际出现再定位处理。这里的“一般不会出现”是当前工程判断，不是已统计的发生率，也不是数学上的绝不发生；该诊断继续作为极端输入边界记录，不提升为当前正式求解故障。本次只记录共识，不改源码、配置或远端。

按用户决定暂缓极端密集短段不断相邻的全面处理。0.0005平台是已接受的局部近似，可轻微提前/延后成本、也可能覆盖邻近更低值，没有统一目标误差保证。本轮不把它改写成完全精确算法，不从几个例子推断其在正式数据中的频率或影响。
