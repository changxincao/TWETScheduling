# 正式计算实验基础设施

本文记录三种精确定价方法、外包模型实验、数据派生、结果输出和服务器批处理的统一入口。当前目标不是立即跑完全部矩阵，而是先固定可复现的配置、数据生成规则和输出口径，使后续更换服务器后只需要调整 manifest 即可运行。

## 1. 三种算法的固定配置

正式入口统一使用 `BestBpcProfiles`，版本为 `2026-08-16-v1`。三个 profile 分别是 `NG_DSSR`、`TIME_INDEXED` 和 `TIME_INDEXED_SRI`。它们共享 ALNS 60 秒初始解、best history、20 个 strong branching 候选、关闭第二阶段、Phase-I repair、dual-bound pruning、关闭 dual stabilization、RMIH 和 route enumeration。每个子 JVM 都强制 CPLEX 单线程。

`NG_DSSR` 使用 nearest K，K 自动取任务规模的十分之一；DSSR 使用 C=1000、K=20 和 `minimumNewPairsSegment` 更新；启用 incremental sourced dominance graph、group-envelope join 预筛、visit-profile 剪枝、all-cycles completion bound、midpoint probe、root time-indexed preprocessing 和最多 200 条 elementary seed 列。hard subtree elimination 关闭，只保留 pricing-only fixing；历史和同节点 warm start 关闭；time-indexed preheuristic 关闭。

`TIME_INDEXED` 使用 dual window、每次最多返回 300 条精确列和 paper arc fixing，不使用外部启发式 pricing，不加 rank-1 cut。`TIME_INDEXED_SRI` 在相同图定价基础上启用 arc-memory rank-1 cut、最多 8 个 cut rounds、每个 job 最多出现在 20 条 active cuts 中，并在 cut loop 中执行 fixing。

这些值来自最近几轮已经反复使用的正式配置，不再从历史日志穷举重新挑参。集中 profile 的作用是防止 runner 之间复制后漂移；后续若确需改参数，应修改 profile 版本和对应回归测试，而不是在单个实验入口临时覆盖。

## 2. 实验矩阵与数据规则

数据生成入口为 `Common.FormalExperimentSuiteGenerator`。默认从 40、50、60、100 个任务的单机基准派生多机实例。60 个任务没有原始单机目录时，确定性截取 100-task 基准的前 60 行形成派生集。任务数不超过 60 时生成 2、3、4 台机器；100-task pilot 生成 2、3、4、5 台机器。现有数据文件不会被覆盖。

机器转换继续使用 `ETConverter` 的确定性 sequence-dependent setup time，平均 setup 水平约为平均处理时间的 0.5，并通过 Floyd 闭包保证三角不等式。正式 scenario 在内存中派生，不修改源文件：处理时间、due date、release time 和 setup time 同比例缩放；due window 以原 due-window 中点为中心重设；setup cost 由 `setupCostCoefficient * setupTime` 控制。当前 manifest 将 setup cost 系数固定为 0，setup time 已存在；setup cost 或 setup 强度的额外实验应作为独立扩展块，不与所有时间尺度和窗口档位做全因子乘积。

纯调度比较默认使用 n=40/50/60，m=2/3/4，时间尺度 1/5/10，due-window 半宽为平均处理时间乘以 0/2/6 后再随时间尺度同步放大。三种算法在同一个 scenario 下共享完全相同的固定初始列快照。n=100 只生成数据并进入 `instances.tsv`，默认不进入完整精确求解矩阵，待 pilot 确认可计算性后再加入。

外包实验不与时间尺度矩阵做全因子乘积。默认在原时间尺度和中等窗口上比较 SP1 `columns` 与 SP2 `masterVariables`，并分别生成外包单位费率 0.75/1.00/1.25 和折扣强度 0/0.15/0.30 的实验。当前令任务外包基数 `b_j=p_j`，使用三段连续数量折扣函数。这些费率是可运行的 pilot 档位，不是最终论文校准值；正式计算前应先确认不会造成全外包或完全不外包，再冻结参数。

## 3. 固定初始列和公平比较

每个 scenario 先执行一次 `FormalExperimentRunner --action=seed`。该步骤在目标 scenario 上运行统一 ALNS 和初始列构造，并将 initial sequences、incumbent sequences 和 SHA-256 fingerprint 写入 UTF-8 seed 快照。三个算法随后读取同一快照，但仍用各自目标数据的 evaluator 重新计算列成本，不跨实例复用数值。

manifest 用 `dependsOn` 显式连接 seed run 和 solve run。seed 失败时，依赖它的求解任务写为 `BLOCKED`，不会在缺少固定起点时偷偷改用另一套初始列。已有 `SUCCESS` 标记的任务会跳过，便于服务器断点续跑。

## 4. 输出与实时监测

每个正式 run 都有独立目录。`live.log` 在求解过程中持续写入，已打开 stage heartbeat 和 node progress summary，可以实时查看 node、incumbent、bound、gap 和阶段耗时；高频 pricing 诊断默认关闭，不进入热循环。

求解结束后，核心文件包括：一行结果 `core-summary.csv`，组件调用和耗时 `components.csv`，节点过程 `nodes.csv`，最终 incumbent 列 `columns.csv`，列池聚合 `pool-summary.csv`，cut 明细 `cuts.csv`，外包决策 `outsourcing.csv`，配置快照和 Markdown 摘要。正式入口额外开启 `writeDetailedBPCArtifacts`，输出全局列池 `pool-columns.csv` 和逐机器、逐任务完工时间及成本分解 `incumbent-schedule.csv`。这两份大文件只在求解结束后构造，普通入口默认关闭，因此不影响 pricing、LP 或 branch-and-bound 热路径。

调度器还为每个子 JVM 写出 `stdout.log`、`stderr.log`、`status.txt`、`args.txt` 和成功标记。核心结果与辅助诊断分文件保存，后续汇总不需要解析超长求解日志。

## 5. 服务器运行入口

先编译项目并确保 CPLEX jar 和 native library 可用。生成实验包：

```powershell
java -cp "target/classes;D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/lib/cplex.jar" Common.FormalExperimentSuiteGenerator --dataRoot=data --outputRoot=experiment-suite/formal-v1 --casesPerSize=3 --sizes=40,50,60,100 --timeLimitSeconds=7200 --maxNodes=100000
```

启动最多四个独立 JVM：

```powershell
java -Djava.library.path="D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/bin/x64_win64" -cp "target/classes;D:/软件/cplex/ILOG/CPLEX_Studio2211/cplex/lib/cplex.jar" HEU.ExperimentBatchScheduler experiment-suite/formal-v1/manifest.tsv 4
```

`ExperimentBatchScheduler` 不在单个 JVM 中开四个求解线程，而是维持最多四个独立子 JVM；每个子 JVM 内部 CPLEX 固定为一线程。任一任务结束后，调度器立即提交下一个依赖已满足的任务。除总 `manifest.tsv` 外，生成器还在 `manifests/` 下分别生成定价比较、外包模型比较、外包价格和折扣实验入口，每个子 manifest 自带所需 seed 任务。迁移到服务器时需要携带代码、编译产物或构建脚本、data、生成后的实验包、CPLEX jar/native library，并修改服务器上的 CPLEX 路径。

## 6. 当前验证和边界

已完成 profile 回归、固定 seed 序列化、数据派生、manifest 依赖、四进程调度成功/跳过/失败传播，以及求解后 CSV 写出的 focused 测试。所有测试均通过。本轮没有启动长时间 CPLEX 正式算例，因此当前确认的是基础设施和配置口径，而不是整套实验的运行时间或论文结论。

正式大批量运行前仍建议先取每个实验块各一个小样本做服务器 smoke test，确认 CPLEX native library、`live.log` 增长、三算法 seed fingerprint 一致、输出目录和磁盘占用正常。之后再直接使用同一 manifest 扩大 `casesPerSize` 或追加 n=100 pilot。
